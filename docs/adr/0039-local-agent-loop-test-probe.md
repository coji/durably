# ADR-0039: local-agent-loop runs a candidate's new and changed tests on the base and on the candidate, and hands the result to the reviewers as trusted context

## Status

accepted

## Context

In `examples/local-agent-loop`, the review rules of a repository run say that a new test which would pass against the base commit does not count, and ask for `needsChanges` when it would. The reviewers cannot check that. A Claude reviewer may only read, a command reviewer gets read and search tools and subagents, and Codex reviews in a read-only sandbox. The review snapshots are trees extracted from commits, without installed dependencies. So a reviewer judges by reading the code whether a test exercises the change.

Issue #307 reports what that costs on artifactshare: more than four in ten of the correctness reviewer's findings say, in some form, that it could not run the tests, and most runs that stopped at the review cap had a correctness reviewer asking for changes in the last round. A reviewer that cannot tell plays safe, and every such `needsChanges` is a repair round.

ADR-0038 added the path for this: a stage reads a file it produced inside its own step, and `withStageContext` registers the settled content for the reviewers' TRUSTED CONTEXT, with a copy outside the worktree that every reviewer may read.

## Decision

- **`testProbe` in `factory.json`, fixed at trigger.** One to twenty `{ glob, command }` entries, each glob at most 200 characters, so the globs the result lists stay a few KiB of its 32 KiB. `command` is argv and must have at least one element that is exactly `{files}`; an element that merely contains it is refused, so the path is never split or expanded by a shell or a tool. The value is validated and stored in the run input at trigger, inherited by `retrigger` and by a repair run, and read again only by `--reload-config`, like `selfCheck` and `parallelReview`. It is not part of `configVersion`: it adds a result to the reviews without changing the roles' calls.
- **What runs.** The `added:` and `modified:` lines of the sealed candidate's `changed-files.txt` whose repository-relative path matches a glob (`path.posix.matchesGlob`), each once, with the first entry it matches. Deleted, renamed and copied files never run. Each file runs on its own, with an argv computed once per file by replacing each `{files}` element with its path as `./<path>`, so a name starting with `-` is never read as an option, and the result is per file. Every command runs with `CI=true` added to its environment, so a snapshot runner such as Vitest or Jest fails on a missing snapshot instead of writing it and passing. A path that leaves the worktree, through a link included, is recorded as not run.
- **A separate base worktree.** With `testProbe`, setup adds a detached worktree at `baseCommit` beside the agent's, `runs/<id>/base-work`, and runs the same `setupCommand` in it. Right after that setup succeeds, the untracked files it left that `.gitignore` does not cover (`git ls-files --others --exclude-standard`) are recorded in `runs/<id>/test-probe/base.json`, each with a fingerprint of what it holds (the sha256 of a file's bytes, a link's target, a directory's whole contents walked in sorted order: each entry's name with a file's sha256 or a link's target, so an edit inside an untracked nested repository shows). For each candidate the probe resets it to the base, removes every untracked file `.gitignore` does not cover that is not in that record, and, within every untracked directory `git clean` would remove, each directory that holds no file once the empty directories below it are gone, deepest first, never a file or a nested repository, so what an earlier candidate's tests wrote goes while a fixture `setupCommand` generated stays, as it does in the agent's worktree, where the first seal commits it (ignored files, such as installed dependencies, stay too). It then checks every recorded path against its fingerprint: one an earlier test changed or removed can only come back from setup, so the base is removed and made again with setup, and recorded again; a setup that fails then makes the base side not run, with the reason. A base whose record lacks the fingerprinted list, made before it existed, is made again too. It then checks out only the matching test files from the candidate commit, with literal pathspecs, all at once and, when that fails, one at a time, so a file git cannot put there leaves only its own base side not run, with the reason. It runs each file there and then on the candidate side, in the agent's worktree, which `assertIntact` proved is the sealed candidate. Afterwards the agent's worktree is reset to the candidate commit and cleaned with `git clean -ffd`, so a test that rewrote a tracked file or wrote a new one leaves nothing for the check, the reviews or the next seal's `git add -A`, and `assertIntact` runs again. A nested repository the seal committed as a gitlink, such as one setup made, is one neither puts back, so each one git then reports as changed, by an edit or a commit inside it, is reset to the commit its gitlink records, one level down; its untracked files stay, as no seal holds them and the check may need them, so untracked files alone do not make one count as changed (`git status --ignore-submodules=untracked`, which also overrides config that would hide nested repositories, for this listing and for `assertIntact`). One that cannot be reset, or that git cannot read at all, such as one whose index a test corrupted, is left for `assertIntact`, which reports it as `candidate-mutated`. Only the matching files come from the candidate: overlaying its other files on the base would test the change, not the base. So a test that needs a fixture, snapshot or helper the candidate added and no glob matches fails on the base for that reason alone; the result text says so, and the output tail shows it.
- **A worker that dies mid-probe.** While the tests may touch the agent's worktree, a marker `runs/<id>/test-probe/<candidate>.running`, outside both worktrees, says so; it is removed once the worktree is back as sealed. A verify stage that finds it, which means the probe step never completed, puts the worktree back the same way before its `assertIntact`, and the probe runs again. `assertIntact` is not weakened otherwise.
- **Failures are results.** A base worktree that cannot be added or set up does not fail setup: it is removed again and its reason stored, and every probe records the base side as not run for that reason while the candidate side still runs. A command that cannot start, or runs past its limit, is recorded as not run with the reason; one that ran past its limit keeps what it printed until then. Each subprocess has the run's `checkTimeoutMs` and an output cap. Only a cancel, a lost lease, or a candidate that no longer matches its seal stops the run.
- **One checkpoint per candidate.** The probe is the verify stage's step `stage:<n>:verify:test-probe`, run before the check, and with `parallelReview` completed before the `step.all` that starts the check and both reviews. Only the verify stage runs or reads that step. Its output is the per-file record, each side's output tail for every file included, and the `test-probe` stage context read inside the step with `readStageContextFile`; a replay after a worker restart reads the output back and runs nothing.
- **The result reaches the reviewers through the run state.** The verify stage's event (`verify.completed`, or `verify-review.completed` with `parallelReview`) carries the settled context. The reducer registers it with `withStageContext`, which replaces an earlier candidate's `test-probe` entry in `setup.target`, and the job builds the target again whenever `setup.target` changes, so the sequential review stage that follows gets a target with it and reads nothing back itself. The verify-review stage reviews within the same stage, so it registers the context the same way and builds its reviewers' target from that setup. Both Codex and Claude reviewers, prompt and command forms alike, get it in the TRUSTED CONTEXT through `prepareStageContext`, as ADR-0038 describes. The result file is written under `runs/<id>/test-probe/`, outside both worktrees.
- **The result is evidence, not a verdict.** The text lists per file the exit code, time and output tail on each side, the end of stdout followed by the end of stderr, neither able to push the other's end out of the tail, and one of: failed on the base and passed on the candidate, passed on both, failed on the candidate, could not run. It says so when no file matched. Tails shrink, then files past the first few are left to the count, and last the globs line goes, to keep it within the 32 KiB stage-context limit, so the probe step never fails on size; the stored record keeps every file's tails whatever the text had room for. The text itself says how to read it: a failure on the base proves nothing about the behaviour when the test only failed to import something the base lacks, or a fixture no glob matched. The review rules stay generic: when a `test-probe` result is attached, judge the tests from any trusted stage result that covers them and read the code only for a test none covers; without one, the rule is as before.
- **Cleanup.** The base worktree is removed, directory and git registration, when the run ends. `git worktree remove -f -f` takes the registration with the directory, also one left locked by a `git worktree add` that was killed and one whose directory is already gone, a directory git refuses is then removed outright and its registration taken again, and the record goes only once `git worktree list` no longer names the base, so a git that fails leaves it for the next cleanup too; it is written before the worktree is made, so a worker that dies midway leaves the record, and the startup sweep, which also looks for a record without its directory, prunes the registration in the repository the record names, even when the run's own record has been deleted. It is removed when the run completes, and with the review snapshots when it fails or is cancelled, also when setup fails after making it or preflight fails. A setup cancelled while making it removes what it made. A cancel from another process, which the worker sees only as a lost lease, removes it in the cancel itself, and the worker's startup sweep removes what a race with that cancel or a dead worker left of an ended run; its path follows from the run's directory and its repository from its record, or else from the run's setup or input. A wait for a person, on the spec or on the approval, does not end the run and keeps it, so the probes after a spec wait need no second install; Durably suspends by throwing from `step.waitFor`, so the job tells a suspension from a failure by that error. A lost lease leaves it for the worker that resumes, and a probe that finds it gone makes it again. `removeRunWorktree`, used by an approved delivery, `demo archive` and `demo prune --apply`, removes each of the run's worktrees, the agent's and the base, the base the same way as above with its record, and prune counts them as one entry.
- **Report.** `testProbes` in the JSON report, and a Test probe section in the Markdown when there is one, give per candidate the number of files, how many failed on the base and passed on the candidate, as the result text counts them, the time and the reasons a side could not run, read from the stored steps.

## Consequences

- Reviewers judge whether new tests exercise the change from what the factory saw, and fall back on reading the code only where the probe had nothing to say.
- A run with `testProbe` installs dependencies twice at setup and runs each new test file twice per candidate. The base worktree stays on disk while the run waits for a person.
- What is trusted is what the factory itself did: it chose the files, ran the commands and recorded the exit codes and times, outside the worktree the implementer edits. The test code, and so every exit code and everything it prints, is the candidate's. The result text says so and fences the output tails, which a reviewer reads as data, never as instructions.
- A run without `testProbe` has no base worktree, no probe step and the review rule it had.

### Known limits

Left as they are after issue #314, each for the reason given:

- Tests in one candidate see each other's changes, on both sides: the worktrees are put back per candidate, since a reset and a clean per file would multiply the probe's git work by the file count for a case the output tails already show.
- A worker that lost its lease midway through a removal, while another worker took the run over, can in its `finally` remove the probe output or marker the new worker wrote (R2-O-2); fencing each removal by the lease generation is out of proportion to a race that needs both a lost lease and a takeover inside that window.
- A `base.json` whose repository is gone stays, and every startup sweep tries it again: a deleted repository cannot be told from one on a volume that is not mounted, and dropping the record in the second case would leave its registration for good.
- `restoreBase` removes untracked files one at a time and fingerprints every recorded path on each probe (C4-2); that is slow only for a setup that leaves very many untracked files, and keeping setup's files needs the per-path work.
- The probe has no limit of its own, so it may take up to two runs of `checkTimeoutMs` per file, after a base setup that runs in the setup step (O-14); a limit would need its own setting and a policy for a half-run probe, which no run has needed yet.
- The job tells a Durably suspension from a failure by the message `Durably execution suspended` (O-7); a type or predicate for it belongs in the library's exports, outside the scope of this example.
- The check that a path stays inside a worktree is written out in five places (O-11), and the verify-review stage registers the stage context and builds its target as the reducer does, with `createTarget` on every stage's services for it (O-12); merging them is a refactor with no change in behaviour, left for one of its own.
- `git worktree list --porcelain` is read without `-z`, for older git, so a worktree path with a line break in it is not recognised; the factory makes no such path.

## Rejected Alternatives

### Run the probe in the base review snapshot, or check out the base in the agent's worktree

Rejected. The snapshots have no dependencies, so the tests could not run there. Switching the agent's worktree to the base and back would put the sealed candidate at risk between the switch and `assertIntact`, and with `parallelReview` the check runs in that worktree.

### Give the reviewers permission to run the tests

Rejected for now, and out of scope of the issue. The reviewers' read-only boundary is what lets them read untrusted candidates safely; a fixed, factory-run probe gives them the one result they most need without widening it.

### Pass all matching files to one invocation

Rejected. One exit code for many files cannot say which test failed on the base, and the reviewer needs that per file.

### Stop the run when the probe cannot run

Rejected. The probe is evidence for the reviewers, not a gate. A run without it is no worse than before, so its failure is written into the result and the report and the run goes on.

### Key the probe step by candidate

Rejected. A step under the verify stage's key keeps the probe's time in the verify stage of the report's timings and visits, and every stage table stays as it was.
