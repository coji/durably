# ADR-0023: local-agent-loop reviewers choose their command, context and output

## Status

accepted

## Context

The two reviewers of `examples/local-agent-loop` (`correctness` and `edge-cases`) are called with a fixed review prompt and read with a fixed `DECISION`/`NOTES` parser (issue #248). A repository that already has a formal review procedure, such as a Claude Code slash command backed by subagents, cannot run that same procedure inside the factory: the factory sends its own prompt, the subagents never see the review context, and the procedure's structured findings do not fit the verdict format.

Running such a procedure needs three things the factory did not have: a way to send the repository's own command, a way to give the review context to subagents that do not see the parent prompt, and a way to read structured findings strictly enough that an unfinished review never passes. It must not weaken what the factory already guarantees: a review never writes, an uncertain call is never resent, a reply that cannot be read is never a pass, and a run whose settings did not change keeps its `configVersion`.

## Decision

- **Three optional fields per reviewer.** `profiles.review.correctness` and `profiles.review.edge-cases` in `factory.json` take `command`, `context` (`prompt` or `local-instructions`) and `output` (`verdict` or `findings-json`), each independently. A lens that names none keeps the factory prompt and the verdict. A lens that names any has all three fixed at trigger, defaults filled in, stored in the run input and the setup record, and hashed into `configVersion`; with no lens configured the hash input is unchanged.
- **Commands are opaque.** The engine knows no command name and no lens-specific behaviour. `command` accepts only `{effort}`, `{base}` and `{head}`, expanded in one pass to the role's effective effort, the run's fixed base commit and the reviewed candidate's commit. An unknown placeholder, an unclosed or unmatched brace, a blank command and an `{effort}` the role cannot resolve are refused at trigger, and again in setup, before any worktree or LLM call. The expanded command is the reviewer's single input for that call.
- **Context in the prompt or in `CLAUDE.local.md`.** With `context: prompt` the review context and the output contract follow the command in the input. In command mode that input reaches the parent session alone, and the call's working directory holds no code, so the factory still writes a short `CLAUDE.local.md` there that names the candidate worktree, the diff, the changed-file list and the base and head trees, and tells every session, subagents included, to read the code there by absolute path. With `local-instructions` they are written to `CLAUDE.local.md` in the review call's own working directory (below), where the parent and every subagent load them as local instructions, and the input is the command alone. The instructions hold the lens's checks, the trusted context, the hash-fenced `TASK`/`SPEC`/`DISPOSITIONS`/`FINDINGS` blocks, the locations of the candidate worktree, the diff, the changed-file list and the base and head snapshots, the dispositions rule, the repair-run rule and the chosen output contract. Nothing is ever written into the candidate's worktree, so a `CLAUDE.local.md` the repository has there is never read, changed or removed.
- **Each command-mode call has a working directory of its own, configured from the base.** When a lens uses a command or local instructions, the factory makes, for each review call, a fresh directory under the run's state, `runs/<runId>/review-snapshots/<candidateId>/<lens>/cwd`. It holds the base commit's `CLAUDE.md` and `.claude/`, copied from the base tree when they exist, and the factory's `CLAUDE.local.md`: the full review instructions for `local-instructions`, the candidate's locations for `prompt`. A link in the copied configuration is followed only when its resolved target stays inside the base tree, since `CLAUDE.md` is often a link to another file of the repository; a link that leaves the base tree, to a host file or directory, is left out, as is one that leads nowhere and a linked directory already being copied on the same path. The guard would refuse the original path of an outside link, but a copy would carry its content into the working directory, where the guard allows every read. The call runs with this directory as its `cwd`. The base is code the user already merged; the candidate's `CLAUDE.md` and `.claude/` are never loaded. Because each lens has its own directory, the two reviewers never read each other's instructions and still run side by side.
- **The candidate is data only.** The candidate worktree, the directory of its diff and changed-file list and the two trees are readable through the tool list and the guard, and are not passed as `additionalDirectories`: Claude Code loads the skills, commands and agent definitions under `.claude/` of every additional directory, and `CLAUDE.md` there too when `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` is set. Claude Code also loads `CLAUDE.md` from the directories above `cwd`; those are the state root's, which hold nothing of the candidate's.
- **Materials outside the worktree, removed by the worker.** When a lens uses a command or local instructions, the review of a candidate materializes the base and candidate commits' trees under `runs/<runId>/review-snapshots/`: the base once per run (`base/`), reused by every candidate, and the candidate's own (`<candidateId>/head/`) right before its first reviewer is called. Each commit is read into a temporary index of its own and written out with `git checkout-index`, so `export-ignore` and `export-subst` in the repository's `.gitattributes` do not change the tree the reviewer is told is the whole repository; checkout filters and line-ending rules apply as they do in the worktree. No archive file is written; the tree is written into a `.partial` directory and renamed into place whole. A retry first discards what an interrupted attempt left: the partial tree, the temporary index and the index's lock file, which a killed `git read-tree` can leave and which would fail every later attempt. Both git processes are registered like every other child, so a cancel, a lost lease or the worker's shutdown kills them. Only the worker removes the materials: the candidate's tree and the reviewers' directories when its review round ends, however it ends, a replay that only reads the recorded reviews included, since every earlier stage handler runs again on replay; everything before `approve`, `finish` and `stop`, the stages after which no review can follow (`reviewCanFollow` in the policy), so nothing waits with the run through the approval wait; everything, awaited inside the job, when the run fails or is cancelled, before the failure is recorded; everything when the run finishes and when setup runs again; and, at worker startup, the materials of every run that has already ended or no longer exists. The startup sweep reads runs under the Durably instance's own state root, so it cannot judge one database's runs against another root's files, and looks a run up only when its directory still has review materials. A lost lease leaves them, since the run may be picked up again and read them. A cancel from another process reaches the worker only as a lost lease, so `demo cancel` also removes the directory, best effort; an extraction the worker had under way at that moment can still leave a tree, which the next worker start removes. The trees and directories never enter the candidate's diff, an iteration commit or the squashed branch.
- **Claude command mode.** A Claude reviewer with a command or local instructions runs with `cwd` set to its own working directory, `tools` and `allowedTools` set to `Read`, `Grep`, `Glob` and `Agent`, `permissionMode: 'dontAsk'` and `settingSources: ['project', 'local']`, so the configuration it loads is the base commit's `CLAUDE.md` and `.claude/` (settings, commands, skills and agent definitions) and the factory's `CLAUDE.local.md`, and nothing else. `canUseTool` and the `PreToolUse` hook share one check that allows only those four tools and only paths inside the working directory, the candidate worktree, the diff's directory and the two trees; hooks also run for subagents, so the same rule binds them. The check resolves symbolic links on both the path and the roots (the longest existing prefix, for a path not there yet) before comparing, so a link in the candidate or a tree that points out is refused; a path starting with `~` is refused outright; a `Glob` pattern's fixed prefix is resolved from its `path` like any other path. An `Agent` call that sets `isolation` (`worktree` or `remote`) is refused; a plain `Agent` passes. An `Agent` call whose `mode` is `acceptEdits`, `auto` or `bypassPermissions` is also refused, as defence in depth rather than the boundary: a plain subagent keeps the parent's permission mode unless its agent definition's `permissionMode` says otherwise, definitions are loaded only from the base, the review has no tool that starts agent-team teammates (for which `mode` is used), and the guard still sees every call a subagent makes. The refusal costs nothing and keeps a later SDK that honours `mode` from widening a review. The call sets `persistSession: false`: a review is never resumed, and each call has a working directory of its own, so a saved session would leave one more project under `~/.claude/projects/` per call. Recursive `Grep` and `Glob` rely on the tools not following links while they walk, which is how ripgrep behaves by default.
- **What command mode turns off.** The flag-settings layer (`settings`, which outranks project and local settings) sets `disableAllHooks: true`, which turns off every hook and status line defined in settings files and plugins, and `disableSkillShellExecution: true`, which replaces inline shell commands in commands and skills with a placeholder; `strictMcpConfig: true` with `mcpServers: {}` starts no MCP server from `.mcp.json`, settings, plugins or agent frontmatter. The base is trusted, but a review still runs nothing it did not ask for. The guard is not affected: it is an SDK callback hook passed in `hooks`, not a settings hook. Settings of the base that are not turned off, such as `env` or helper scripts for credentials, apply as they would to anyone working on the base.
- **Only command mode changes a Claude call's settings.** Every other Claude call keeps its settings, with one exception: a configured review that is not in command mode (only `output: findings-json`, for example) is shown `Read` alone (`tools: ['Read']`), so it is not offered a tool the guard would refuse. Codex reviewers refuse `command` and `local-instructions` at trigger — the CLI refuses them from `factory.json`, and the job's input schema refuses them from a direct `trigger`, so the run is never stored; the fake provider accepts them so tests can exercise the engine.
- **`findings-json` is a provider-independent contract.** The reply's last line must be exactly `REVIEW_STATUS: COMPLETE` — one conventional trailing newline (`\n` or `\r\n`) is allowed after it, but any other trailing whitespace on that line makes the review incomplete — with no other `REVIEW_STATUS:` line. The last ` ```json ` block is read from its opening fence to the first closing fence at which the text parses as a JSON array, so a fence inside a finding does not cut it short, and an earlier block is never read instead. Each finding needs `severity` `blocker` or `non-blocker` and a non-empty `title` and `body`; `file` and `line` are optional, but when a key is present `file` must be non-empty text and `line` a positive integer (a file-level finding leaves `line` out rather than writing `0`) — `null` counts as present-with-the-wrong-type, not absent, so it makes the review incomplete; other keys are ignored. One blocker makes the review `needsChanges`, with the blockers as the notes (`- [file:line] title — body`, one per line) that reach the repair; every line break in `title`, `body` and `file` (line feed, carriage return, vertical tab, form feed, next line U+0085, and the Unicode line and paragraph separators), with the spaces around it, becomes a single space, so a finding never spans lines. An empty array or non-blockers alone pass. The notes are bounded: each line is cut at 1,000 characters and only the first 20 blockers are listed, followed by a count of the rest, about 20 × 1,000 characters at most, so a reviewer cannot grow the repair prompt and the stored events without limit while every listed blocker keeps its place, title and the start of its body.
- **Interpretation after the checkpoint.** Every call still goes through the started and completed checkpoints. The reply is read after the completed checkpoint, so a missing status line, broken JSON, a malformed finding, a truncated reply or a Claude permission denial stops the review as `review-incomplete` and is never resent. Explicit provider refusals and uncertain failures keep their existing classification. (A permission denial alone no longer stops it, by the 2026-10-02 amendment below.)
- **Usage from `modelUsage`, in command mode only.** A command-mode review's usage is the final result's `modelUsage`, which covers the main loop and every subagent, summed across models once and never added to the main-loop numbers it already contains. A leg some model does not report stays unknown. Every other Claude call, default reviews included, keeps the main loop's usage exactly as before, so runs that configure no reviewer are measured as they were under the same `configVersion`.
- **Each model priced at its own rate.** The command-mode usage is also recorded per model (`usageByModel`). Its cost is each model's tokens priced at that model's rate through the existing pricing table, summed per meter; if any model is unpriced, or its usage cannot be priced, the cost stays unknown instead of borrowing the main model's rate. Per-role totals use the existing measurement path.

## Consequences

- A repository can run its own review procedure as one reviewer and have its findings drive the factory's repair loop, while the other reviewer keeps the factory prompt.
- A Claude command-mode reviewer runs with the base commit's `CLAUDE.md` and `.claude/`: a candidate cannot change what the reviewer is told or which commands, skills and agents it has. A change to that configuration takes effect for reviews once it is merged. A file `CLAUDE.md` imports with `@` is not in the working directory and is not read. A review command that relies on inline shell (`!` commands) gets a placeholder instead of the output.
- The candidate is read through the tool list and the guard rather than as an additional directory, which relies on the guard's allow and the pre-approved tools reaching paths outside the working directories.
- Local-instructions reviews run side by side, as default reviews do.
- The issue's completion criteria were amended when this design replaced the one that wrote into the worktree (see the next section).
- Such runs take extra disk for the base tree and one candidate tree while a candidate is being reviewed; nothing is kept after the round, during the approval wait or after the run, except a tree a cross-process cancel raced, until the next worker start.
- A permission denial in a command-mode review stopped the run even if the reply looked complete, so a procedure that needs Bash could not run as a reviewer. Since the 2026-10-02 amendment below, a readable reply is used and the denial is recorded; a procedure that needs Bash still gets no Bash.
- Runs without the new fields keep their `configVersion`, prompts, verdict parsing and parallel reviews.

## Amended completion criteria

Two of issue #248's approved criteria were written for the earlier design that put `CLAUDE.local.md` in the candidate worktree. With a working directory per call, they no longer describe a guarantee, and were replaced.

- **An existing `CLAUDE.local.md` in the worktree is no longer refused.** The old criterion asked `local-instructions` to refuse a worktree that already had one, because the factory would have had to write its own file in the same place. Nothing is written into the worktree now, and the file there is not a settings source of the review: the review's `cwd` is its own directory. The repository's file is therefore never read, changed or removed, which is what the refusal protected, and refusing would only stop reviews of repositories that keep local instructions. New criterion: `local-instructions` writes nothing into the candidate's worktree and neither reads, changes nor removes a `CLAUDE.local.md` already there; the worker removes the working directories and snapshots it makes after success, failure, cancel and resume.
- **The two reviewers run in parallel, not one after the other.** The old criterion serialized the two calls because both would have read the one `CLAUDE.local.md` in the shared worktree, and taking turns was the only way each saw only its own role's instructions. Each call now has its own directory and its own file, so the isolation holds without taking turns, and serializing would only double the review's wall-clock time. New criterion: each reviewer reads only its own instructions, in a working directory of its own, and the two run in parallel with `local-instructions` too. The end-to-end test checks both: each call sees only its role's instructions from start to answer, and the calls overlap.

## Amendment (2026-10-02): a refused tool call is recorded, not fatal

A Claude command-mode reviewer asked for a `Glob` outside its allowed directories. The guard refused it, as it should, and the reviewer still returned a complete, readable reply. Because the provider reported a permission denial, `readReviewReply` stopped the review as `review-incomplete` and failed the run. That happened in two real runs, each after its last candidate had been sealed and had passed the pinned check, so the completed, check-passing work was thrown away and the only way on was to pay for it again.

### Decision

- **The guard is the boundary.** It refuses every path outside the review's own working directory, the candidate worktree, the directory of its diff and changed-file list, and the base and head trees. A refusal therefore never hides any part of the candidate: what the reviewer could not read is not part of what it was asked to judge. The guard's roots and tool decisions are unchanged.
- **A denial alone does not make a review incomplete.** The reply is read as before. When it parses as a verdict or a `findings-json` reply, its result is used, whether or not the provider reported denials. A missing status line, broken JSON, a malformed finding and a truncated reply still stop the review as `review-incomplete`, with or without denials. This applies to every configured review, the command-mode ones and a `findings-json` review without a command alike, and to repository and spec reviews. Spec author and fixer calls are unchanged.
- **The denials are recorded.** Each denial is kept as its tool name and the guard's reason. A denial by the `PreToolUse` hook reaches the provider's result without a reason, so the Claude provider keeps the reason the guard gave for that tool call and uses it. A refused `Glob` names its pattern and its `path` argument, so the record shows which root the guard judged. The record is bounded: the total count and the first 10 entries, each cut to 300 characters. The same record is kept in the review step's result, in the call attempt's measurement (written from the call's result, so a call read back from its completed checkpoint records the same denials), and in the report: a `permissionDenials` field on each affected review in the JSON report, and one line under the review in the Markdown report. A review with no denial has no field.

### Consequences

- A review that strays outside its directories no longer costs the run. The owner sees that it strayed, and what it asked for, in the report.
- A reviewer that needed a refused read to reach its verdict gives that verdict without it. The read was outside the candidate, so the verdict still covers everything the review was asked to judge.

## Rejected Alternatives

### Build a specific review command into the engine

Rejected. It would tie the example to one repository's procedure and one tool, and every other procedure would need engine changes. The engine only expands three placeholders and passes the result on.

### Put the review context in a subagent prompt or a settings file

Rejected. The parent prompt does not reach subagents started by a slash command, and a generated settings file would change more than instructions. `CLAUDE.local.md` is what Claude Code loads for every agent in the working directory.

### Write `CLAUDE.local.md` into the candidate worktree and load the candidate's settings

Rejected after two review rounds. Writing into the worktree needed an ownership marker to tell the factory's file from the user's, and still left windows: a kill between creating the file and writing its marker left a file no run could claim, a file that carried a marker could be removed although the user wrote it, and the two reviewers had to take turns so neither read the other's file. Loading the project's settings from the worktree meant loading what the implementer wrote: every setting that can run a program (`apiKeyHelper` and the other credential helpers, `env`, agent frontmatter's `permissionMode`, and whatever Claude Code adds next) would have to be turned off one by one. A working directory per call, configured from the base, removes both classes of problem at once.

### Pass the candidate and the trees as additional directories

Rejected. Claude Code loads the skills, commands and agent definitions of every additional directory, which would bring the candidate's configuration back in by another door.

### Run local-instructions reviews in separate worktrees

Rejected. A second worktree would need its own dependency install and would not be the sealed candidate the other stages address. The reviewer reads the one worktree, and only its working directory is its own.

### Read the first JSON block, or retry when the reply cannot be read

Rejected. The first block is often a draft or an example, and a retry would resend a call that may already have been paid for and acted on. The last block, read strictly, with the call never resent, keeps an unfinished review from passing.

### Add each model's usage to the main loop's usage

Rejected. `modelUsage` already contains the main loop, so adding it would count the parent call twice.

### Price a call's tokens at the main model's rate

Rejected. A subagent often runs on another model, and its tokens would be priced wrongly. Each model is priced at its own rate, and an unpriced model leaves the cost unknown.
