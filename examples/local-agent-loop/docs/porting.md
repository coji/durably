# このファクトリーを別のリポジトリへ移す

読み手はAIエージェントを想定しています。人間が読んでも同じ手順です。

## 何をコピーして何を書くか

コードは三層に分かれています。移植で書くのは一番下だけです。

| 層             | 扱い                                       |
| -------------- | ------------------------------------------ |
| `src/engine/`  | そのままコピーする。リポジトリに依存しない |
| `src/factory/` | そのままコピーする。工程のつなぎ方         |
| `src/targets/` | ここだけ書く。何に対して働くか             |

`engine/` を書き換えないでください。ここには、レビューを一度通して初めて出てきた
種類のバグの修正が入っています。未処理のpromise rejection、遅れて届いた使用量
snapshotによる最終計測の巻き戻し、孫プロセスの取り残し、chunk境界でのUTF-8破損、
送信済みか不明な呼び出しの再送判定。コピー先ごとに触ると、それぞれが別々に劣化
します。直すべき点を見つけたら、コピー元に直して配り直してください。

## 最短の移植手順

1. `src/engine/` と `src/factory/` を丸ごとコピーする。
2. `src/targets/repo.ts` と `src/targets/index.ts` をコピーする。多くの場合、
   実リポジトリ向けの `RepoTarget` はそのまま使えます。
3. `src/durably.ts` と `src/cli.ts` を、そのプロジェクトのDB配置と起動方法に
   合わせて書き換える。
4. 採点コマンドを決める。これが一番重要な判断です（下記）。
5. fake providerで一周させて配線を確かめる。実LLMはそのあと。

`RepoTarget` で足りる限り、新しい `Target` を書く必要はありません。

## 新しい Target を書く場合

`src/factory/target.ts` の `Target` を実装します。必要なのは5つの決定だけです。

- **どこで作業するか** (`workdir`)。編集可能な場所。実リポジトリなら
  `git worktree`。あなたが開いているcheckoutを直接使ってはいけません。
  中断したrunが作業途中のcheckoutを残します。
- **どう封印するか** (`seal` / `assertIntact`)。検証・レビュー・成果物が同じ
  バイト列を見ることを保証する仕組みです。gitならcommitのtree sha、
  ディレクトリならcontent hash。`assertIntact` は工程の前後で呼ばれます。
- **何をもって合格とするか** (`grade`)。下記。
- **レビュアーに何を渡すか** (`reviewContext` / `reviewCwd`)。レビュアーは
  独立した新規sessionで、候補しか見ません。ベースからの変更一覧と元の内容を
  こちらから渡さないと、「変更が最小か」を判断できません。
- **人間が何を受け取るか** (`deliver`)。patch、Draft PR、ディレクトリなど。
  外向きの操作を含むので、`stages.ts` はこれを独立したstepで呼びます。replayで
  二度publishしません。

`TargetConfig` はJSONとして永続化されます。クラスインスタンスや関数を入れては
いけません。workerがrunを拾い直すとき、手元にあるのはDBとディスクだけです。

## 採点コマンドの決め方

ここが移植で唯一むずかしい判断です。

**エージェントが走り出す前に固定してください。** 固定していないと、エージェントが
テストスクリプトを書き換えて通すことができます。このサンプルは `checkCommand` を
setup時に記録し、shellを介さずargvとして実行します。

**同梱題材の「テストは不変」という前提は、実リポジトリでは成り立ちません。**
機能追加のissueではエージェントがテストを書きます。代わりに次の二段で守ります。

1. コマンド自体を固定する。エージェントが何を書き換えても、走るものは変わらない。
2. レビュー工程で、テストが空虚でないかを見る。「修正がなくても通るテスト」は
   合格にしない、とpromptで明示する。

コマンドは速すぎても遅すぎてもいけません。反復ごとに走るので、数分を超えると
ループが回らなくなります。単体テストとlintとtypecheckまでが現実的で、e2eや
デプロイ検証は向きません。

## 動かす前に確かめること

- fake providerで一周する。`--provider fake` で実LLMを呼ばずに配線を検証できます。
- worktreeが期待した場所にでき、元のcheckoutが動いていないこと。
- 検証が失敗したときに、失敗理由が修正promptに渡っていること。
- `demo report --run <id>` が工程別の時間とtokenを出すこと。

## やらないこと

- `engine/` をプロジェクトごとに書き換える。
- 採点コマンドをエージェントに選ばせる。
- 最初から `--publish` を付ける。まずpatchで確かめてください。
- 承認待ちを消す判断を、成果物がレビュー可能かどうかを見ずに決める。Draft PRなら
  人間はそこで見られますが、patchを黙って置くだけなら誰も見ません。
