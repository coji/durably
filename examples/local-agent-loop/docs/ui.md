# ブラウザで見る（web UI）

[README](../README.md) に戻る。

ワーカーを動かしたまま、別のターミナルで web UI を起動できます。一覧と詳細を
見るほか、承認、却下、仕様の判断、再実行、アーカイブを画面から行えます。

```bash
pnpm --filter example-local-agent-loop demo ui             # http://127.0.0.1:4380/
pnpm --filter example-local-agent-loop demo ui --port 4500
```

- 表示された URL をブラウザで開きます。待ち受けるのは `127.0.0.1` だけで、外には
  公開しません。`--port` は 1〜65535 の整数だけを受け付けます。
- 前もってビルドする必要はありません。画面は、要求されたときに Vite が変換して
  配信します。`pnpm --filter example-local-agent-loop build:ui` は、静的なファイルを
  ビルドできるかを確かめるためのものです。
- UI は、固定した状態のルートの DB を、CLI と同じ接続で開きます。DB がまだなければ
  空の画面を出し、DB は作りません。ワーカーか `trigger` が DB を作ると、次の更新
  から表示されます。画面を読むだけでは、何も書き込みません。
- UI はワーカーを起動せず、ワーカーのロックも取りません。承認や再実行のあとで
  実行を進めるのは、別に動かしているワーカーです。
- 画面は 3 秒ごとに読み直します。前の読み込みが終わるまで、次は始めません。
  読み込みに失敗したときは直前の表示を残し、上部に「更新失敗」と表示します。
- 画面の操作は、CLI の `approve`、`reject`、`spec-revise`、`retrigger`
  （`--reload-config` なし）、`archive`、`unarchive` と同じ関数（`src/actions.ts`）を
  呼びます。確かめる内容も結果も CLI と同じです。承認と却下は、実行がいま待っている
  待ちにだけ、候補か仕様の版に結びつけて送ります。別の実行の待ち、判断済みの
  待ち、種類の違う待ちには送りません。再実行は保存済みの入力だけを使い、CLI が
  再実行を断る停止には、画面からも実行しません。`factory.json` の読み直しは、CLI だけの
  操作です。
- どの操作にも、同じ操作の CLI コマンドを添えます。操作ボタンの下の、閉じた
  「同じ操作の CLI コマンド」を開くと、レポートや状態の確認を含む次のコマンドの
  「〜をコピー」ボタンと全文が出ます。却下とアーカイブは控えめなボタンで、押すと
  確認を挟みます。再実行も費用のかかる新しい実行を始めるので、保存済みの入力で
  新しい実行を始めると伝える確認を挟みます。承認も確認を挟み、その確認には、レビューの
  回数、最後の回の結果、直した指摘と残した指摘の件数と題名を出します。確認の中には、
  その操作のコマンドを 1 行とコピーボタンで出し、確認のあいだは同じ行のほかの操作を
  隠します。仕様の修正では、画面に書いたメモをそのまま送ります。CLI では、同じメモを
  書いたファイルを `--notes-file` に渡します。
- 操作の結果は画面の上部に知らせとして出し、一覧は次の更新で変わります。断られたときは、
  CLI と同じ英語のメッセージを知らせに出します。
- 書き込みの API は `POST /api/runs/<id>/<action>` だけです。サーバーは起動の
  たびにランダムなトークンを作ってページに埋め込み、書き込みには
  `x-loop-ui-token` ヘッダーのトークンと、このサーバー自身を指す `Origin`
  ヘッダーを求めます。Host、トークン、Origin のどれかが違えば 403、POST 以外は
  405 で、操作の関数を呼ぶ前に断ります。実行の ID の書き方が壊れたパスは 400 です。
  トークンはログに出さず、cookie も使いません。ページは CORS を許さないので、
  localhost のほかのポートのページからもトークンは読めません。読み取りの API は GET と HEAD だけです。
- ログの読み取りは `GET /api/runs/<id>/logs/<attemptId>?from=<バイト位置>` です。
  既定はその試行のエージェントの出力で、`&file=stdout` と `&file=stderr` で、検証の
  標準出力と標準エラー出力を読みます。応答は `{ chunk, nextOffset, done }` で、1 回に
  読むのは 64 KiB までです。`from` は省略すると 0 で、0 以上の整数だけを受け付け、
  ほかの値は 400 です。UTF-8 の文字の途中で切れた末尾は返さず、次の読み取りに
  回します。`nextOffset` は、返したバイト数だけ進みます。`done` は、試行が終わって
  ファイルの最後まで読んだときに `true` になります。試行は実行の ID と合わせて DB で
  探し、ファイルの場所は試行が記録したパスだけを使います。リクエストでパスは
  指定できません。知らない試行や、そのログを記録していない試行は 404、記録した
  パスが実行のディレクトリの外にあるか、リンクをたどると外に出るときは 403、
  記録したファイルが消えているときは 410 です。ほかの読み取りと同じ Host の制限が
  かかり、トークンは要りません。
- 操作のない行では、次のコマンドを「〜をコピー」ボタンで出し、全文は
  「コマンド全文」を開くと見られます。表示にもコピーにも、
  CLI が付ける英語の `# ...` の補足は含めません。補足は、ボタンにマウスを重ねると
  日本語で出ます。
- `http://127.0.0.1:4380/#/design` は、画面の部品と状態を、固定の見本データで並べた
  ページです。DB も API も使わないので、ワーカーや DB がなくても開けます。

実行は、保存済みの入力から付けた名前で並びます。イシューから作った実行は
`#番号 タイトル`、`--task` / `--task-file` の実行はタスクの最初の行（80 文字まで）、
同梱の題材は「同梱題材: calc の add を直す」です。一覧には実行の ID を出さず、
完全な ID は実行の詳細と、コピーしたコマンドにあります。作成時刻は「3分前」のような
相対的な表し方で、正確な時刻はマウスを重ねると出ます。

各行と実行の詳細には、その実行のリポジトリ名を、名前の横に出します。名前は
`factory.json` の `name`（`trigger` のときに入力の `target.name` に保存したもの）です。
同じリポジトリの実行のうち、名前を持ついちばん新しい実行のものを使うので、`name` を
書く前の実行も同じ名前で出ます。どの実行にもなければ、保存済みの入力の
`target.repoPath` のディレクトリ名です。同じ名前のリポジトリがほかにあるときや、
「すべて」「同梱題材」「不明」と同じ名前のときだけ、見分けられるところまで親の
ディレクトリを前に付けます（`a/public` と `b/public` など）。それでも見分けられない
ときは、パスで出します。修正の実行は、修正元の最初の実行のリポジトリに
数えます。同梱の題材の実行は「同梱題材」です。完全なパスは、実行の詳細と、切り替えの
リポジトリ名にマウスを重ねると出ます。

実行のリポジトリが 2 つ以上あるときは、タスク一覧と集計の上に「リポジトリ」の
切り替えが出ます。既定は「すべて」です。リポジトリを選ぶと、一覧の各節、件数の
並び、止まったものの「すべて選ぶ」、集計（週ごとの推移と設定ごとの比較）が、
そのリポジトリのタスクと実行だけになります。選んだリポジトリは
`#/?repo=<パス>`、`#/compare?repo=<パス>` のように URL に残るので、読み込み直しても
変わりません。一覧と集計のあいだを移っても、実行の詳細（その URL にも残ります）から
一覧へ戻っても、選んだままです。
API も同じで、`/api/runs`、`/api/trend`、`/api/compare` に `?repo=<パス>` を付けると、
そのリポジトリだけを返します。どの実行にもないパスは「すべて」として扱います（画面の
URL からも外します）。リポジトリは、保存された `--repo` のパスを git のトップレベルに
直して見分けるので、末尾の `/` や、リポジトリの中のディレクトリを渡した実行も、同じ
リポジトリに数えます。git が答えられないとき（リポジトリが消えたときなど）は、パスを
そのまま正規化して使い、ほかの実行のリポジトリのパスの下にあれば、いちばん近い
そのリポジトリに数えます。git には画面の応答を止めない形で問い合わせ、答えたパスは
覚えておきます。答えられなかったパスは、1 分たってから問い合わせ直します。
リポジトリが 1 つだけのときは、切り替えを出しません。

**タスク一覧**はタスクごとに 1 行で、先頭の件数の並びと 4 つの節に分かれます。並びと
区分は、`demo status` と同じ関数（`groupTasks`）で決めます。行の末尾には、実行が
2 件以上あるときの件数、所要時間、費用、代表の実行の作成時刻を、列をそろえて
出します。所要時間と費用は、終わったタスクか、実行が 2 件以上あるタスクだけに出し、
2 件以上なら全部の実行の合計です（マウスを重ねると、合計であることが出ます）。どれかの実行の
値が不明なら「不明」です（`demo status` の `total` と同じ値）。

- **件数の並び**：「判断待ち」「動いているもの」「止まったもの」「終わった」の件数です。
  押すと、その節へ移ります。0 件には色を付けません。「動いているもの」は、実行中の
  ものがあるときだけ青にします。判断待ちも止まったものもなければ、「人の手が要る
  ものはありません」と出します。
- **判断待ち**：承認、仕様の判断、承認以外の入力を待つタスク。行は開いた状態で、
  理由、工程の並び、その実行にできる操作と、同じ操作の CLI コマンドを出します。
  コマンドの補足は、ボタンにマウスを重ねると出ます。
- **動いているもの**：実行中（期限内のリース）、ワーカー停止中（リースが切れて
  ワーカーが止まった。ワーカーを起動すれば再開）、順番待ち、判断済み・再開待ちのタスク。
  行は開いた状態で、実行中なら、名前の下にいまの工程と経過時間を出します。
- **止まったもの**：未解決の停止（検証の失敗、レビューの上限、未確定の外部の呼び出しなど）の
  タスク。新しいものから 5 件だけを出し、残りは「さらに N 件表示」で出します。節の件数は、すべてを数えます。
  各行のチェックボックスか、節の「すべて選ぶ」でタスクを選ぶと、画面の下に操作バーが出ます。
  「すべて選ぶ」は、まだ表示していない行も含めて、節の全件を選びます。「N 件をアーカイブ」は、
  選んだタスクの名前と `demo archive --series <id> --series <id> …` を並べて確認してから、
  タスクごとに `archive --series` と同じ関数で、1 件ずつ順に、止まった実行をアーカイブします。
  進むあいだは、知らせに「N 件中 M 件」を出し、1 件終わるごとに更新します。まとめての操作は
  それぞれ自分の知らせを持ち、途中で別の操作をしても、その知らせは上書きされません。終わると、件数と、
  作業ツリーやブランチを片付けられなかったタスクと git の理由、できなかったタスクとその理由を
  知らせ、「まとめて戻す」で、いまアーカイブした実行を戻せます。一部の実行だけをアーカイブできた
  タスクも、アーカイブした実行は戻せ、警告も出します。行は閉じた状態で、状態のバッジと名前だけを 1 行で出します。開くと、止まった
  理由、工程の並び、再実行できるか、操作とコマンド、各実行が出ます。同じタスクに、
  動いている実行か、判断を待つ実行がほかにあるとき（再実行した修正など）は、行を
  開いた状態で出し、各実行の状態が開かなくても見えるようにします。前に止まった実行が
  残っているだけでは開きません。表示のあとでそうなったときも、3 秒ごとの読み直しで
  開き、そうした実行がなくなれば、また閉じます。自分で開け閉めした行は、タスクが同じ節にあるあいだは、その状態を保ちます。別の
  節へ移ったとき、実行の詳細を開いてから一覧へ戻ったとき、ページを読み込み直した
  ときは、その節の既定の状態に戻ります。後の修正の実行の承認で解決した停止と、アーカイブした停止は
  出ません。
- **終わったタスク**：新しい順に 30 件ずつ出し、「さらに表示」で次を出します。
  アーカイブしたタスクは既定で隠し、「アーカイブ済みも表示」で出します。タスク名で
  絞り込めます。どちらも表示だけの切り替えで、タスクや数値は変えません。節の件数は
  全件で、隠したり絞り込んだりしているときは、「144 件中 104 件」のように添えます。
  行の名前は代表の実行の詳細へのリンクで、左の矢印で開くと、工程の並びと、実行が
  複数あるタスクでは、「最初の実行」「指摘からの修正 1」…のように各実行と、その
  所要時間と費用を出します。後の修正で解決した実行には「後の修正で解決」と添えます。
  アーカイブしたタスクには「アーカイブ済み」と添え、状態は色を付けずに出します。
  開くと、止まった理由と「アーカイブから戻す」が出ます。最初の実行が fake プロバイダーで
  動いたタスクも、隠さずに並べ、「模擬」と添えます。修正の実行が実際のプロバイダーでも、
  最初の実行で決まります（`demo status --format json` のタスクの `fake`）。

状態は、1 つの実行につき 1 つだけ出します。動いている実行はいまの状態（承認待ち、
実行中など）、終わった実行は結果（承認済み、検証失敗など）です。
状態の名前は必ず文字で出し、色は「人待ち（琥珀）」「失敗（赤）」「実行中（青）」だけに
付けます。状態の区分と次のコマンドは、`demo status` と同じ関数（`src/engine/status.ts`）から
作るので、同じ時点の `demo status --run <id>` と一致します。説明文は、区分と停止の種類から
画面用の日本語で出し、CLI の英語の理由（reason）は表示しません。未確定の外部の呼び出しで
止まった実行には、再実行を促すコマンドを出しません。プロバイダーに呼び出しを
断られて止まった実行には、拒否の理由を停止の理由の欄に出し、設定を読み直す再実行と、
通常の再実行のコマンドを、コピーできる形で出します。工程の並びでは、通った工程に ✓ を
付けます。承認待ちを作らずに完了まで進んだ実行（`--approve auto`）の承認は、
「✓ 承認 自動」と出します。

実行中の実行の「全体 … 経過」は実行の開始（リースを取ったとき、まだなら作ったとき）から、
「この工程 … 経過」はいまの工程の試行の開始から、画面を読んだ時点までの暫定の値です。
レポートの確定した値（所要時間、工程ごとの時間）とは別に扱い、確定した値には混ぜません。

**実行の詳細**は、`demo report --run <id> --format json` と同じ値を、上から読んで
途中でやめても要点が分かる順に並べます。

名前の下には、同じタスクの実行を「最初の実行」「指摘からの修正 N」として、
状態と開始時刻と一緒に並べ、表示している実行に「表示中」と添えます。

1. **いまの状況**：停止や判断待ちの理由、人が確かめること、再実行できるか、
   その実行にできる操作と、同じ操作の CLI コマンド。主な操作（承認、仕様を直す、
   再実行）だけを強いボタンで出します。人が確かめることとしてログファイルを読むよう求める停止では、その
   すぐ下に、チェックのログのパスをコピーできる形で出します。ファイルがなければ
   「ファイルがありません」、記録にパスがなければ、そう書きます。承認・納品済みの
   実行では、納品したブランチをコピーできる形で出します。
   その下に、所要時間、工程の作業時間、人の待ち時間、費用、合計のトークン、
   修正とレビューの回数を 1 行で並べ、作業時間が所要時間より長いときは、理由を
   1 行添えます。停止の記録（終了コードなど）は、「停止の記録を見る」を開くと出ます。
2. **レビューの要点**：レポートの `reviewHighlights` です。最後より前のレビューで
   出た、直すべき指摘を、最後のレビューが通過したときは「直した指摘」、そうでなければ
   「これまでの指摘」として、最後のレビューの助言を「残した指摘」として、件数と題名を
   出します。採点値のある指摘には、題名の横に頻度と深刻さを添えます。最後のレビューが通過したと言えるのは、両方のレビュアーの判定がそろい、
   どちらも通過したときだけです。通らなかった実行では、そこで出た直すべき指摘を
   「残っている直すべき指摘」として別に出し、判定がそろっていない回はそう書きます。
   指摘を、回をまたいで突き合わせることはしません。見出しの件数は、レポートと同じ指摘の
   数です。判定だけを返すレビュー（verdict）は、回、観点、判定だけを題名の下に出し
   （直した側では「〜が求めた修正」）、件数には数えません。最後のレビューで通過した
   verdict のレビューは何も残していないので、「残した指摘」ではなく、最後のレビューの結果の
   下に出します。メモの本文は、記録の詳細の節で読みます。
3. **工程の時系列**と**工程ごとの時間と費用**：工程ごとに、作業時間（呼び出しの時間の
   合計）、所要時間（時計の時間）、費用を 1 行で並べます。費用の「–」はモデルを
   呼ばなかった工程、「不明」は値の分からない呼び出しを含む工程です。終わった実行の
   時系列は全部の行を出し、動いている実行だけが枠の中でスクロールします。レビューのように並んで動いた
   工程は、作業時間を重ねて数えるので、作業時間の合計が所要時間を超えることが
   あります。仕様の工程がある実行には、「仕様の工程まとめ」として、仕様の作成、
   仕様レビュー、採点コマンドの決定を合わせた経過時間（レポートの `specWallMs`）を
   出します。並んだレビューは一度だけ数え、人の判断を待った時間は含みません。
4. **記録の詳細**（最初は閉じています）：仕様、レビューの全部の回の判定とメモ（メモは
   開くと出ます）、工程別・役割別のトークンと費用、見立てと較正の材料、候補と候補ごとの
   変更の規模、納品物、入力ファイルの SHA-256、注記。

工程の時系列で行を選ぶと、実装の行には封印した候補の規模を、レビューの行には
その回の判定とメモを、検証の行には終了コードと検証のログのパスを出します。
パスは「〜のパスをコピー」ボタンでコピーできます。

エージェントを呼んだ行を選ぶと、その呼び出しの出力を「エージェントの出力」に
出します。検証の行では、標準出力と標準エラー出力を切り替えて読めます。出すのは
その行の最後の試行のログで、やり直した工程では、試行の行を開くと、その試行の
ログを読めます。

- 書き込み中のログは 3 秒ごとに続きを読み、「書き込み中」の印を付けます。
  前の読み込みが終わるまで、次は始めません。試行が終わって最後まで読むと、
  「書き終わり」と出し、読み直しを止めます。
- 終わったログも、先頭から順に読みます。画面に残すのは末尾の 256 KiB までで、
  それより長いログは末尾だけを出します。全文は、ファイルのパスをコピーして、
  エディタや `less` で開いてください。
- 本文は文字としてそのまま出し、Markdown や HTML として解釈しません。端末の色などの
  エスケープは取り除きます。
- 本文の末尾を見ているあいだは、追記に合わせて下へ送ります。上へスクロールすると、
  その位置で止まります。
- 記録したファイルが消えていれば、そのことを出します。

承認待ちの実行では、レビューの判定とメモは承認待ちのメタデータから、候補は
保存済みの候補の `step` から読みます（レポートの `reviews` と `candidate` にも
同じ値が入ります）。

**集計**は、2 つの見方を切り替えます。開いたときは「週ごとの推移」です。ほかの画面へ
移って戻っても、ページを読み直すまでは、最後に選んだ見方のままです。

- **週ごとの推移**：`demo compare --trend --format json` と同じ値です（リポジトリで
  絞ったときは、そのリポジトリのタスクだけで数えます）。実行ではなく
  タスクを数えます。最後の実行が直近 30 日に終わったタスクを、最初の実行の実装に
  使ったモデルと推論量の組ごとにまとめます。まとまりごとに、まず期間全体の初回の承認率、
  最終の承認率、タスクあたりの所要時間と費用の中央値を出し、その横に、週（月曜始まり、
  この PC の時刻）ごとのタスク数、初回の承認、最終の承認、所要時間、費用、修正の実行の数の
  中央値を並べます。タスクが 1 件だけの週には「1 件のみ」と添えます。最初の実行が
  模擬（fake プロバイダー）のタスクは除き、期間に終わったタスクが模擬だけのときは、除いた
  件数をそう書きます。CLI の版はまとまりに含めないので、同じモデルの新しい版は同じ表に
  並びます。数え方は、CLI の節の `--trend` と同じです。
- **設定ごとの比較**：終わった実行を `demo compare --runs` と同じ処理にかけ、
  設定の版（config version）ごとのまとまりを、閉じた状態で並べます。見出しに件数と成功率が出て、
  開くと、所要時間・作業時間・費用などの中央値、最小、最大、件数、不明の数、工程別の
  値、見立ての判定別の結果と停止の理由の件数、判定別の較正の材料の中央値を
  表示します。

表示した値の読み方：

- 費用は、記録したトークン数を API の料金で換算した参考の値です。サブスクリプションの
  請求額ではありません。
- 使用量や価格が分からないものは、web UI では「不明」、CLI の Markdown（`report`、
  `compare`）では `unknown` と表示し、0 とは表示しません。一部の
  呼び出しだけ分かっている値と、一部の試行だけ計測できた工程の時間には、「一部」を
  付けます。
- 集計の統計は不明な値を除いて計算し、除いた数を「不明」の列に出します。

## デモデータ

実際の使い方に近い実行を並べて web UI を見たいときは、`demo seed` を使います。
実際の LLM は呼ばず、すべて fake プロバイダーで動きます。

```bash
pnpm --filter example-local-agent-loop demo seed
pnpm --filter example-local-agent-loop demo seed --home ~/tmp/factory-demo --latency 3000-15000
```

- 使い捨ての HOME を OS の一時ディレクトリに作り、その場所を表示します。
  `--home` には、空のディレクトリか、まだないパスを渡します。普段の
  `~/.local/state/local-agent-loop/` には触れません。
- その HOME に、小さな JS プロジェクトの git リポジトリと `factory.json` を作り、
  日本語のタスクで、リポジトリが対象の実行を 13 本起動します。承認された 1 本には、外部の
  指摘からの修正の実行を 1 本足します。固定したテストは、本物の `node --test` です。
- `factory.json` の各役割には、実際に使いそうなモデルを書いています。実装と
  正しさのレビュー（correctness）は `gpt-6-sol`、境界条件のレビュー（edge-cases）は
  `claude-opus-5-5`、見立ては `gpt-6-luna` です。プロバイダーは fake なので、
  これらは指定したモデル（requested model）として記録され、トークン数と費用は
  そのモデルの価格で計算します。実行は fake と表示され、実際の LLM での検証には
  数えません。
- 結論は一通りそろいます。修正 1 回で承認、初回で承認、レビューの上限、検証の失敗、
  未確定の呼び出し、承認待ち 2 本、却下、見立ての `routine` と `probe` です。
- `--latency` は 1 回の呼び出しにかかる時間の範囲で、既定は `20000-90000` ミリ秒
  です。`demo seed` はこれらの実行を同時に進め、承認と却下を
  `demo approve` / `demo reject` と同じ処理で送り、落ち着くまで待ちます。
- 最後の 2 本は、1 回の呼び出しに 10〜20 分かかる設定で、バックグラウンドの
  ワーカーに渡します。`demo seed` が終わった時点で、1 本は実行中、もう 1 本は
  ワーカー待ちです。ワーカーの pid とログの場所を表示します。
- 作成時刻は、実際に `demo seed` を動かした時刻です。時刻は Durably が記録し、
  `demo seed` は DB を書き換えないので、数日分の履歴には見えません。

最後に、画面を開くコマンドと、ワーカーを止めたあとで続きを動かすコマンドを
表示します。

```bash
HOME=<表示された場所> pnpm --filter example-local-agent-loop demo ui
HOME=<表示された場所> pnpm --filter example-local-agent-loop demo worker
```
