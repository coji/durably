# 日々の操作

[README](../README.md) に戻る。ワーカー、実行の状態、待ち、アーカイブ、片付け、データの置き場所をまとめます。

## ワーカーは状態のルートごとに 1 つだけ動く

ワーカーは状態のルート（state root）ごとに 1 つだけ動きます。ワーカーは起動するときに
`~/.local/state/local-agent-loop/worker.lock` を OS のファイルロック（SQLite の排他
トランザクション）で握ります。同じ状態のルートで 2 つ目を起動すると、動いている
ワーカーの pid と起動元のチェックアウトを表示し、終了コード 1 で起動を断ります。

```text
another worker already runs on ~/.local/state/local-agent-loop: pid 41234, started 2026-09-25T01:02:03.000Z from /Users/me/src/durably/examples/local-agent-loop. Stop it first (kill 41234); two workers would pick up each other's runs.
```

- ロックはプロセスと一緒に消えます。Ctrl-C、SIGTERM、初期化の失敗では自分で
  解放し、`kill -9` やクラッシュでは OS が解放します。pid を書いた
  `worker.json` が残っていても、次のワーカーはロックを取り直して上書きするので、
  古い情報だけで起動を断ることはありません。
- `demo trigger`、`demo status`、`demo wait` は、同じロックファイルをのぞいて
  ワーカーがいるかを確かめます（`wait` は 1 秒ごと。読み取りの瞬間だけ共有ロックを
  握ります）。ワーカーの起動は、この瞬間とぶつかっても最大 2 秒までやり直して
  乗り越えるので、`wait` で見ている最中にワーカーを起動しても失敗しません。1 つ目の
  ワーカーが排他ロックを握り続けているあいだは、2 つ目のワーカーはこのやり直しを
  過ぎても、これまでどおり断られます。
- ロックファイルが読めない（壊れている、権限がないなど）ときは、ワーカーがいるかを
  「不明」（`running: null`、`worker: unknown`）と表示します。`wait` は「不明」を
  「ワーカーがいない」とは数えないので、それだけで終了コード 6 にはなりません。
- 別の状態のルート（`HOME` が違う環境）のワーカーどうしは、互いを断りません。
- 時間の上限は `trigger` のときに実行の入力へ固定されるので、ワーカーの環境変数で
  既存の実行の値が変わることはありません（[「`trigger` のときに固定されるもの」](configuration.md)）。

## ワーカーの自動起動とアイドル終了

ターミナル 1 でワーカーを動かし続けなくても、実行を進めるコマンドが、必要なときに
ワーカーを起動します。

- `trigger`、`repair`、`retrigger`、`approve`、`reject`、`spec-revise` が成功した
  あと、ワーカーの仕事があれば、ワーカーのロックを調べます。ワーカーがいなければ
  `demo worker --exit-when-idle` を起動し、もういれば何もしません。ロックが読めず、
  ワーカーがいるか分からないとき（`running: null`）は起動せず、理由を標準エラー出力に
  出します。失敗したコマンドや、入力の検証で断ったコマンドは起動しません。
- ワーカーの仕事とは、`pending` と `leased` の実行（リースの期限は問いません）と、
  いま待っている待ちが判断済み（`resolved`）の `waiting` の実行です。判断済みの
  待ちを持つ実行は、`pending` に戻るのを待たずにワーカーが再開します。誰も判断して
  いない待ちだけを待つ実行は数えません。
- 起動したワーカーは、起動元とは別のセッション（別のプロセスグループ）で動き、
  コマンドの終わりを待たせません。エージェントが起動元のシェルやプロセスグループを
  片付けても、ワーカーは止まりません。
- 起動の知らせと警告は、すべて標準エラー出力に出します。標準出力には、これまでどおり
  コマンドの出力（`trigger` の JSON など）だけを出します。起動に失敗しても、
  コマンドの終了コードは変わりません（実行はもう保存されています）。起動に成功すると、
  ワーカーの pid とログの場所を 1 行出します。
- ワーカーの標準出力と標準エラー出力は、状態のルートの
  `~/.local/state/local-agent-loop/logs/worker-YYYY-MM-DD.log`（起動した日、
  ローカル時刻）に追記します。同じ日に何度起動しても、既存のログは消しません。
- 自動起動を止めるには、各コマンドに `--no-auto-worker` を付けるか、環境変数
  `LOCAL_AGENT_LOOP_NO_AUTO_WORKER=1` を設定します。実行は、ワーカーが来るまで
  `pending` のままです。
- 自動起動したワーカーのアイドル期間は `LOCAL_AGENT_LOOP_IDLE_MS`（既定 30000）で
  変えられます。1 から 2147483647 までの整数のミリ秒だけを受け付け、範囲の外なら
  ワーカーを起動せずに警告します。
- 自動起動したワーカーは、コマンドを実行したチェックアウトの CLI で動きます（どの
  チェックアウトかは `worker.json` の `checkout` に残ります）。同じ状態のルートを
  共有していると、固定したチェックアウト（[「durably のチェックアウトを固定して呼ぶ」](configuration.md)の節）とは
  別のチェックアウトから実行したコマンドが、そのチェックアウトのワーカーを起動する
  ことがあります。固定したチェックアウトのワーカーで処理したいときは、その
  チェックアウトでワーカーを動かしておくか、自動起動を止めてください。

`demo worker --exit-when-idle [--idle-ms <ms>]` は、仕事がない状態が `--idle-ms`
（既定 30000、1 から 2147483647 までの整数）続くと終わります。オプションなしの
`demo worker` は、これまでどおり動き続けます。

- 仕事があるかは 500 ミリ秒ごと（`--idle-ms` がそれより短ければその間隔）に確かめ、
  前の確認が終わってから次を始めます。DB（データベース）を読めなかった確認は
  アイドルと数えず、エラーを標準エラー出力に出して、アイドル期間を数え直します。
- アイドル期間が過ぎたら、ポーリングを止めてからもう一度確かめます。そこで仕事が
  見つかれば、ポーリングを再開して処理します。
- この最後の確認からロックを手放すまでのあいだに実行が作られると、起動元のコマンドは
  まだワーカーがいると見て、新しく起動しません。そのため、アイドルで終わるワーカーは
  ロックを手放したあとにもう一度仕事を確かめます。仕事があれば、自動起動と同じ方法で
  次のワーカーを起動し、ログに `[idle] work arrived as the worker stopped; started
a successor (pid N)` を書きます。次のワーカーも同じようにアイドルで終わるので、
  ワーカーがロックを握っているあいだに作られた実行は、そのワーカーがロックを手放す
  前か後のどちらかで必ず見つかります。次のワーカーが起動しない場合（起動の失敗、
  自動起動を止めている場合）は、実行が `pending` のまま残ります。`demo wait` は
  `--worker-timeout`（既定 10 秒）でワーカーがいない状態を見つけ、終了コード 6 で
  知らせるので、そのときは `demo worker` を起動してください。
- SIGTERM、SIGINT、アイドル終了では、`[shutdown] reason=SIGTERM`、
  `[shutdown] reason=SIGINT`、`[shutdown] reason=idle` をログに書きます。その後、
  実行中のエージェントの CLI を止め、進行中のアイドルの確認を待ち、ポーリングを止めて
  ロックを手放します。アイドル終了なら、ここで上に書いた次のワーカーの確認をします。
  最後に DB を閉じ、出力を書き終えてから、終了コード 0 で終わります。終了処理の
  最中にシグナルが届いても、終了処理を重ねて走らせることはありません。

## 止まった実行と次の手順を見る

`--run` を付けない `status` は、手を打つ必要があるタスクを一覧にします。タスクは、
最初の実行と、そこから `demo repair` で始めた修正の実行（修正の修正も含む）を
まとめた単位です。タスクごとに、状態を代表する実行の理由と、次に打つコマンドを
表示し、その下にタスクの名前と、ほかの実行を `also:` として並べます。

- 先に「人の判断待ち」（承認待ち、仕様の判断待ち、承認以外の入力待ち）と
  「未解決の停止」のタスクを、次に `pending`、`leased`、判断済みで再開待ちのタスクを
  出します。それぞれ新しい順です。
- 修正の実行が止まっても、同じ修正元から後に始めた修正の実行が承認されていれば、
  その停止は解決済みとして扱い、一覧の上部には出しません（`also:` に
  `replaced by a later approved repair` と付けます）。
- 代表の実行は、判断待ちや停止があればその実行、動いている実行があればその実行、
  どれもなければ置き換えられていない最新の実行です。
- `demo archive` でアーカイブした止まった実行は、終わった実行として数えます
  （下の「止まった実行をアーカイブする」）。同じタスクのほかの実行が人の手を
  待っていれば、そのタスクは上部に残ります。アーカイブした実行は、最後に
  `stopped run(s) archived:` として、戻すコマンドと一緒に並べます。
- 止まったままアーカイブしていない実行があるタスクには、`stops:` の行で、その件数と
  `demo archive --series <最初の run の ID>` を出します。後の修正の実行が承認されて
  置き換えた停止も数え、アーカイブした停止は数えません。この行はテキストの表示だけで、
  `--format json` と web UI には出しません。
- 何もなければ `No runs need attention` と表示します。
- 実行が複数あるタスクには、`total:` の行で、全部の実行の所要時間と費用の合計を
  出します。どれかの実行の値が分からなければ `unknown` です。
- `--format json` は、同じタスクの並び（`tasks`、合計は各タスクの `total`）、
  ワーカーの状態、DB の場所を JSON で出します。web UI の一覧（`/api/runs` の
  `tasks`）と同じ値です。

```bash
pnpm --filter example-local-agent-loop demo status
pnpm --filter example-local-agent-loop demo status --format json
```

```text
01M375ZAYC...  waiting  (created 2026-09-23T13:06:11.530Z)
  reason:  waiting for human approval of candidate candidate-1-9958e915bf52
  next:    pnpm --filter example-local-agent-loop demo report --run 01M375ZAYC...  # read the reviews first
           pnpm --filter example-local-agent-loop demo approve --run 01M375ZAYC... --wait 01M375ZC2C...
           pnpm --filter example-local-agent-loop demo reject --run 01M375ZAYC... --wait 01M375ZC2C...
  task:    #261 Round the report's cost to cents  (first run 01M375ZAYC..., 1 run(s))
```

- 表示するコマンドは、リポジトリの中のどこからでも、そのまま貼り付けて実行できます。
  補足は `  # ...` のシェルのコメントとして後ろに付けます。
- 承認待ちで止まっている実行にだけ、その実行の ID と待ちの ID を入れた `approve` と
  `reject` を表示します。承認か却下を記録済みで、まだワーカーが取り出していない
  実行には、判断を記録済みであることと、ワーカーの起動を表示します。
- `leased` は、リースの期限内なら実行中、期限切れならワーカーが止まったものとして
  分けます。期限切れは失敗ではないので、ワーカーを起動すればチェックポイントから
  再開します。ただし、完了のチェックポイントがないエージェントの呼び出しが残って
  いれば、再開した実行はその呼び出しで止まり、人の確認を待ちます。
- 止まった実行には、理由、やり直してよいか（`retry`）、人が確かめること
  （`check`）を表示します。`retry: yes` は「新しい実行を始めても、結果の
  分からないエージェントの呼び出しを重ねて送らない」という意味で、同じ入力で
  成功するという保証ではありません。
- 開始のチェックポイントだけが残ったエージェントの呼び出しは、
  `uncertain-invocation` として `retry: NO` になり、送り直すコマンドは出しません。
  プロバイダーの履歴と作業場所、表示されたチェックポイントを人が確かめてください。
  この実行には、作業ツリーを消すコマンドも出しません。分類できない失敗も
  `retry: NO` です。
- 事前確認を通ったあとで、プロバイダーが実装、修正、レビュー、見立ての呼び出しを
  はっきり断った場合（ログイン切れ、利用上限、使えなくなったモデルなど）は、
  `rejected-invocation` として `retry: yes` で止まります。断られたことは呼び出しの
  完了のチェックポイントとして記録するので、再開しても送り直さず、同じ拒否の理由を
  表示します（`refusal: ...`）。拒否と判定するのは、プロバイダーがはっきり断った
  場合だけです。時間の上限、取り消し、接続の切断、判定できないエラーは、拒否として
  扱いません。事前確認のほかでは、その呼び出しでエージェントが動いたあと（文章、
  推論、ツールの呼び出し、使用量の報告のどれかが届いたあと）のエラーも、すでに
  何かを実行したかもしれないので、拒否とせず `uncertain-invocation` として止めます。
  開始だけのチェックポイントが残っていれば、拒否より先に `uncertain-invocation` と
  して扱います。
- factory が自分の時間の上限でエージェントの呼び出しを止めた場合は、結果の
  分からない呼び出しにはしません。止めた理由が分かっているので、上限の種類（全体か
  無通信か）と長さを完了のチェックポイントとして記録し、再開しても送り直しません。
  実装と修正の呼び出しが作業ツリーに変更を残していれば、それを通常どおり候補として
  封印し、検証へ進みます（[「実際のリポジトリで動かす」](configuration.md)を参照）。変更がない場合と、
  仕様の作成・修正・レビュー、レビュー、事前確認の呼び出しを止めた場合は、
  `agent-timeout` として `retry: yes` で止まります。見立ては、これまでどおり
  `unknown` を記録して実行を続けます。ワーカーの停止やリースを失ったことで呼び出しが
  終わった場合は、これまでどおり `uncertain-invocation` です。
- `--publish` 付きで取り消した実行は、`cancelled-publish` として `retry: NO`
  になります。プッシュやプルリクエストの作成が、記録する前に済んでいるかもしれないので、
  リモートのブランチとプルリクエストを先に確かめてください。
- `retry: yes` の実行には `demo retrigger --run <id>` を表示します。止まった実行に
  保存した入力（タスク、設定、プロファイル）のまま、新しい実行を 1 回だけ始めます。
  同じコマンドをもう一度打っても、最初に始めた実行を返すだけです。`retry: NO` の
  実行や、まだ止まっていない実行には、実行を断ります。素の `demo trigger` は同梱の
  題材で動くので、次の手順には出しません。
- `baseline-check-failed`、`preflight-failed`、`rejected-invocation`、`agent-timeout` には、
  `demo retrigger --run <id> --reload-config` も表示します。`factory.json` を直してから打つコマンドです。
  保存したタスク、仕様、`dispositions`、確定した文脈（context）、イシュー、対象のリポジトリはそのままで、
  `factory.json` だけを読み直します。読み直すのは、`trigger` のときに `--config` で
  渡したファイルで、渡していなければリポジトリ直下の `factory.json` です。
  直下の `factory.json` を消した場合は、設定なしの `trigger` と同じに扱います。
  `--config` で渡したファイル（パスが直下の `factory.json` でも）がなくなって
  いれば、設定なしとはみなさず、エラーにします。
  プロファイル、`check`、`selfCheck`、`testProbe`、`setup`、`base`、`codexPath`、時間の上限、
  `baselineCheck`、`baselineReuse` は、`trigger` と同じ規則で決めて検証します。`trigger` のときの
  `--check`、`--setup`、`--base` は、これまでどおり設定より優先します。その実行では、
  次の手順の注記にもそう表示します。これらを変えるときは `trigger` からやり直します。
  同梱の題材の実行と、外部の指摘からの修正の実行（`demo repair`）は `factory.json` を
  読まないので、`--reload-config` は表示しません。修正の実行の、人が確かめることの欄も、
  設定を変えるときは通常の `trigger` から始めるか、直したあとに承認された実行から
  修正をやり直すよう案内します。
  時間の上限を設定に書いていなければ、`retrigger` を打ったプロセスの環境変数を、
  それもなければ既定値を使います。ファイルの中身が同じあいだは、何度打っても最初に
  始めた実行を返します。書き換えれば、その版で 1 回だけ新しい実行を始めます。
  環境だけを直した場合（依存パッケージのインストール、プロバイダーへのログインなど）は、
  `--reload-config` なしの `retrigger` を使います。
- 終わった、リポジトリが対象の実行の作業ツリーが残っていれば、
  `git -C '<repo>' worktree remove '<workdir>'` を表示します。準備の工程が記録した
  パスがあるときだけ出し、強制削除やブランチの削除は含みません。変更が残っている
  作業ツリーは、git が削除を断ります。実行するかどうかは、使う人が決めます。
  承認・納品済みの実行とアーカイブ済みの実行は、本来片付いているはずなので、
  代わりに `demo prune --apply` を表示します。こちらは強制削除と、Git の登録の
  片付けまで行い、ブランチは残します。
  まとめて片付けるときは `demo prune` を使います（下の「終わった実行の作業ツリーを
  片付ける」）。
- 作業ツリーを片付けた実行には `worktree: removed` と表示します。承認・納品のあとに
  片付けられなかった実行には、git が出したエラーを `warning:` として表示します。

同じ理由と次の手順は、`status --run <runId>` の `diagnosis` と、レポートの
`failure`（JSON）と `Stop reason` の節（Markdown）にも出ます。

## ワーカーの稼働状態

`trigger` の JSON、`status --run` の JSON、`status` の一覧は、ワーカーが動いているかを
表示します。ワーカーがいなければ `pending` の実行は進まないので、`trigger` と `status`
はワーカーを起動するコマンドを案内します。ただし、`trigger` がワーカーを自動で起動した
ときは、`start` を `null` にし、起動したワーカーの pid とログの場所を `autoStarted`
に入れます。起動したワーカーがまだロックを握っていなければ、`running` が `false` の
ことがあります。自動で起動しなかったとき（止めている、要らない、ワーカーがいる）の
JSON は下の例のとおりで、`autoStarted` はありません。

```json
"worker": {
  "running": false,
  "pid": null,
  "startedAt": null,
  "start": "pnpm --filter example-local-agent-loop demo worker"
}
```

- 動いているかは、ワーカーのロック（`worker.lock`）が握られているかで決めます。
  `kill -9` で止まったワーカーの `worker.json` は残りますが、ロックは残らないので、
  動いているとは表示しません。pid と起動した時刻は、ロックが握られているときだけ
  `worker.json` から読んで表示します。

```json
"worker": {
  "running": false,
  "pid": null,
  "startedAt": null,
  "start": null,
  "unknownReason": null,
  "autoStarted": {
    "pid": 51234,
    "log": "~/.local/state/local-agent-loop/logs/worker-2026-10-22.log"
  }
}
```

- ワーカーが動いていれば、`pending` の実行や判断済みの待ちに、ワーカーの起動を
  案内しません。
- `status --run` の `lastLeaseRenewedAt` は、ワーカーがその実行のリースを最後に
  更新した時刻です。専用の生存通知（heartbeat）は記録していないので、有効なリースの
  期限からリースの長さ（10 秒）を引いて求めます。リースを持たない `pending`、
  `waiting`、終わった実行と、リースが期限切れの実行では `null` です。ワーカーは
  実行を進めているあいだだけリースを更新するので、ワーカーが動いていても、実行を
  持っていないあいだは更新がありません。

## 実行が止まるまで待つ（wait）

`wait` は、実行が終わるか、人の判断を待つところで止まるまで待ち、結果をまとめて
表示して終わります。実行の状態やレポートを何度も確かめる代わりに使います。

```bash
pnpm --filter example-local-agent-loop demo wait --run <runId> \
  [--timeout <ms>] [--worker-timeout <ms> | --no-worker-timeout] [--format json]
```

- 保存された実行を 1 秒ごとに読み直します。別のプロセスのワーカーのイベントは
  このプロセスに届かないので、DB だけを見ます。実行を進めるのは、別に起動した
  ワーカーです。
- 止まったと判断するのは、実行そのものの `status` が `completed`、`failed`、
  `cancelled` のときと、`waiting` で、実行の `waitingOnWaitId` が指す待ちが
  まだ解決していないときです。`output` や `progress` の中にある `status` は見ません。
  承認か却下を記録済みで、ワーカーの再開を待っている実行は、待ち続けます。
- `--timeout` は全体の制限時間です。省略すると制限しません。
- `--worker-timeout` は、ワーカーがいない状態が続いたときに打ち切るまでの時間です。
  既定は 10 秒です。ワーカーがまた見つかれば、数え直します。`--no-worker-timeout`
  を付けると、ワーカーがいないことだけでは打ち切りません。
- どちらの時間の上限も、1 以上 2147483647 以下の整数のミリ秒です。範囲の外の値や
  小数を渡すと、待ち始める前に終了コード 1 で終わります。
- 実行が止まっていれば、時間の上限やワーカーの不在よりも、その結果を優先します。
- レポートは、結果が決まったあとに 1 回だけ作ります。

まとめには、実行の ID、実行の状態、結論（`conclusion`）、止まった理由、次のコマンド、
ワーカーの状態、最後にリースを更新した時刻、工程ごとの時間を出します。計測できて
いない試行を含む工程の時間は、分かった分だけの合計を出さず、`null`（通常の出力では
`unknown`）にします。`--format json` では、同じ項目を 1 つの JSON オブジェクトで出します。

```text
run:        01M3NS4V2HEWGT14DDC8TPKC0H
status:     completed
conclusion: approved
stopped:    completed: approved and delivered (exit 0)
diagnosis:  finished: approved
worker: running (pid 43292, started 2026-09-29T05:10:46.402Z)
last lease renewal: none recorded
timing:
  setup: work=20 ms, wall=20 ms
  code: work=71 ms, wall=73 ms
  ...
  stage total: 236 ms
  run elapsed: 11764 ms
```

終了コードは次のとおりです。

| 終了コード | 意味                                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| 0          | 承認され、納品まで済んで完了した                                                 |
| 1          | コマンドの誤り（引数の誤り、存在しない実行など）                                 |
| 2          | まだ解決していない待ちで止まっている（承認待ちと、それ以外の Durably の `wait`） |
| 3          | 失敗した、または承認・納品に至らずに完了した（却下、検証の失敗、レビューの上限） |
| 4          | 取り消された                                                                     |
| 5          | `--timeout` に達した                                                             |
| 6          | ワーカーがいない状態が `--worker-timeout` 続いた                                 |

## 止まった実行をアーカイブする

止まったまま誰も手を打たない実行は、アーカイブすると、`status` の上部
（`wait on a person or stopped`）と web UI の「止まったもの」から外れます。

```bash
pnpm --filter example-local-agent-loop demo archive --run <runId>
pnpm --filter example-local-agent-loop demo archive --run <runId> --delete-branch
pnpm --filter example-local-agent-loop demo archive --series <runId>
pnpm --filter example-local-agent-loop demo archive --series <runId> --delete-branch
pnpm --filter example-local-agent-loop demo unarchive --run <runId>
```

- アーカイブできるのは、止まった実行だけです。`failed` か `cancelled` で終わった実行と、
  承認と納品まで進まずに `completed` になった実行（検証の失敗、レビューの上限）が
  当たります。承認されて納品した実行や、人が却下して終わった実行は、誰の手も
  要らないので、アーカイブを断ります。判断待ちの実行は、アーカイブせずに
  `approve`、`reject`、`spec-revise` で判断します。この判定は、CLI、`status`、web UI が
  同じ関数（`archivable`）で行います。
- `unarchive` は、アーカイブのファイルがある実行なら、どれでも戻せます。
- アーカイブすると、状態のルートの `archived/<runId>` に小さなファイルを置きます。
  実行の状態、`step`、待ちは変えないので、止まった理由はそのまま残り、
  `unarchive` でファイルを消すと元の区分に戻ります。
- リポジトリが対象の実行をアーカイブすると、その実行の作業ツリーとレビュー用の
  スナップショットも片付けます。git が削除を断ったときは警告を表示し、アーカイブは
  そのまま済ませます。すでにアーカイブした実行にもう一度 `archive` を打つと、残った
  作業ツリーの片付けをやり直します。`unarchive` しても、作業ツリーは元に戻りません。
  準備の途中で失敗した実行（`pnpm install` の失敗など）は準備の記録がないので、
  git の登録から `runs/<runId>/work` と、そこにチェックアウトしたブランチを探して
  片付けます。消すブランチは、準備の工程がその実行に付ける名前のものだけです。人が
  切り替えた別のブランチは残します。登録もディレクトリもなければ、何もせず、警告も
  出しません。
- `git worktree remove` には 10 分の上限があります。依存パッケージを入れた大きな
  作業ツリーは、消すのに数分かかることがあるためです。上限で止まったときは、作業ツリーが
  一部だけ消えて残ることがあり、警告がそのパスと一緒にそう伝えます。消せなかったときは、
  git がまだそのディレクトリを作業ツリーとして登録しているかを確かめ、警告に書きます。
  登録が残っていれば、`demo prune --apply` で続きを消せます。残っていなければ、git は
  そのディレクトリを作業ツリーとして扱えず、ほかの方法では消さないので、手で消すように
  書きます。準備をやり直す前に前回の作業ツリーを消すときも同じ上限で、取り消しや
  リースを失ったときはそこで止めます。アーカイブ、片付け（`demo prune`）、納品後、
  新しいテストの試し実行のベースの片付けは、取り消しのあとにも実行する必要があるので、
  止めずに上限まで待ちます。web UI は書き込みを 1 つずつ処理するので、片付けの
  あいだは、ほかの操作が待ちます。
- アーカイブの印を付けた時点で応答を返し、作業ツリーを後で消す、という形はとって
  いません。消せなかったことを応答で伝えられなくなり、CLI と web UI が同じ関数から
  同じ結果を受け取れなくなるためです。
- ブランチは残します。`--delete-branch` を付けたときだけ、その実行が記録した
  factory のブランチ（イシュー付きの実行は `factory/issue-<番号>-<runId>`）と
  `factory/<runId>-squashed` を消します。
- `--series` は、指定した実行が属するタスク（最初の実行と、その下の修正の実行すべて）の、
  止まった実行をまとめてアーカイブします。タスクのどの実行の ID を渡してもかまいません。
  `--series` を繰り返すと、複数のタスクを順にアーカイブし、1 つが失敗しても残りは続けます。
  `unarchive` も、`--run` を繰り返すと、複数の実行をまとめて戻します。
  `status` の `stops:` の行は、最初の実行の ID でこのコマンドを出します。
- `--series` がアーカイブするのは、止まった実行だけです。判断待ち、実行中、承認と納品まで
  済んだ実行はそのまま残し、エラーにもしません。納品済みの実行の ID を渡しても、
  同じタスクの止まった実行をアーカイブします。
- 納品済みのタスクでも、止まった実行は自動では解決済みになりません。アーカイブは
  「人が確認を終えた」という合図で、作業ツリーの片付けもこの合図で行うためです。
- `--series` は、すでにアーカイブした止まった実行にも、片付けをやり直します。
  `--delete-branch` を付けると、対象の各実行のブランチを、`--run` と同じ規則で消します。
  警告は、実行の ID を先頭に付けて表示します。
- `--series` で一部の実行のアーカイブに失敗しても、残りの実行は続けてアーカイブします。
  最後に、失敗した実行を ID 付きで表示し、0 以外の終了コードで終わります。
- `--run` と `--series` は同時に指定できません。どちらもなければエラーです。
- `status` と web UI は、同じファイルを同じ関数（`groupTasks`）で読むので、
  どちらでアーカイブしても、両方から外れます。

## 終わった実行の作業ツリーを片付ける

リポジトリが対象の実行の作業ツリー（`runs/<runId>/work`）は、次のときに片付けます。
片付けるのは、作業ツリー、レビュー用のスナップショット（`runs/<runId>/review-snapshots`）、
`testProbe` のベースの作業ツリー（`runs/<runId>/base-work`）だけです。

- 承認して納品した実行は、納品の記録を `step` に残した直後に、自分の作業ツリーを
  片付けます。納品のあとで直すときは、記録したコミットとブランチから新しい実行を
  作るので（`demo repair`）、元の作業ツリーは要りません。
- 止まった実行をアーカイブしたとき（上の「止まった実行をアーカイブする」）。
- `demo prune --apply` を打ったとき。この変更より前に終わった実行の作業ツリーを、
  まとめて片付けるためのものです。

```bash
pnpm --filter example-local-agent-loop demo prune                      # 対象と容量を表示するだけ
pnpm --filter example-local-agent-loop demo prune --apply              # worktree を片付ける
pnpm --filter example-local-agent-loop demo prune --delete-branches    # 消すブランチも表示する
pnpm --filter example-local-agent-loop demo prune --delete-branches --apply
```

- 削除は `git worktree remove --force` で行い、続けて `git worktree prune` で
  git の登録も消します。git が削除を断ったときは、ディレクトリをほかの方法で
  消さずに残し、警告にします。
- 納品のあとの片付けに失敗しても、実行は承認・納品済みとして終わります。失敗の理由は
  実行の出力の `worktreeCleanupWarning` に残り、`status`、レポート、web UI の
  詳細画面に出ます。`demo prune --apply` でやり直せます。
- `demo prune` の対象は、終わった、リポジトリが対象の実行のうち、承認して納品したもの
  か、アーカイブしたもので、作業ツリーがまだ残っているものです。保存した実行、準備、
  納品の記録、アーカイブのファイルから決め、ディレクトリの名前だけからは決めません。
  `--apply` なしでは、対象の実行の ID、作業ツリーごとの容量、合計を表示するだけで、
  何も消しません。同じコマンドをもう一度打っても、片付けが済んでいれば、何もせずに
  成功します。
- `pending`、`leased`、`waiting` の実行は、アーカイブのファイルがあっても片付けません。
  アーカイブしていない止まった実行、却下した実行、納品せずに完了した実行も
  対象外です。止まった実行の作業ツリーは、人が原因を調べる材料だからです。
- ブランチは、通常の片付けでは消しません。`demo prune --delete-branches --apply` は、
  アーカイブした実行が記録した factory のブランチと `factory/<runId>-squashed`
  だけを消します。作業ツリーが残っているかどうかは問いません。`--apply` なしでは、
  消す予定のブランチを表示します。納品した実行のブランチは消しません。納品物で
  あり、`demo repair` の起点だからです。
- 片付けたあとも、仕様、検証のログ、エージェントの出力、レポート、チェックポイント、
  候補の差分、納品の記録（パッチと `delivery`）は、そのまま読めます。レポートと
  web UI は、片付けた作業ツリーのパスを作業場所として案内せず、「作業ツリーは
  片付け済み」と表示します。
- 実行全体、リモートのブランチ、プルリクエストは消しません。この方針は
  [ADR-0028](../../../docs/adr/0028-local-agent-loop-worktree-retention.md) に
  まとめています。

## DB と作業物の置き場所

DB（データベース）と、すべての実行のデータは、`~/.local/state/local-agent-loop/`
に置きます。

```text
~/.local/state/local-agent-loop/
  local-agent-loop.db              run、step、attempt、wait
  runs/<runId>/
    work/                          worktree（同梱題材ではコピー）。repo runでは
                                   納品後やアーカイブ時に片付ける
    worktree-removed               納品後に片付けを始めた印（再実行の判定用）
    operation-checkpoints/         LLM呼び出しと検証のcheckpoint
    agent-logs/<attempt>.log       エージェントの出力（LLM呼び出しの試行ごと）
    verification-scratch/          検証用の一時領域
    verification-logs/<candidate>/<attempt>/
      stdout.log                   検証コマンドの標準出力（全文）
      stderr.log                   検証コマンドの標準エラー（全文）
    candidates/<candidate>/        repo runの候補ごと
      changes.diff                 base commitから候補commitまでの全差分
      changed-files.txt            変更ファイルの一覧（1行1ファイル）
    delivery/<candidate>.patch     成果物
```

- **検証のログ**: 採点コマンドの出力は、検証の実際の試行（step attempt）ごとに、
  `verification-logs/` へ切り詰めずに保存します。レポートの抜粋や、修正の
  プロンプトに渡す出力は、これまでどおり末尾だけですが、ログファイルには途中の
  失敗した箇所も残ります。時間の上限で打ち切った試行は、終了コードを `null` にし、
  打ち切るまでの出力を残します。完了のチェックポイントから復旧した試行は、採点を
  やり直さず、元の試行のログと終了コードを指します。開始のチェックポイントだけが
  残った試行は、採点し直し、新しい試行のログを別のディレクトリに書きます。止まった
  試行のログも消しません。
  取り消しやリースを失ったことで中断した試行も、終了コードを `null` にして途中までの
  ログを記録し、`interrupted: true` を付けます。この試行は判定を出していないので、
  検証の結果には数えません。子プロセスを起動する前に中断した試行は、ログを記録
  しません。ログファイルへの書き込みに失敗しても、検証の結果は変えず、エラーを
  `writeError` に残します。そのログファイルは、中身が欠けているかもしれません。
- **エージェントの出力**: LLM を呼ぶ試行は、送る前に `agent-logs/<attempt>.log` を
  作り、そのパスを試行の `agentLog.path` に記録してから呼び出します。ファイルには、
  アシスタントの本文を届いた順に追記します。ツールの呼び出しは、名前と短い引数
  （コマンド、検索語、パスを優先）で `> exec pnpm test` のように 1 行ずつ、
  コマンドの終了コードは `< exec exit 1` のように 1 行ずつ追記します。プロンプト、
  思考や推論のブロック、使用量は書きません。完了のチェックポイントから復旧した
  試行と、送る前に取りやめた試行は、ファイルを作りません。追記に失敗しても呼び出しの
  結果は変えず、エラーを `agentLog.writeError` に残します。作業ツリーの片付けや
  `demo prune` では消しません。保存の期限やローテーションはありません。
- **候補の差分**: リポジトリの実行では、候補を封印するたびに、記録済みのベースの
  コミットと候補のコミットの差分を `candidates/<candidate>/` に書き出します。
  作業ツリーの外なので、エージェントが書き換えることはできません。検証で止まって
  レビューに進まなかった候補にも書きます。両方のレビュアーのプロンプトには、この
  2 つのファイルの絶対パスが入り、全文を読むよう指示します。Claude のレビュアーは、
  作業場所の外では、この 2 つのファイルだけを読めて、書き込みはできません。

`worker`、`trigger`、`status`、`waits`、`approve`、`report`、`compare` は、どれも引数なしで同じ
DB を見ます。ディレクトリがなければ、DB を開く前に作ります。durably の
チェックアウトの中にも、対象のリポジトリの中にも、DB や `runs/` は作りません。
チェックアウトをどのコミットに切り替えても、過去の実行はそのまま読めます。置き場所を
変える引数や環境変数はありません。2 つのプロセスが別の DB を見ると、実行が黙って
見えなくなるからです。
