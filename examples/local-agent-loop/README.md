# local-agent-loop — Durably local factory demo

Durably、ローカルの SQLite、AI SDK v7、ログイン済みの CLI 1 つ（Codex か
Claude Code）を使い、実装、固定したテスト、独立したレビュー、人の承認までを
ローカルで実行するサンプルです。新しいワークフローのフレームワーク、Docker、
GitHub の認証、CI は使いません。

設計の中心は、工程の区切りと会話の区切りを別にすることです。

- 工程は `code → verify → review → approve → finish/stop` に分け、それぞれの
  判断と実行を Durably の `step` として保存します。
- `code` は最初の実装と修正で同じものを使います。`--context reuse` では、
  プロバイダーが持つ同じセッションを ID を指定して再開し、`--context fresh` では
  毎回新しい会話を使います。
- `verify` と 2 つの `review` は、編集できる作業ディレクトリではなく、固定した
  同じ候補を見ます。レビューの会話は、実装の会話とは別の新しいセッションです。
- 修正すると新しい候補になり、古いテスト結果、レビュー、承認は reducer
  （状態を更新する関数）が無効にします。
- 承認待ちとその `signal` には同じ候補の ID が必要で、最終的な成果物として
  承認された候補を返します。

## 構造

`src/factory/job.ts` がするのは、保存した状態から次の工程を決める判断を記録し、
実際の関数を登録した表から呼び、返ったイベントで状態を更新することだけです。
作業場所の用意、固定したテスト、並列のレビュー、待ちは、`src/factory/stages.ts`
の各工程が組み立てます。工程全体をまとめて `step.run()` で包まないので、
承認待ちは Durably の正しい区切りにあります。

```text
setup
triage (profiles.triage があるときだけ一度。判定を記録するだけ)
decision:N
  └─ stages[decision.stage](...)
       ├─ code: agent call → fixed Candidate
       ├─ verify: fixed acceptance command against Candidate
       ├─ review: correctness + edge-cases (step.all, new sessions)
       ├─ approve: prepareWait → waitFor(Candidate ID)
       └─ finish/stop: approved Candidate or terminal failure
```

ここでいう候補（Candidate）は、「実装を終えた時点のコードをコピーした候補の版」
です。テスト、レビュー、承認がそれぞれ別のコードを見ないようにするための
識別子で、信頼できないコードを隔離するセキュリティのサンドボックスではありません。
候補は次の参照を持ちます。

```ts
type CandidateRef = {
  id: string
  snapshotDir: string
  sourceHash: string
  acceptanceHash: string
}
```

受け入れテストは、開始のときに別のディレクトリへ固定します。検証のコマンドは
サンプル側で固定した `node --test` で、エージェントが編集した `package.json` の
`test` スクリプトは合否の判定に使いません。候補は作ったあとに同じ場所へ上書きせず、
検証とレビューの前後、承認から再開したあと、終わる直前に、ファイルのバイト列
そのもののハッシュを確かめます。これは、工程のあいだの取り違えや意図しない変更を
見つけるための仕組みで、悪意のあるコードからファイルシステムを守るものでは
ありません。レビューのプロンプトには、固定したベースからの変更の一覧と元の
`src/calc.js` を渡します。そのため、候補だけを読む独立したセッションでも、
「変更が最小か」「`mul()` を触っていないか」を比べられます。
固定したテストは、通常の子プロセスで実行します。子プロセスは自分のプロセス
グループを持ち、時間の上限や取り消しではグループごと終わるので、CLI が起動した
孫プロセスが残りません。強制終了は、node 自身の `--test-timeout` より少し後に
置きます。同時に送ると SIGKILL で先に終わり、「どのテストが止まったか」を含まない
結果が修正のプロンプトへ渡るためです。

## セットアップ

```bash
pnpm install
pnpm --filter example-local-agent-loop typecheck
pnpm --filter example-local-agent-loop test:unit
```

使うプロバイダーだけをインストールし、ログインしておきます。

```bash
codex --version
codex login

# または
claude --version
claude auth login
```

Codex では `ai-sdk-provider-codex-cli@2.3.0` の app-server モードを使います。
最初の呼び出しで続けて使えるスレッド（persistent thread）を作り、修正のときは
保存した `threadId` を指定します。Claude では `ai-sdk-provider-claude-code@4.3.1`
が返す `sessionId` を保存し、修正のときは `resume` で再開するセッションを指定
します。「作業ディレクトリでいちばん新しい会話を選ぶ」動きは使いません。

## 実行

ターミナル 1 でワーカーを動かし続ける手順です。動かし続けなくても、ターミナル 2
の `trigger` などがワーカーを自動で起動します（「ワーカーの自動起動とアイドル終了」の節）。

ターミナル 1:

```bash
pnpm --filter example-local-agent-loop demo worker
```

ワーカーは状態のルート（state root）ごとに 1 つだけ動きます。ワーカーは起動するときに
`~/.local/state/local-agent-loop/worker.lock` を OS のファイルロック（SQLite の排他
トランザクション）で握ります。同じ状態のルートで 2 つ目を起動すると、動いている
ワーカーの pid と起動元のチェックアウトを表示し、終了コード 1 で起動を断ります。

```text
another worker already runs on ~/.local/state/local-agent-loop: pid 41234, started 2026-09-25T01:02:03.000Z from /Users/me/src/durably/examples/local-agent-loop. Stop it first (kill 41234); two workers would pick up each other's runs.
```

- ロックはプロセスと一緒に消えます。Ctrl-C、SIGTERM、初期化の失敗では自分で
  解放し、`kill -9` やクラッシュでは OS が解放します。pid を書いた
  `worker.json` が残っていても、次のワーカーはロックを取り直して上書きするので、
  古い情報だけで起動を断ることはありません。
- `demo trigger`、`demo status`、`demo wait` は、同じロックファイルをのぞいて
  ワーカーがいるかを確かめます（`wait` は 1 秒ごと。読み取りの瞬間だけ共有ロックを
  握ります）。ワーカーの起動は、この瞬間とぶつかっても最大 2 秒までやり直して
  乗り越えるので、`wait` で見ている最中にワーカーを起動しても失敗しません。1 つ目の
  ワーカーが排他ロックを握り続けているあいだは、2 つ目のワーカーはこのやり直しを
  過ぎても、これまでどおり断られます。
- ロックファイルが読めない（壊れている、権限がないなど）ときは、ワーカーがいるかを
  「不明」（`running: null`、`worker: unknown`）と表示します。`wait` は「不明」を
  「ワーカーがいない」とは数えないので、それだけで終了コード 6 にはなりません。
- 別の状態のルート（`HOME` が違う環境）のワーカーどうしは、互いを断りません。
- 時間の上限は `trigger` のときに実行の入力へ固定されるので、ワーカーの環境変数で
  既存の実行の値が変わることはありません（「trigger時点で固定されるもの」）。

ターミナル 2:

```bash
pnpm --filter example-local-agent-loop demo trigger \
  --provider codex --context reuse --max-iterations 2

pnpm --filter example-local-agent-loop demo status --run <runId>
pnpm --filter example-local-agent-loop demo waits --run <runId>
pnpm --filter example-local-agent-loop demo approve --run <runId> --wait <waitId>
pnpm --filter example-local-agent-loop demo report --run <runId> --format md
```

`--max-iterations` は、1 つの実行で実装と修正を合わせて何回までするかで、1 から 5
まで指定できます。省略すると 2 です。

Claude では `--provider claude` に替えるだけです。承認の CLI は承認待ちの
メタデータから候補の ID を読み、`signal` のペイロードにも同じ ID を入れます。
却下するときは、`approve` の代わりに `reject` を使います。

### ワーカーの自動起動とアイドル終了

ターミナル 1 でワーカーを動かし続けなくても、実行を進めるコマンドが、必要なときに
ワーカーを起動します。

- `trigger`、`repair`、`retrigger`、`approve`、`reject`、`spec-revise` が成功した
  あと、ワーカーの仕事があれば、ワーカーのロックを調べます。ワーカーがいなければ
  `demo worker --exit-when-idle` を起動し、もういれば何もしません。ロックが読めず、
  ワーカーがいるか分からないとき（`running: null`）は起動せず、理由を標準エラー出力に
  出します。失敗したコマンドや、入力の検証で断ったコマンドは起動しません。
- ワーカーの仕事とは、`pending` と `leased` の実行（リースの期限は問いません）と、
  いま待っている待ちが判断済み（`resolved`）の `waiting` の実行です。判断済みの
  待ちを持つ実行は、`pending` に戻るのを待たずにワーカーが再開します。誰も判断して
  いない待ちだけを待つ実行は数えません。
- 起動したワーカーは、起動元とは別のセッション（別のプロセスグループ）で動き、
  コマンドの終わりを待たせません。エージェントが起動元のシェルやプロセスグループを
  片付けても、ワーカーは止まりません。
- 起動の知らせと警告は、すべて標準エラー出力に出します。標準出力には、これまでどおり
  コマンドの出力（`trigger` の JSON など）だけを出します。起動に失敗しても、
  コマンドの終了コードは変わりません（実行はもう保存されています）。起動に成功すると、
  ワーカーの pid とログの場所を 1 行出します。
- ワーカーの標準出力と標準エラー出力は、状態のルートの
  `~/.local/state/local-agent-loop/logs/worker-YYYY-MM-DD.log`（起動した日、
  ローカル時刻）に追記します。同じ日に何度起動しても、既存のログは消しません。
- 自動起動を止めるには、各コマンドに `--no-auto-worker` を付けるか、環境変数
  `LOCAL_AGENT_LOOP_NO_AUTO_WORKER=1` を設定します。実行は、ワーカーが来るまで
  `pending` のままです。
- 自動起動したワーカーのアイドル期間は `LOCAL_AGENT_LOOP_IDLE_MS`（既定 30000）で
  変えられます。1 から 2147483647 までの整数のミリ秒だけを受け付け、範囲の外なら
  ワーカーを起動せずに警告します。
- 自動起動したワーカーは、コマンドを実行したチェックアウトの CLI で動きます（どの
  チェックアウトかは `worker.json` の `checkout` に残ります）。同じ状態のルートを
  共有していると、固定したチェックアウト（「durably checkoutを固定して呼ぶ」の節）とは
  別のチェックアウトから実行したコマンドが、そのチェックアウトのワーカーを起動する
  ことがあります。固定したチェックアウトのワーカーで処理したいときは、その
  チェックアウトでワーカーを動かしておくか、自動起動を止めてください。

`demo worker --exit-when-idle [--idle-ms <ms>]` は、仕事がない状態が `--idle-ms`
（既定 30000、1 から 2147483647 までの整数）続くと終わります。オプションなしの
`demo worker` は、これまでどおり動き続けます。

- 仕事があるかは 500 ミリ秒ごと（`--idle-ms` がそれより短ければその間隔）に確かめ、
  前の確認が終わってから次を始めます。DB（データベース）を読めなかった確認は
  アイドルと数えず、エラーを標準エラー出力に出して、アイドル期間を数え直します。
- アイドル期間が過ぎたら、ポーリングを止めてからもう一度確かめます。そこで仕事が
  見つかれば、ポーリングを再開して処理します。
- この最後の確認からロックを手放すまでのあいだに実行が作られると、起動元のコマンドは
  まだワーカーがいると見て、新しく起動しません。そのため、アイドルで終わるワーカーは
  ロックを手放したあとにもう一度仕事を確かめます。仕事があれば、自動起動と同じ方法で
  次のワーカーを起動し、ログに `[idle] work arrived as the worker stopped; started
a successor (pid N)` を書きます。次のワーカーも同じようにアイドルで終わるので、
  ワーカーがロックを握っているあいだに作られた実行は、そのワーカーがロックを手放す
  前か後のどちらかで必ず見つかります。次のワーカーが起動しない場合（起動の失敗、
  自動起動を止めている場合）は、実行が `pending` のまま残ります。`demo wait` は
  `--worker-timeout`（既定 10 秒）でワーカーがいない状態を見つけ、終了コード 6 で
  知らせるので、そのときは `demo worker` を起動してください。
- SIGTERM、SIGINT、アイドル終了では、`[shutdown] reason=SIGTERM`、
  `[shutdown] reason=SIGINT`、`[shutdown] reason=idle` をログに書きます。その後、
  実行中のエージェントの CLI を止め、進行中のアイドルの確認を待ち、ポーリングを止めて
  ロックを手放します。アイドル終了なら、ここで上に書いた次のワーカーの確認をします。
  最後に DB を閉じ、出力を書き終えてから、終了コード 0 で終わります。終了処理の
  最中にシグナルが届いても、終了処理を重ねて走らせることはありません。

### 止まった実行と次の手順を見る

`--run` を付けない `status` は、手を打つ必要があるタスクを一覧にします。タスクは、
最初の実行と、そこから `demo repair` で始めた修正の実行（修正の修正も含む）を
まとめた単位です。タスクごとに、状態を代表する実行の理由と、次に打つコマンドを
表示し、その下にタスクの名前と、ほかの実行を `also:` として並べます。

- 先に「人の判断待ち」（承認待ち、仕様の判断待ち、承認以外の入力待ち）と
  「未解決の停止」のタスクを、次に `pending`、`leased`、判断済みで再開待ちのタスクを
  出します。それぞれ新しい順です。
- 修正の実行が止まっても、同じ修正元から後に始めた修正の実行が承認されていれば、
  その停止は解決済みとして扱い、一覧の上部には出しません（`also:` に
  `replaced by a later approved repair` と付けます）。
- 代表の実行は、判断待ちや停止があればその実行、動いている実行があればその実行、
  どれもなければ置き換えられていない最新の実行です。
- `demo archive` でアーカイブした止まった実行は、終わった実行として数えます
  （下の「止まった実行をアーカイブする」）。同じタスクのほかの実行が人の手を
  待っていれば、そのタスクは上部に残ります。アーカイブした実行は、最後に
  `stopped run(s) archived:` として、戻すコマンドと一緒に並べます。
- 止まったままアーカイブしていない実行があるタスクには、`stops:` の行で、その件数と
  `demo archive --series <最初の run の ID>` を出します。後の修正の実行が承認されて
  置き換えた停止も数え、アーカイブした停止は数えません。この行はテキストの表示だけで、
  `--format json` と web UI には出しません。
- 何もなければ `No runs need attention` と表示します。
- 実行が複数あるタスクには、`total:` の行で、全部の実行の所要時間と費用の合計を
  出します。どれかの実行の値が分からなければ `unknown` です。
- `--format json` は、同じタスクの並び（`tasks`、合計は各タスクの `total`）、
  ワーカーの状態、DB の場所を JSON で出します。web UI の一覧（`/api/runs` の
  `tasks`）と同じ値です。

```bash
pnpm --filter example-local-agent-loop demo status
pnpm --filter example-local-agent-loop demo status --format json
```

```text
01M375ZAYC...  waiting  (created 2026-09-23T13:06:11.530Z)
  reason:  waiting for human approval of candidate candidate-1-9958e915bf52
  next:    pnpm --filter example-local-agent-loop demo report --run 01M375ZAYC...  # read the reviews first
           pnpm --filter example-local-agent-loop demo approve --run 01M375ZAYC... --wait 01M375ZC2C...
           pnpm --filter example-local-agent-loop demo reject --run 01M375ZAYC... --wait 01M375ZC2C...
  task:    #261 Round the report's cost to cents  (first run 01M375ZAYC..., 1 run(s))
```

- 表示するコマンドは、リポジトリの中のどこからでも、そのまま貼り付けて実行できます。
  補足は `  # ...` のシェルのコメントとして後ろに付けます。
- 承認待ちで止まっている実行にだけ、その実行の ID と待ちの ID を入れた `approve` と
  `reject` を表示します。承認か却下を記録済みで、まだワーカーが取り出していない
  実行には、判断を記録済みであることと、ワーカーの起動を表示します。
- `leased` は、リースの期限内なら実行中、期限切れならワーカーが止まったものとして
  分けます。期限切れは失敗ではないので、ワーカーを起動すればチェックポイントから
  再開します。ただし、完了のチェックポイントがないエージェントの呼び出しが残って
  いれば、再開した実行はその呼び出しで止まり、人の確認を待ちます。
- 止まった実行には、理由、やり直してよいか（`retry`）、人が確かめること
  （`check`）を表示します。`retry: yes` は「新しい実行を始めても、結果の
  分からないエージェントの呼び出しを重ねて送らない」という意味で、同じ入力で
  成功するという保証ではありません。
- 開始のチェックポイントだけが残ったエージェントの呼び出しは、
  `uncertain-invocation` として `retry: NO` になり、送り直すコマンドは出しません。
  プロバイダーの履歴と作業場所、表示されたチェックポイントを人が確かめてください。
  この実行には、作業ツリーを消すコマンドも出しません。分類できない失敗も
  `retry: NO` です。
- 事前確認を通ったあとで、プロバイダーが実装、修正、レビュー、事前判定の呼び出しを
  はっきり断った場合（ログイン切れ、利用上限、使えなくなったモデルなど）は、
  `rejected-invocation` として `retry: yes` で止まります。断られたことは呼び出しの
  完了のチェックポイントとして記録するので、再開しても送り直さず、同じ拒否の理由を
  表示します（`refusal: ...`）。拒否と判定するのは、プロバイダーがはっきり断った
  場合だけです。時間の上限、取り消し、接続の切断、判定できないエラーは、拒否として
  扱いません。事前確認のほかでは、その呼び出しでエージェントが動いたあと（文章、
  推論、ツールの呼び出し、使用量の報告のどれかが届いたあと）のエラーも、すでに
  何かを実行したかもしれないので、拒否とせず `uncertain-invocation` として止めます。
  開始だけのチェックポイントが残っていれば、拒否より先に `uncertain-invocation` と
  して扱います。
- factory が自分の時間の上限でエージェントの呼び出しを止めた場合は、結果の
  分からない呼び出しにはしません。止めた理由が分かっているので、上限の種類（全体か
  無通信か）と長さを完了のチェックポイントとして記録し、再開しても送り直しません。
  実装と修正の呼び出しが作業ツリーに変更を残していれば、それを通常どおり候補として
  封印し、検証へ進みます（下の「実リポジトリに対して動かす」を参照）。変更がない場合と、
  仕様の作成・修正・レビュー、レビュー、事前確認の呼び出しを止めた場合は、
  `agent-timeout` として `retry: yes` で止まります。事前判定は、これまでどおり
  `unknown` を記録して実行を続けます。ワーカーの停止やリースを失ったことで呼び出しが
  終わった場合は、これまでどおり `uncertain-invocation` です。
- `--publish` 付きで取り消した実行は、`cancelled-publish` として `retry: NO`
  になります。プッシュやプルリクエストの作成が、記録する前に済んでいるかもしれないので、
  リモートのブランチとプルリクエストを先に確かめてください。
- `retry: yes` の実行には `demo retrigger --run <id>` を表示します。止まった実行に
  保存した入力（タスク、設定、プロファイル）のまま、新しい実行を 1 回だけ始めます。
  同じコマンドをもう一度打っても、最初に始めた実行を返すだけです。`retry: NO` の
  実行や、まだ止まっていない実行には、実行を断ります。素の `demo trigger` は同梱の
  題材で動くので、次の手順には出しません。
- `baseline-check-failed`、`preflight-failed`、`rejected-invocation`、`agent-timeout` には、
  `demo retrigger --run <id> --reload-config` も表示します。`factory.json` を直してから打つコマンドです。
  保存したタスク、仕様、`dispositions`、確定した文脈（context）、イシュー、対象のリポジトリはそのままで、
  `factory.json` だけを読み直します。読み直すのは、`trigger` のときに `--config` で
  渡したファイルで、渡していなければリポジトリ直下の `factory.json` です。
  直下の `factory.json` を消した場合は、設定なしの `trigger` と同じに扱います。
  `--config` で渡したファイル（パスが直下の `factory.json` でも）がなくなって
  いれば、設定なしとはみなさず、エラーにします。
  プロファイル、`check`、`selfCheck`、`testProbe`、`setup`、`base`、`codexPath`、時間の上限、
  `baselineCheck`、`baselineReuse` は、`trigger` と同じ規則で決めて検証します。`trigger` のときの
  `--check`、`--setup`、`--base` は、これまでどおり設定より優先します。その実行では、
  次の手順の注記にもそう表示します。これらを変えるときは `trigger` からやり直します。
  同梱の題材の実行と、外部の指摘からの修正の実行（`demo repair`）は `factory.json` を
  読まないので、`--reload-config` は表示しません。修正の実行の、人が確かめることの欄も、
  設定を変えるときは通常の `trigger` から始めるか、直したあとに承認された実行から
  修正をやり直すよう案内します。
  時間の上限を設定に書いていなければ、`retrigger` を打ったプロセスの環境変数を、
  それもなければ既定値を使います。ファイルの中身が同じあいだは、何度打っても最初に
  始めた実行を返します。書き換えれば、その版で 1 回だけ新しい実行を始めます。
  環境だけを直した場合（依存パッケージのインストール、プロバイダーへのログインなど）は、
  `--reload-config` なしの `retrigger` を使います。
- 終わった、リポジトリが対象の実行の作業ツリーが残っていれば、
  `git -C '<repo>' worktree remove '<workdir>'` を表示します。準備の工程が記録した
  パスがあるときだけ出し、強制削除やブランチの削除は含みません。変更が残っている
  作業ツリーは、git が削除を断ります。実行するかどうかは、使う人が決めます。
  承認・納品済みの実行とアーカイブ済みの実行は、本来片付いているはずなので、
  代わりに `demo prune --apply` を表示します。こちらは強制削除と、Git の登録の
  片付けまで行い、ブランチは残します。
  まとめて片付けるときは `demo prune` を使います（下の「終わった実行の作業ツリーを
  片付ける」）。
- 作業ツリーを片付けた実行には `worktree: removed` と表示します。承認・納品のあとに
  片付けられなかった実行には、git が出したエラーを `warning:` として表示します。

同じ理由と次の手順は、`status --run <runId>` の `diagnosis` と、レポートの
`failure`（JSON）と `Stop reason` の節（Markdown）にも出ます。

### ワーカーの稼働状態

`trigger` の JSON、`status --run` の JSON、`status` の一覧は、ワーカーが動いているかを
表示します。ワーカーがいなければ `pending` の実行は進まないので、`trigger` と `status`
はワーカーを起動するコマンドを案内します。ただし、`trigger` がワーカーを自動で起動した
ときは、`start` を `null` にし、起動したワーカーの pid とログの場所を `autoStarted`
に入れます。起動したワーカーがまだロックを握っていなければ、`running` が `false` の
ことがあります。自動で起動しなかったとき（止めている、要らない、ワーカーがいる）の
JSON は下の例のとおりで、`autoStarted` はありません。

```json
"worker": {
  "running": false,
  "pid": null,
  "startedAt": null,
  "start": "pnpm --filter example-local-agent-loop demo worker"
}
```

- 動いているかは、ワーカーのロック（`worker.lock`）が握られているかで決めます。
  `kill -9` で止まったワーカーの `worker.json` は残りますが、ロックは残らないので、
  動いているとは表示しません。pid と起動した時刻は、ロックが握られているときだけ
  `worker.json` から読んで表示します。

```json
"worker": {
  "running": false,
  "pid": null,
  "startedAt": null,
  "start": null,
  "unknownReason": null,
  "autoStarted": {
    "pid": 51234,
    "log": "~/.local/state/local-agent-loop/logs/worker-2026-10-22.log"
  }
}
```

- ワーカーが動いていれば、`pending` の実行や判断済みの待ちに、ワーカーの起動を
  案内しません。
- `status --run` の `lastLeaseRenewedAt` は、ワーカーがその実行のリースを最後に
  更新した時刻です。専用の生存通知（heartbeat）は記録していないので、有効なリースの
  期限からリースの長さ（10 秒）を引いて求めます。リースを持たない `pending`、
  `waiting`、終わった実行と、リースが期限切れの実行では `null` です。ワーカーは
  実行を進めているあいだだけリースを更新するので、ワーカーが動いていても、実行を
  持っていないあいだは更新がありません。

### 実行が止まるまで待つ（wait）

`wait` は、実行が終わるか、人の判断を待つところで止まるまで待ち、結果をまとめて
表示して終わります。実行の状態やレポートを何度も確かめる代わりに使います。

```bash
pnpm --filter example-local-agent-loop demo wait --run <runId> \
  [--timeout <ms>] [--worker-timeout <ms> | --no-worker-timeout] [--format json]
```

- 保存された実行を 1 秒ごとに読み直します。別のプロセスのワーカーのイベントは
  このプロセスに届かないので、DB だけを見ます。実行を進めるのは、別に起動した
  ワーカーです。
- 止まったと判断するのは、実行そのものの `status` が `completed`、`failed`、
  `cancelled` のときと、`waiting` で、実行の `waitingOnWaitId` が指す待ちが
  まだ解決していないときです。`output` や `progress` の中にある `status` は見ません。
  承認か却下を記録済みで、ワーカーの再開を待っている実行は、待ち続けます。
- `--timeout` は全体の制限時間です。省略すると制限しません。
- `--worker-timeout` は、ワーカーがいない状態が続いたときに打ち切るまでの時間です。
  既定は 10 秒です。ワーカーがまた見つかれば、数え直します。`--no-worker-timeout`
  を付けると、ワーカーがいないことだけでは打ち切りません。
- どちらの時間の上限も、1 以上 2147483647 以下の整数のミリ秒です。範囲の外の値や
  小数を渡すと、待ち始める前に終了コード 1 で終わります。
- 実行が止まっていれば、時間の上限やワーカーの不在よりも、その結果を優先します。
- レポートは、結果が決まったあとに 1 回だけ作ります。

まとめには、実行の ID、実行の状態、結論（`conclusion`）、止まった理由、次のコマンド、
ワーカーの状態、最後にリースを更新した時刻、工程ごとの時間を出します。計測できて
いない試行を含む工程の時間は、分かった分だけの合計を出さず、`null`（通常の出力では
`unknown`）にします。`--format json` では、同じ項目を 1 つの JSON オブジェクトで出します。

```text
run:        01M3NS4V2HEWGT14DDC8TPKC0H
status:     completed
conclusion: approved
stopped:    completed: approved and delivered (exit 0)
diagnosis:  finished: approved
worker: running (pid 43292, started 2026-09-29T05:10:46.402Z)
last lease renewal: none recorded
timing:
  setup: work=20 ms, wall=20 ms
  code: work=71 ms, wall=73 ms
  ...
  stage total: 236 ms
  run elapsed: 11764 ms
```

終了コードは次のとおりです。

| 終了コード | 意味                                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| 0          | 承認され、納品まで済んで完了した                                                 |
| 1          | コマンドの誤り（引数の誤り、存在しない実行など）                                 |
| 2          | まだ解決していない待ちで止まっている（承認待ちと、それ以外の Durably の `wait`） |
| 3          | 失敗した、または承認・納品に至らずに完了した（却下、検証の失敗、レビューの上限） |
| 4          | 取り消された                                                                     |
| 5          | `--timeout` に達した                                                             |
| 6          | ワーカーがいない状態が `--worker-timeout` 続いた                                 |

### 止まった実行をアーカイブする

止まったまま誰も手を打たない実行は、アーカイブすると、`status` の上部
（`wait on a person or stopped`）と web UI の「止まったもの」から外れます。

```bash
pnpm --filter example-local-agent-loop demo archive --run <runId>
pnpm --filter example-local-agent-loop demo archive --run <runId> --delete-branch
pnpm --filter example-local-agent-loop demo archive --series <runId>
pnpm --filter example-local-agent-loop demo archive --series <runId> --delete-branch
pnpm --filter example-local-agent-loop demo unarchive --run <runId>
```

- アーカイブできるのは、止まった実行だけです。`failed` か `cancelled` で終わった実行と、
  承認と納品まで進まずに `completed` になった実行（検証の失敗、レビューの上限）が
  当たります。承認されて納品した実行や、人が却下して終わった実行は、誰の手も
  要らないので、アーカイブを断ります。判断待ちの実行は、アーカイブせずに
  `approve`、`reject`、`spec-revise` で判断します。この判定は、CLI、`status`、web UI が
  同じ関数（`archivable`）で行います。
- `unarchive` は、アーカイブのファイルがある実行なら、どれでも戻せます。
- アーカイブすると、状態のルートの `archived/<runId>` に小さなファイルを置きます。
  実行の状態、`step`、待ちは変えないので、止まった理由はそのまま残り、
  `unarchive` でファイルを消すと元の区分に戻ります。
- リポジトリが対象の実行をアーカイブすると、その実行の作業ツリーとレビュー用の
  スナップショットも片付けます。git が削除を断ったときは警告を表示し、アーカイブは
  そのまま済ませます。すでにアーカイブした実行にもう一度 `archive` を打つと、残った
  作業ツリーの片付けをやり直します。`unarchive` しても、作業ツリーは元に戻りません。
  準備の途中で失敗した実行（`pnpm install` の失敗など）は準備の記録がないので、
  git の登録から `runs/<runId>/work` と、そこにチェックアウトしたブランチを探して
  片付けます。消すブランチは、準備の工程がその実行に付ける名前のものだけです。人が
  切り替えた別のブランチは残します。登録もディレクトリもなければ、何もせず、警告も
  出しません。
- `git worktree remove` には 10 分の上限があります。依存パッケージを入れた大きな
  作業ツリーは、消すのに数分かかることがあるためです。上限で止まったときは、作業ツリーが
  一部だけ消えて残ることがあり、警告がそのパスと一緒にそう伝えます。消せなかったときは、
  git がまだそのディレクトリを作業ツリーとして登録しているかを確かめ、警告に書きます。
  登録が残っていれば、`demo prune --apply` で続きを消せます。残っていなければ、git は
  そのディレクトリを作業ツリーとして扱えず、ほかの方法では消さないので、手で消すように
  書きます。準備をやり直す前に前回の作業ツリーを消すときも同じ上限で、取り消しや
  リースを失ったときはそこで止めます。アーカイブ、片付け（`demo prune`）、納品後、
  新しいテストの試し実行のベースの片付けは、取り消しのあとにも実行する必要があるので、
  止めずに上限まで待ちます。web UI は書き込みを 1 つずつ処理するので、片付けの
  あいだは、ほかの操作が待ちます。
- アーカイブの印を付けた時点で応答を返し、作業ツリーを後で消す、という形はとって
  いません。消せなかったことを応答で伝えられなくなり、CLI と web UI が同じ関数から
  同じ結果を受け取れなくなるためです。
- ブランチは残します。`--delete-branch` を付けたときだけ、その実行が記録した
  factory のブランチ（イシュー付きの実行は `factory/issue-<番号>-<runId>`）と
  `factory/<runId>-squashed` を消します。
- `--series` は、指定した実行が属するタスク（最初の実行と、その下の修正の実行すべて）の、
  止まった実行をまとめてアーカイブします。タスクのどの実行の ID を渡してもかまいません。
  `--series` を繰り返すと、複数のタスクを順にアーカイブし、1 つが失敗しても残りは続けます。
  `unarchive` も、`--run` を繰り返すと、複数の実行をまとめて戻します。
  `status` の `stops:` の行は、最初の実行の ID でこのコマンドを出します。
- `--series` がアーカイブするのは、止まった実行だけです。判断待ち、実行中、承認と納品まで
  済んだ実行はそのまま残し、エラーにもしません。納品済みの実行の ID を渡しても、
  同じタスクの止まった実行をアーカイブします。
- 納品済みのタスクでも、止まった実行は自動では解決済みになりません。アーカイブは
  「人が確認を終えた」という合図で、作業ツリーの片付けもこの合図で行うためです。
- `--series` は、すでにアーカイブした止まった実行にも、片付けをやり直します。
  `--delete-branch` を付けると、対象の各実行のブランチを、`--run` と同じ規則で消します。
  警告は、実行の ID を先頭に付けて表示します。
- `--series` で一部の実行のアーカイブに失敗しても、残りの実行は続けてアーカイブします。
  最後に、失敗した実行を ID 付きで表示し、0 以外の終了コードで終わります。
- `--run` と `--series` は同時に指定できません。どちらもなければエラーです。
- `status` と web UI は、同じファイルを同じ関数（`groupTasks`）で読むので、
  どちらでアーカイブしても、両方から外れます。

### 終わった実行の作業ツリーを片付ける

リポジトリが対象の実行の作業ツリー（`runs/<runId>/work`）は、次のときに片付けます。
片付けるのは、作業ツリー、レビュー用のスナップショット（`runs/<runId>/review-snapshots`）、
`testProbe` のベースの作業ツリー（`runs/<runId>/base-work`）だけです。

- 承認して納品した実行は、納品の記録を `step` に残した直後に、自分の作業ツリーを
  片付けます。納品のあとで直すときは、記録したコミットとブランチから新しい実行を
  作るので（`demo repair`）、元の作業ツリーは要りません。
- 止まった実行をアーカイブしたとき（上の「止まった実行をアーカイブする」）。
- `demo prune --apply` を打ったとき。この変更より前に終わった実行の作業ツリーを、
  まとめて片付けるためのものです。

```bash
pnpm --filter example-local-agent-loop demo prune                      # 対象と容量を表示するだけ
pnpm --filter example-local-agent-loop demo prune --apply              # worktree を片付ける
pnpm --filter example-local-agent-loop demo prune --delete-branches    # 消すブランチも表示する
pnpm --filter example-local-agent-loop demo prune --delete-branches --apply
```

- 削除は `git worktree remove --force` で行い、続けて `git worktree prune` で
  git の登録も消します。git が削除を断ったときは、ディレクトリをほかの方法で
  消さずに残し、警告にします。
- 納品のあとの片付けに失敗しても、実行は承認・納品済みとして終わります。失敗の理由は
  実行の出力の `worktreeCleanupWarning` に残り、`status`、レポート、web UI の
  詳細画面に出ます。`demo prune --apply` でやり直せます。
- `demo prune` の対象は、終わった、リポジトリが対象の実行のうち、承認して納品したもの
  か、アーカイブしたもので、作業ツリーがまだ残っているものです。保存した実行、準備、
  納品の記録、アーカイブのファイルから決め、ディレクトリの名前だけからは決めません。
  `--apply` なしでは、対象の実行の ID、作業ツリーごとの容量、合計を表示するだけで、
  何も消しません。同じコマンドをもう一度打っても、片付けが済んでいれば、何もせずに
  成功します。
- `pending`、`leased`、`waiting` の実行は、アーカイブのファイルがあっても片付けません。
  アーカイブしていない止まった実行、却下した実行、納品せずに完了した実行も
  対象外です。止まった実行の作業ツリーは、人が原因を調べる材料だからです。
- ブランチは、通常の片付けでは消しません。`demo prune --delete-branches --apply` は、
  アーカイブした実行が記録した factory のブランチと `factory/<runId>-squashed`
  だけを消します。作業ツリーが残っているかどうかは問いません。`--apply` なしでは、
  消す予定のブランチを表示します。納品した実行のブランチは消しません。納品物で
  あり、`demo repair` の起点だからです。
- 片付けたあとも、仕様、検証のログ、エージェントの出力、レポート、チェックポイント、
  候補の差分、納品の記録（パッチと `delivery`）は、そのまま読めます。レポートと
  web UI は、片付けた作業ツリーのパスを作業場所として案内せず、「作業ツリーは
  片付け済み」と表示します。
- 実行全体、リモートのブランチ、プルリクエストは消しません。この方針は
  [ADR-0028](../../docs/adr/0028-local-agent-loop-worktree-retention.md) に
  まとめています。

### ブラウザで見る（web UI）

ワーカーを動かしたまま、別のターミナルで web UI を起動できます。一覧と詳細を
見るほか、承認、却下、仕様の判断、再実行、アーカイブを画面から行えます。

```bash
pnpm --filter example-local-agent-loop demo ui             # http://127.0.0.1:4380/
pnpm --filter example-local-agent-loop demo ui --port 4500
```

- 表示された URL をブラウザで開きます。待ち受けるのは `127.0.0.1` だけで、外には
  公開しません。`--port` は 1〜65535 の整数だけを受け付けます。
- 前もってビルドする必要はありません。画面は、要求されたときに Vite が変換して
  配信します。`pnpm --filter example-local-agent-loop build:ui` は、静的なファイルを
  ビルドできるかを確かめるためのものです。
- UI は、固定した状態のルートの DB を、CLI と同じ接続で開きます。DB がまだなければ
  空の画面を出し、DB は作りません。ワーカーか `trigger` が DB を作ると、次の更新
  から表示されます。画面を読むだけでは、何も書き込みません。
- UI はワーカーを起動せず、ワーカーのロックも取りません。承認や再実行のあとで
  実行を進めるのは、別に動かしているワーカーです。
- 画面は 3 秒ごとに読み直します。前の読み込みが終わるまで、次は始めません。
  読み込みに失敗したときは直前の表示を残し、上部に「更新失敗」と表示します。
- 画面の操作は、CLI の `approve`、`reject`、`spec-revise`、`retrigger`
  （`--reload-config` なし）、`archive`、`unarchive` と同じ関数（`src/actions.ts`）を
  呼びます。確かめる内容も結果も CLI と同じです。承認と却下は、実行がいま待っている
  待ちにだけ、候補か仕様の版に結びつけて送ります。別の実行の待ち、判断済みの
  待ち、種類の違う待ちには送りません。再実行は保存済みの入力だけを使い、CLI が
  再実行を断る停止には、画面からも実行しません。`factory.json` の読み直しは、CLI だけの
  操作です。
- どの操作にも、同じ操作の CLI コマンドを添えます。操作ボタンの下の、閉じた
  「同じ操作の CLI コマンド」を開くと、レポートや状態の確認を含む次のコマンドの
  「〜をコピー」ボタンと全文が出ます。却下とアーカイブは控えめなボタンで、押すと
  確認を挟みます。再実行も費用のかかる新しい実行を始めるので、保存済みの入力で
  新しい実行を始めると伝える確認を挟みます。承認も確認を挟み、その確認には、レビューの
  回数、最後の回の結果、直した指摘と残した指摘の件数と題名を出します。確認の中には、
  その操作のコマンドを 1 行とコピーボタンで出し、確認のあいだは同じ行のほかの操作を
  隠します。仕様の修正では、画面に書いたメモをそのまま送ります。CLI では、同じメモを
  書いたファイルを `--notes-file` に渡します。
- 操作の結果は画面の上部に知らせとして出し、一覧は次の更新で変わります。断られたときは、
  CLI と同じ英語のメッセージを知らせに出します。
- 書き込みの API は `POST /api/runs/<id>/<action>` だけです。サーバーは起動の
  たびにランダムなトークンを作ってページに埋め込み、書き込みには
  `x-loop-ui-token` ヘッダーのトークンと、このサーバー自身を指す `Origin`
  ヘッダーを求めます。Host、トークン、Origin のどれかが違えば 403、POST 以外は
  405 で、操作の関数を呼ぶ前に断ります。実行の ID の書き方が壊れたパスは 400 です。
  トークンはログに出さず、cookie も使いません。ページは CORS を許さないので、
  localhost のほかのポートのページからもトークンは読めません。読み取りの API は GET と HEAD だけです。
- ログの読み取りは `GET /api/runs/<id>/logs/<attemptId>?from=<バイト位置>` です。
  既定はその試行のエージェントの出力で、`&file=stdout` と `&file=stderr` で、検証の
  標準出力と標準エラー出力を読みます。応答は `{ chunk, nextOffset, done }` で、1 回に
  読むのは 64 KiB までです。`from` は省略すると 0 で、0 以上の整数だけを受け付け、
  ほかの値は 400 です。UTF-8 の文字の途中で切れた末尾は返さず、次の読み取りに
  回します。`nextOffset` は、返したバイト数だけ進みます。`done` は、試行が終わって
  ファイルの最後まで読んだときに `true` になります。試行は実行の ID と合わせて DB で
  探し、ファイルの場所は試行が記録したパスだけを使います。リクエストでパスは
  指定できません。知らない試行や、そのログを記録していない試行は 404、記録した
  パスが実行のディレクトリの外にあるか、リンクをたどると外に出るときは 403、
  記録したファイルが消えているときは 410 です。ほかの読み取りと同じ Host の制限が
  かかり、トークンは要りません。
- 操作のない行では、次のコマンドを「〜をコピー」ボタンで出し、全文は
  「コマンド全文」を開くと見られます。表示にもコピーにも、
  CLI が付ける英語の `# ...` の補足は含めません。補足は、ボタンにマウスを重ねると
  日本語で出ます。
- `http://127.0.0.1:4380/#/design` は、画面の部品と状態を、固定の見本データで並べた
  ページです。DB も API も使わないので、ワーカーや DB がなくても開けます。

実行は、保存済みの入力から付けた名前で並びます。イシューから作った実行は
`#番号 タイトル`、`--task` / `--task-file` の実行はタスクの最初の行（80 文字まで）、
同梱の題材は「同梱題材: calc の add を直す」です。一覧には実行の ID を出さず、
完全な ID は実行の詳細と、コピーしたコマンドにあります。作成時刻は「3分前」のような
相対的な表し方で、正確な時刻はマウスを重ねると出ます。

各行と実行の詳細には、その実行のリポジトリ名を、名前の横に出します。名前は
`factory.json` の `name`（`trigger` のときに入力の `target.name` に保存したもの）です。
同じリポジトリの実行のうち、名前を持ついちばん新しい実行のものを使うので、`name` を
書く前の実行も同じ名前で出ます。どの実行にもなければ、保存済みの入力の
`target.repoPath` のディレクトリ名です。同じ名前のリポジトリがほかにあるときや、
「すべて」「同梱題材」「不明」と同じ名前のときだけ、見分けられるところまで親の
ディレクトリを前に付けます（`a/public` と `b/public` など）。それでも見分けられない
ときは、パスで出します。修正の実行は、修正元の最初の実行のリポジトリに
数えます。同梱の題材の実行は「同梱題材」です。完全なパスは、実行の詳細と、切り替えの
リポジトリ名にマウスを重ねると出ます。

実行のリポジトリが 2 つ以上あるときは、タスク一覧と集計の上に「リポジトリ」の
切り替えが出ます。既定は「すべて」です。リポジトリを選ぶと、一覧の各節、件数の
並び、止まったものの「すべて選ぶ」、集計（週ごとの推移と設定ごとの比較）が、
そのリポジトリのタスクと実行だけになります。選んだリポジトリは
`#/?repo=<パス>`、`#/compare?repo=<パス>` のように URL に残るので、読み込み直しても
変わりません。一覧と集計のあいだを移っても、実行の詳細（その URL にも残ります）から
一覧へ戻っても、選んだままです。
API も同じで、`/api/runs`、`/api/trend`、`/api/compare` に `?repo=<パス>` を付けると、
そのリポジトリだけを返します。どの実行にもないパスは「すべて」として扱います（画面の
URL からも外します）。リポジトリは、保存された `--repo` のパスを git のトップレベルに
直して見分けるので、末尾の `/` や、リポジトリの中のディレクトリを渡した実行も、同じ
リポジトリに数えます。git が答えられないとき（リポジトリが消えたときなど）は、パスを
そのまま正規化して使い、ほかの実行のリポジトリのパスの下にあれば、いちばん近い
そのリポジトリに数えます。git には画面の応答を止めない形で問い合わせ、答えたパスは
覚えておきます。答えられなかったパスは、1 分たってから問い合わせ直します。
リポジトリが 1 つだけのときは、切り替えを出しません。

**タスク一覧**はタスクごとに 1 行で、先頭の件数の並びと 4 つの節に分かれます。並びと
区分は、`demo status` と同じ関数（`groupTasks`）で決めます。行の末尾には、実行が
2 件以上あるときの件数、所要時間、費用、代表の実行の作成時刻を、列をそろえて
出します。所要時間と費用は、終わったタスクか、実行が 2 件以上あるタスクだけに出し、
2 件以上なら全部の実行の合計です（マウスを重ねると、合計であることが出ます）。どれかの実行の
値が不明なら「不明」です（`demo status` の `total` と同じ値）。

- **件数の並び**：「判断待ち」「動いているもの」「止まったもの」「終わった」の件数です。
  押すと、その節へ移ります。0 件には色を付けません。「動いているもの」は、実行中の
  ものがあるときだけ青にします。判断待ちも止まったものもなければ、「人の手が要る
  ものはありません」と出します。
- **判断待ち**：承認、仕様の判断、承認以外の入力を待つタスク。行は開いた状態で、
  理由、工程の並び、その実行にできる操作と、同じ操作の CLI コマンドを出します。
  コマンドの補足は、ボタンにマウスを重ねると出ます。
- **動いているもの**：実行中（期限内のリース）、ワーカー停止中（リースが切れて
  ワーカーが止まった。ワーカーを起動すれば再開）、順番待ち、判断済み・再開待ちのタスク。
  行は開いた状態で、実行中なら、名前の下にいまの工程と経過時間を出します。
- **止まったもの**：未解決の停止（検証の失敗、レビューの上限、未確定の外部の呼び出しなど）の
  タスク。新しいものから 5 件だけを出し、残りは「さらに N 件表示」で出します。節の件数は、すべてを数えます。
  各行のチェックボックスか、節の「すべて選ぶ」でタスクを選ぶと、画面の下に操作バーが出ます。
  「すべて選ぶ」は、まだ表示していない行も含めて、節の全件を選びます。「N 件をアーカイブ」は、
  選んだタスクの名前と `demo archive --series <id> --series <id> …` を並べて確認してから、
  タスクごとに `archive --series` と同じ関数で、1 件ずつ順に、止まった実行をアーカイブします。
  進むあいだは、知らせに「N 件中 M 件」を出し、1 件終わるごとに更新します。まとめての操作は
  それぞれ自分の知らせを持ち、途中で別の操作をしても、その知らせは上書きされません。終わると、件数と、
  作業ツリーやブランチを片付けられなかったタスクと git の理由、できなかったタスクとその理由を
  知らせ、「まとめて戻す」で、いまアーカイブした実行を戻せます。一部の実行だけをアーカイブできた
  タスクも、アーカイブした実行は戻せ、警告も出します。行は閉じた状態で、状態のバッジと名前だけを 1 行で出します。開くと、止まった
  理由、工程の並び、再実行できるか、操作とコマンド、各実行が出ます。同じタスクに、
  動いている実行か、判断を待つ実行がほかにあるとき（再実行した修正など）は、行を
  開いた状態で出し、各実行の状態が開かなくても見えるようにします。前に止まった実行が
  残っているだけでは開きません。表示のあとでそうなったときも、3 秒ごとの読み直しで
  開き、そうした実行がなくなれば、また閉じます。自分で開け閉めした行は、タスクが同じ節にあるあいだは、その状態を保ちます。別の
  節へ移ったとき、実行の詳細を開いてから一覧へ戻ったとき、ページを読み込み直した
  ときは、その節の既定の状態に戻ります。後の修正の実行の承認で解決した停止と、アーカイブした停止は
  出ません。
- **終わったタスク**：新しい順に 30 件ずつ出し、「さらに表示」で次を出します。
  アーカイブしたタスクは既定で隠し、「アーカイブ済みも表示」で出します。タスク名で
  絞り込めます。どちらも表示だけの切り替えで、タスクや数値は変えません。節の件数は
  全件で、隠したり絞り込んだりしているときは、「144 件中 104 件」のように添えます。
  行の名前は代表の実行の詳細へのリンクで、左の矢印で開くと、工程の並びと、実行が
  複数あるタスクでは、「最初の実行」「指摘からの修正 1」…のように各実行と、その
  所要時間と費用を出します。後の修正で解決した実行には「後の修正で解決」と添えます。
  アーカイブしたタスクには「アーカイブ済み」と添え、状態は色を付けずに出します。
  開くと、止まった理由と「アーカイブから戻す」が出ます。最初の実行が fake プロバイダーで
  動いたタスクも、隠さずに並べ、「模擬」と添えます。修正の実行が実際のプロバイダーでも、
  最初の実行で決まります（`demo status --format json` のタスクの `fake`）。

状態は、1 つの実行につき 1 つだけ出します。動いている実行はいまの状態（承認待ち、
実行中など）、終わった実行は結果（承認済み、検証失敗など）です。
状態の名前は必ず文字で出し、色は「人待ち（琥珀）」「失敗（赤）」「実行中（青）」だけに
付けます。状態の区分と次のコマンドは、`demo status` と同じ関数（`src/engine/status.ts`）から
作るので、同じ時点の `demo status --run <id>` と一致します。説明文は、区分と停止の種類から
画面用の日本語で出し、CLI の英語の理由（reason）は表示しません。未確定の外部の呼び出しで
止まった実行には、再実行を促すコマンドを出しません。プロバイダーに呼び出しを
断られて止まった実行には、拒否の理由を停止の理由の欄に出し、設定を読み直す再実行と、
通常の再実行のコマンドを、コピーできる形で出します。工程の並びでは、通った工程に ✓ を
付けます。承認待ちを作らずに完了まで進んだ実行（`--approve auto`）の承認は、
「✓ 承認 自動」と出します。

実行中の実行の「全体 … 経過」は実行の開始（リースを取ったとき、まだなら作ったとき）から、
「この工程 … 経過」はいまの工程の試行の開始から、画面を読んだ時点までの暫定の値です。
レポートの確定した値（所要時間、工程ごとの時間）とは別に扱い、確定した値には混ぜません。

**実行の詳細**は、`demo report --run <id> --format json` と同じ値を、上から読んで
途中でやめても要点が分かる順に並べます。

名前の下には、同じタスクの実行を「最初の実行」「指摘からの修正 N」として、
状態と開始時刻と一緒に並べ、表示している実行に「表示中」と添えます。

1. **いまの状況**：停止や判断待ちの理由、人が確かめること、再実行できるか、
   その実行にできる操作と、同じ操作の CLI コマンド。主な操作（承認、仕様を直す、
   再実行）だけを強いボタンで出します。人が確かめることとしてログファイルを読むよう求める停止では、その
   すぐ下に、チェックのログのパスをコピーできる形で出します。ファイルがなければ
   「ファイルがありません」、記録にパスがなければ、そう書きます。承認・納品済みの
   実行では、納品したブランチをコピーできる形で出します。
   その下に、所要時間、工程の作業時間、人の待ち時間、費用、合計のトークン、
   修正とレビューの回数を 1 行で並べ、作業時間が所要時間より長いときは、理由を
   1 行添えます。停止の記録（終了コードなど）は、「停止の記録を見る」を開くと出ます。
2. **レビューの要点**：レポートの `reviewHighlights` です。最後より前のレビューで
   出た、直すべき指摘を、最後のレビューが通過したときは「直した指摘」、そうでなければ
   「これまでの指摘」として、最後のレビューの助言を「残した指摘」として、件数と題名を
   出します。採点値のある指摘には、題名の横に頻度と深刻さを添えます。最後のレビューが通過したと言えるのは、両方のレビュアーの判定がそろい、
   どちらも通過したときだけです。通らなかった実行では、そこで出た直すべき指摘を
   「残っている直すべき指摘」として別に出し、判定がそろっていない回はそう書きます。
   指摘を、回をまたいで突き合わせることはしません。見出しの件数は、レポートと同じ指摘の
   数です。判定だけを返すレビュー（verdict）は、回、観点、判定だけを題名の下に出し
   （直した側では「〜が求めた修正」）、件数には数えません。最後のレビューで通過した
   verdict のレビューは何も残していないので、「残した指摘」ではなく、最後のレビューの結果の
   下に出します。メモの本文は、記録の詳細の節で読みます。
3. **工程の時系列**と**工程ごとの時間と費用**：工程ごとに、作業時間（呼び出しの時間の
   合計）、所要時間（時計の時間）、費用を 1 行で並べます。費用の「–」はモデルを
   呼ばなかった工程、「不明」は値の分からない呼び出しを含む工程です。終わった実行の
   時系列は全部の行を出し、動いている実行だけが枠の中でスクロールします。レビューのように並んで動いた
   工程は、作業時間を重ねて数えるので、作業時間の合計が所要時間を超えることが
   あります。仕様の工程がある実行には、「仕様の工程まとめ」として、仕様の作成、
   仕様レビュー、採点コマンドの決定を合わせた経過時間（レポートの `specWallMs`）を
   出します。並んだレビューは一度だけ数え、人の判断を待った時間は含みません。
4. **記録の詳細**（最初は閉じています）：仕様、レビューの全部の回の判定とメモ（メモは
   開くと出ます）、工程別・役割別のトークンと費用、見立てと較正の材料、候補と候補ごとの
   変更の規模、納品物、入力ファイルの SHA-256、注記。

工程の時系列で行を選ぶと、実装の行には封印した候補の規模を、レビューの行には
その回の判定とメモを、検証の行には終了コードと検証のログのパスを出します。
パスは「〜のパスをコピー」ボタンでコピーできます。

エージェントを呼んだ行を選ぶと、その呼び出しの出力を「エージェントの出力」に
出します。検証の行では、標準出力と標準エラー出力を切り替えて読めます。出すのは
その行の最後の試行のログで、やり直した工程では、試行の行を開くと、その試行の
ログを読めます。

- 書き込み中のログは 3 秒ごとに続きを読み、「書き込み中」の印を付けます。
  前の読み込みが終わるまで、次は始めません。試行が終わって最後まで読むと、
  「書き終わり」と出し、読み直しを止めます。
- 終わったログも、先頭から順に読みます。画面に残すのは末尾の 256 KiB までで、
  それより長いログは末尾だけを出します。全文は、ファイルのパスをコピーして、
  エディタや `less` で開いてください。
- 本文は文字としてそのまま出し、Markdown や HTML として解釈しません。端末の色などの
  エスケープは取り除きます。
- 本文の末尾を見ているあいだは、追記に合わせて下へ送ります。上へスクロールすると、
  その位置で止まります。
- 記録したファイルが消えていれば、そのことを出します。

承認待ちの実行では、レビューの判定とメモは承認待ちのメタデータから、候補は
保存済みの候補の `step` から読みます（レポートの `reviews` と `candidate` にも
同じ値が入ります）。

**集計**は、2 つの見方を切り替えます。開いたときは「週ごとの推移」です。ほかの画面へ
移って戻っても、ページを読み直すまでは、最後に選んだ見方のままです。

- **週ごとの推移**：`demo compare --trend --format json` と同じ値です（リポジトリで
  絞ったときは、そのリポジトリのタスクだけで数えます）。実行ではなく
  タスクを数えます。最後の実行が直近 30 日に終わったタスクを、最初の実行の実装に
  使ったモデルと推論量の組ごとにまとめます。まとまりごとに、まず期間全体の初回の承認率、
  最終の承認率、タスクあたりの所要時間と費用の中央値を出し、その横に、週（月曜始まり、
  この PC の時刻）ごとのタスク数、初回の承認、最終の承認、所要時間、費用、修正の実行の数の
  中央値を並べます。タスクが 1 件だけの週には「1 件のみ」と添えます。最初の実行が
  模擬（fake プロバイダー）のタスクは除き、期間に終わったタスクが模擬だけのときは、除いた
  件数をそう書きます。CLI の版はまとまりに含めないので、同じモデルの新しい版は同じ表に
  並びます。数え方は、CLI の節の `--trend` と同じです。
- **設定ごとの比較**：終わった実行を `demo compare --runs` と同じ処理にかけ、
  設定の版（config version）ごとのまとまりを、閉じた状態で並べます。見出しに件数と成功率が出て、
  開くと、所要時間・作業時間・費用などの中央値、最小、最大、件数、不明の数、工程別の
  値、見立て（事前判定の判定）別の結果と停止の理由の件数、判定別の較正の材料の中央値を
  表示します。

表示した値の読み方：

- 費用は、記録したトークン数を API の料金で換算した参考の値です。サブスクリプションの
  請求額ではありません。
- 使用量や価格が分からないものは、web UI では「不明」、CLI の Markdown（`report`、
  `compare`）では `unknown` と表示し、0 とは表示しません。一部の
  呼び出しだけ分かっている値と、一部の試行だけ計測できた工程の時間には、「一部」を
  付けます。
- 集計の統計は不明な値を除いて計算し、除いた数を「不明」の列に出します。

### デモデータ

実際の使い方に近い実行を並べて web UI を見たいときは、`demo seed` を使います。
実際の LLM は呼ばず、すべて fake プロバイダーで動きます。

```bash
pnpm --filter example-local-agent-loop demo seed
pnpm --filter example-local-agent-loop demo seed --home ~/tmp/factory-demo --latency 3000-15000
```

- 使い捨ての HOME を OS の一時ディレクトリに作り、その場所を表示します。
  `--home` には、空のディレクトリか、まだないパスを渡します。普段の
  `~/.local/state/local-agent-loop/` には触れません。
- その HOME に、小さな JS プロジェクトの git リポジトリと `factory.json` を作り、
  日本語のタスクで、リポジトリが対象の実行を 13 本起動します。承認された 1 本には、外部の
  指摘からの修正の実行を 1 本足します。固定したテストは、本物の `node --test` です。
- `factory.json` の各役割には、実際に使いそうなモデルを書いています。実装と
  正しさのレビュー（correctness）は `gpt-6-sol`、境界条件のレビュー（edge-cases）は
  `claude-opus-5-5`、事前判定は `gpt-6-luna` です。プロバイダーは fake なので、
  これらは指定したモデル（requested model）として記録され、トークン数と費用は
  そのモデルの価格で計算します。実行は fake と表示され、実際の LLM での検証には
  数えません。
- 結論は一通りそろいます。修正 1 回で承認、初回で承認、レビューの上限、検証の失敗、
  未確定の呼び出し、承認待ち 2 本、却下、事前判定の `routine` と `probe` です。
- `--latency` は 1 回の呼び出しにかかる時間の範囲で、既定は `20000-90000` ミリ秒
  です。`demo seed` はこれらの実行を同時に進め、承認と却下を
  `demo approve` / `demo reject` と同じ処理で送り、落ち着くまで待ちます。
- 最後の 2 本は、1 回の呼び出しに 10〜20 分かかる設定で、バックグラウンドの
  ワーカーに渡します。`demo seed` が終わった時点で、1 本は実行中、もう 1 本は
  ワーカー待ちです。ワーカーの pid とログの場所を表示します。
- 作成時刻は、実際に `demo seed` を動かした時刻です。時刻は Durably が記録し、
  `demo seed` は DB を書き換えないので、数日分の履歴には見えません。

最後に、画面を開くコマンドと、ワーカーを止めたあとで続きを動かすコマンドを
表示します。

```bash
HOME=<表示された場所> pnpm --filter example-local-agent-loop demo ui
HOME=<表示された場所> pnpm --filter example-local-agent-loop demo worker
```

## 実リポジトリに対して動かす

同梱の題材ではなく、実際のリポジトリの作業を渡す場合です。リポジトリごとに変わらない
設定は、対象リポジトリ直下の `factory.json` で管理します。

```json
{
  "name": "myapp",
  "check": ["pnpm", "validate"],
  "setup": ["pnpm", "install", "--frozen-lockfile"],
  "base": "main",
  "baselineCheck": true,
  "checkTimeoutMs": 900000,
  "agentTimeoutMs": 7200000,
  "agentIdleTimeoutMs": 900000,
  "commit": {
    "authorName": "Factory Bot",
    "authorEmail": "factory-bot@example.com"
  },
  "profiles": {
    "code": { "provider": "codex", "model": "gpt-5.6-sol", "effort": "medium" },
    "review": {
      "correctness": { "provider": "codex", "model": "gpt-5.6-terra" },
      "edge-cases": { "provider": "claude", "model": "claude-sonnet-5" }
    }
  }
}
```

これがあれば、作業内容を書いたファイルを渡すだけで起動できます。

```bash
pnpm --filter example-local-agent-loop demo trigger \
  --repo ~/progs/myapp --task-file ~/work/task.md \
  [--spec-file ~/work/spec.md] [--dispositions-file ~/work/dispositions.md] \
  [--context-file ~/work/decisions.md]
```

- `--repo` のリポジトリから `git worktree` を切り、その中だけで作業します。
  あなたが開いているcheckoutは一切動きません。
- 作業内容は `--task-file`、`--task "..."`、`--issue 234` のどれか一つで渡します。
  `--issue` は `gh issue view` で本文を取ります。
- `--spec-file` は実装とレビュー二つの全員に、`--dispositions-file`（過去の
  レビュー指摘をどう扱ったか）はレビューだけに渡ります。どれも中身を解釈しない
  UTF-8テキストで、1ファイル256 KiBまでです。promptでは「信頼しないデータ」として区切った区画に入り、
  factoryの指示や出力形式とは混ざりません。
- `--context-file` は、ownerが確定した決定やテストの結果など、**信頼できる情報**を
  渡すファイルです。UTF-8の空でないテキストで、32 KiB（32,768バイト）までです。
  超えるもの、空のもの、UTF-8として読めないものはrunを作る前に拒否します。
  実装と修正のpromptには、TASKやFINDINGSとは別の信頼できる区画として入り、
  「ownerが確定した決定に反する変更をしない。反すると判断したら変更せず、
  返答のNOTESで理由を述べる」と指示します。両レビューには、factoryが作る
  TRUSTED CONTEXTの中に入ります。`--dispositions-file` はこれまでどおり
  レビューだけに渡る信頼しないデータで、contextに格上げはしません。
- 実装と修正の返答は、変更したファイルの短い要約に続けて、わざと直さなかった
  指摘や変更があるときだけ `NOTES:` の節で、どれをなぜ直さなかったかを書きます。
  節が無い返答も、空の節も、`none` や `特にありません` だけの節も、これまでどおり
  有効です。節は、プロンプトのとおり大文字で `NOTES` と書いた、字下げのない最初の
  行から始まります。`NOTES:` だけの行も、`## NOTES` や `**NOTES:**` のような見出しも
  含みます。そういう行が無いときは `notes:` のような `NOTES:` だけの行から、それも
  無いときは `## Notes` のような最初の見出しから読みます。`## Notes` で始めた節の
  本文に字下げのない `NOTES:` の行があると、その行から読みます。
  factoryは決着した返答から一度だけ読み取り（UTF-8で4 KiBまで）、候補のstepに
  保存します。replayは保存した
  ものを読み、返答を読み直しません。その候補の両レビューには、TRUSTED CONTEXTの
  後ろに「信頼しないデータ」の `REPAIR_NOTES` 区画として渡し、理由を候補、タスク、
  仕様、確定事項と照らして判断すること、理由が書いてあるだけでは指摘は片付かない
  ことを指示します。factoryのコピーもstageの結果と同じ場所に置き、読めるファイルと
  command形式の `CLAUDE.local.md` に載せます。TRUSTED CONTEXTにも
  DISPOSITIONSにも入れません。次の実装か修正が終わると、その返答の分に置き換わります。
  コピーは新しい候補をsealした時点で消え、次のレビューの回で新しい候補の分が
  書かれます。
  reportの `implementerNotes[]`、Markdownのreport、run詳細に、回と役割ごとに出ます。
- `check` は**エージェントが走り出す前に固定される採点コマンド**です。argvとして
  そのまま実行するのでshellではありません。configにもフラグにも無ければ起動しません。
  何を直せば通るのかが決まっていない依頼は、そもそもファクトリーに向きません。
- `setup` は新しいworktreeに依存をインストールするためのものです。省略すると
  installなしで `check` が走ります。`base` の既定は `HEAD` です。
- `name` は web UI に出すリポジトリ名です（空でない文字列）。省略すると
  ディレクトリ名を出します。`trigger` の時点でrun inputの `target.name` に保存するので、
  リポジトリが消えても名前は残ります。表示だけに使い、設定のバージョンには入りません。
- `--check`、`--setup`、`--base` を付けるとconfigの値より優先します。別の場所の
  configは `--config <path>` で選べます。相対パスはCLIプロセスのcwdから解決します。
  `pnpm --filter` はpackageのディレクトリでCLIを動かすので、パスは絶対パスで
  渡してください。
- `profiles` は `code`（実装と、`repair` が無ければ修正も）、`review.correctness`、
  `review.edge-cases` の三役割を別々に指定できます。修正だけを別の設定にする
  `repair` と、事前判定の `triage` は任意です（下の節を参照）。configが省いた役割と、役割の中で省いた項目だけを
  `--provider`、`--model`、`--effort` とpresetで補います（`repair` で省いた項目は
  `code` から補います）。ただし `--provider` と
  違うproviderを指定した役割は `--model` と `--effort` を引き継がず、そのproviderの
  既定presetを使います。明示した役割の値が他の役割やフラグで上書きされることは
  ありません。fakeと実providerを役割ごとに混ぜる
  ことはできません。
- agent呼び出しには二つの時間の上限があります。`agentTimeoutMs` は呼び出しの
  開始からの全体の上限です。`agentIdleTimeoutMs` は無通信の上限で、agentの活動
  （文章、推論、tool呼び出しとその結果、実行中のtoolの進捗）、出力、usageの報告が
  この時間途絶えたら止めます。どれかが届くたびに数え直すので、動き続けている
  呼び出しは無通信の上限を超えても続き、全体の上限で止まります。providerに渡す
  上限はfactoryの全体の上限より遅くしてあり、止めるのは常にfactoryのtimerです。
- timeoutの既定値はターゲットで変わります。実リポジトリはagent呼び出しが全体2時間、
  無通信15分、検査15分。同梱題材は全体5分、無通信5分、検査2分です。`factory.json` の
  `agentTimeoutMs`、`agentIdleTimeoutMs`、`checkTimeoutMs`（ミリ秒）が最優先で、
  無ければ `trigger` を実行したプロセスの `AGENT_TIMEOUT_MS`、`AGENT_IDLE_TIMEOUT_MS`、
  `TEST_TIMEOUT_MS`、それも無ければ既定値を使います。無通信の既定値は全体の上限を
  超えないように、全体の上限に合わせて短くします。どれも2147483647以下の正の整数に限り、`0`、負数、小数、
  `NaN`、`Infinity`、2147483647超は `trigger` の時点で拒否します。これより大きい
  値はNodeのtimerがあふれて約1ミリ秒で発火し、呼び出しを始めた直後に打ち切るからです。
  無通信の上限が全体の上限より長い組み合わせも、作業ツリーを作る前に `trigger` で拒否します。
  解決した値はrun inputに保存し、workerの環境変数は読みません（この変更より前に
  保存されたrunだけは、従来どおりworkerの環境変数を読みます）。修正のrunは親が
  保存した値を引き継ぎ、`retrigger --reload-config` だけが `factory.json` から読み直します。
  reportは解決した全体と無通信の上限を表示します。
- 実装や修正の呼び出しをfactoryが時間の上限で止めたときは、その呼び出しを始めた
  時点の候補（最初の実装ならbase）から作業ツリーに変更があるかを見ます。変更が
  あれば、終わった呼び出しと同じ手順でcommitして候補にし、通常どおり検証します。
  検証に落ちれば、修正の回数を1つ使って次の修正へ進みます。次の修正には、前の
  呼び出しが時間の上限で止まり、その途中の作業が今の候補だと伝えます。report、
  traceは、その候補が時間切れの呼び出しから作られたことを表示します。変更が
  無ければ候補を作らず `agent-timeout` で止まります。
- 反復ごとにcommitして封印します。検証・レビュー・成果物は同じcommitを見ます。
- 既定の成果物は `~/.local/state/local-agent-loop/runs/<runId>/delivery/<candidate>.patch`
  です。patchはbase commitと最後のcandidateの差分です。issueなしのrunのbranchは
  `factory/<runId>`（issue付きは `factory/issue-<番号>-<runId>`）で、反復ごとの
  commitと承認されたcommitはこのbranchに残ります。`status` とreportがbranch名と
  commit SHAを表示します。承認されず成果物が無いrun（却下、検証失敗、レビュー上限）
  でも、最後に封印したcandidateのbranchとcommitを `candidate` として表示します。
- 承認されて成果物を作るときは、もう一つ `factory/<runId>-squashed` を作ります
  （issue付きのrunも同じ名前です）。記録したbase commitを唯一の親とし、最後の
  candidateと同じtreeを持つcommitが1つだけ乗ったbranchです。candidateがbaseと
  同じtreeでも空のcommitを1つ作るので、baseからのcommit数は常に1です。refだけで
  作るので、元のbranch、worktree、あなたのcheckoutは動きません。成果物を作る
  stepが途中で止まって再実行されたときは、まず `git commit-tree` で期待する
  commitを組み立て、既にあるこのbranchがそのcommitを指しているときだけ使い回します。
  author、message、親、treeのすべてが一致している必要があります。それ以外の
  branchは拒否し、手を付けずに残します。承認されなかったrunには作りません。
  branch名とcommit SHAは `delivery.squashedBranch` と `delivery.squashedCommit`
  に記録し、`status --run` のJSONとreportのJSON・Markdownに出ます。web UIの
  納品物はbranch名だけ表示します。この記録が無い以前のrunでは `null` です。
- `--publish` を付けると反復履歴のあるbranchをpushしてDraft PRを作ります。
  `commit.publishSquashed` が `true` のときだけ、代わりにsquash branchをpushして
  Draft PRのheadにします。どちらの場合も、同じheadで開いているPRが既にあれば
  （PR作成後に記録前で止まったstepの再実行など）新しく作らずにそれを使います。
  `delivery.location` は実際に公開したbranchのPRのURLです。

`--publish` を付けない限り、外向きの操作は起きません。まずpatchで確かめてから
PRに進むのが安全です。

人間の承認待ちは、実リポジトリでは既定で入りません。Draft PR自体が人間の
レビュー対象で、マージするのも人間だからです。`--approve manual` で
同梱題材と同じ承認waitを挟めます。

### commitの作者とメッセージ（commit）

`factory.json` の `commit` で、factoryが作るcommitの作者とメッセージを決められます。
どの項目も省略でき、文字列は空（空白だけも含む）を `trigger` の時点で拒否します。

```json
{
  "commit": {
    "authorName": "Factory Bot",
    "authorEmail": "factory-bot@example.com",
    "messageTemplate": "fix: {task} (factory {runId}, iteration {iteration})",
    "publishSquashed": true
  }
}
```

- `authorName` と `authorEmail` は反復commitとsquash commitの作者とcommitterに
  なります。省略した項目は `durably-factory` と `durably-factory@localhost` です。
- `messageTemplate` の `{iteration}`、`{runId}`、`{task}` を置き換えます。
  `{task}` は保存したtaskの1行目、`{iteration}` は反復commitではその反復の番号、
  squash commitでは最後のcandidateを封印した反復の番号です。省略すると反復commitは
  `factory iteration <番号>`、squash commitは `factory run <runId>` です。
- 変更の無い反復では、従来どおり空の反復commitを作りません。
- `publishSquashed` の既定は `false` です。`--publish` が無ければ、この値に
  かかわらずpushもPR作成もしません。
- 設定は `trigger` の時点で解決してrun inputに保存します。trigger後に
  `factory.json` を書き換えても既存のrunは変わらず、`retrigger --reload-config`
  で作ったrunは書き換えた後の値を使います。
- 作者とメッセージテンプレートは反復commitとしてworktreeの履歴に残り、エージェントが
  読めるので `configVersion` に入ります。どちらも省略したrunの版は従来と同じです。
  `publishSquashed` は `--publish` と同じく公開先を選ぶだけなので入りません。

### baseの採点を先に確かめる（baselineCheck）

`factory.json` に `"baselineCheck": true` を書くと、setupが終わった直後、
エージェントを呼ぶ前に、base commitのworktreeで固定した `check` を一度だけ
実行します。既定は `false` で、そのときは実行しません。repo targetだけの設定です。

- baseで `check` が失敗したら `baseline-check-failed` で止まります。エージェント
  呼び出し（triageとpreflightを含む）は0回です。`retry: yes` で、次の手順は
  「採点コマンドか環境（setup、依存、base）を直す」です。
- 終了コードと、stdout・stderrの全文ログのpath（`runs/<id>/baseline-logs/<attempt>/`）
  を `status`、reportのJSON（`baseline`、`failure.details`）とMarkdown
  （「Baseline check」節）、web UIの停止理由に出します。timeoutで打ち切られた
  ときは終了コードを不明（`unknown`）とし、打ち切りまでの時間を出します。
- 検証と同じcheckpointで記録します。完了した結果はworker再開時に読み戻して
  再実行せず、途中で止まった採点はやり直します。中断した試行の部分ログは
  合否の根拠にしません。
- setupや採点がworktreeのtracked fileを書き換えた場合は、最初のcandidateに
  混ざるので `baseline-check-failed` で止め、エラーにその旨を出します。採点
  コマンドが起動できない場合（コマンドが見つからないなど）も同じ分類で止めます。
- setupは、`.gitignore` の対象外の未追跡ファイルを残してはいけません。空の
  ディレクトリも同じです。採点後の片付けで消えてしまうからです。判定には
  片付けと同じ `git clean -ffdn` の結果を使うので、無視されたファイルだけが
  入ったディレクトリは残してかまいません。
  `baselineCheck` がオンのときは、setupの直後、採点の前に確かめます。残って
  いれば採点もエージェント呼び出しもせずに `baseline-check-failed` で止め、
  最初の数件のpathを `failure.details` に出します。次の手順は「setupが
  `.gitignore` にないファイルを作っているので、そのファイルを `.gitignore` に
  入れるか `baselineCheck` を外す」です。ignore対象のファイル（`node_modules`
  など）は残してかまいません。
- 採点が通ったら `git clean -ffd` で、`.gitignore` の対象外の未追跡ファイルを
  入れ子のgitリポジトリも含めてすべて消します。カバレッジやテスト結果の
  ファイルが最初のcandidateに入らないようにするためです。上の前提があるので、
  消えるのは採点が残したものだけです。途中で止まった採点をworker再開時に
  やり直した場合も、前の試行が残したファイルごと消えます。ignore対象の
  ファイルは残ります。消したあとも対象外の未追跡ファイルが残っていれば、
  `baseline-check-failed` で止めます。

### baseの採点結果を使い回す（baselineReuse）

同じリポジトリの同じbase commitから続けてrunを始めると、runごとに数分かかる
baseの採点を繰り返します。`baselineCheck` と一緒に `baselineReuse` を書くと、
条件が同じで期限内の、ほかのrunの成功した結果を使い、採点を省きます。

```json
{
  "baselineCheck": true,
  "baselineReuse": { "maxAgeMs": 3600000 }
}
```

- `maxAgeMs` はミリ秒の正の整数で、上限は7日分のミリ秒です。索引の記録は
  7日より古くなると消えるため、上限もそれに合わせています。0、負の数、
  小数、7日を超える値は `trigger` が拒否します。省略すると使い回しは
  しません。`baselineCheck` がオフのrunでは読みません。
- 使い回すのは、同じstate DBにある、ほかのrunのbaselineで、そのrun自身が採点して
  成功した結果だけです。失敗した結果、終わっていない結果、別の結果を使い回した
  結果、この機能より前の形式の結果は使いません。
- 次の値がすべて一致する結果だけを使います。リポジトリのルート（シンボリック
  リンクを解決したpath）、base commit、`check` と `setup` のargv、
  `checkTimeoutMs`、Node.jsの版、OSのplatform、architecture、`check` の先頭の
  コマンドが実際に起動するファイル（PATHから探し、シンボリックリンクを解決した
  path。worktreeの中のファイルはworktreeからの相対path）。起動するファイルは
  `spawn` と同じ順で探します。PATHの空の要素はworktreeを指します。PATHが
  未設定のときとWindowsでは分からないものとします。どれかが分からない
  runは、結果を使わず、ほかのrunに使わせる結果も残しません。
- これらの値はsetupで一度だけ求めて記録します。setupとbaselineの間でworkerが
  再起動し、Node.jsやPATHが変わっても、setupで記録した値で照合します。
- 比べるのはこれだけです。依存パッケージの中身、環境変数、`check` が内部で
  呼ぶほかのコマンド、ignore対象のファイル（`node_modules` など）は比べません。
  これらが変わったときは、`baselineReuse` を外すか、期限を短くします。
- 採点して成功したrunは、state rootの `baseline-index/<条件のSHA-256>/<run ID>.json`
  に、run IDと採点の完了時刻を書きます。runごとに自分のファイルだけを書き、
  ほかのrunのファイルは上書きしません。同時に書くrunがあっても、書く操作自体が
  互いの記録を消すことはありません。
- 使い回しを判断するときは、条件のディレクトリを1つ読みます。読めない記録と
  期限切れの記録を除き、残りを新しい順に試します。書かれたrunのbaselineを
  state DBから読み直し、採点して成功した結果であることと条件の一致を確かめ、最初に通ったものを
  使います。どれも通らなければ、通常どおり採点します。読むのはその条件の記録
  だけで、過去のrunを全部は読みません。
- 自分の記録を書いたあと、その条件の記録のうち `checkedAt` が7日より古いものと
  読めないものを消します。それより新しい記録は消さないので、同時に書いたrunの
  記録も残ります。ほかのrunが同時に消していても失敗にしません。`maxAgeMs` の
  上限は7日なので、期限内の記録が整理で消えることはありません。
- 期限は、元のrunで採点が完了した時刻（checkpointの記録）から、このrunが
  使い回しを判断する時刻までで測ります。元のrunが再開後にbaselineを保存して
  いても、再開の時刻からは測りません。時計の変更は扱いません。起きても、
  採点が1回増えるか、このマシンの時計で判断した結果を使うだけです。
- 使い回すときも、setupは毎回実行し、新しいworktreeを作ります。setupの直後の
  未追跡ファイルの確認も省きません。採点を省く前に、worktreeがbase commitに
  あること、tracked fileに変更がないこと、`.gitignore` の対象外の未追跡ファイル
  がないことを確かめ、満たさなければ通常の `baseline-check-failed` で止めます。
- 使い回しの判断はbaselineの結果として記録します。worker再開時は記録を読み戻し、
  候補を探し直しません。このrunで採点を始めたあとに再開した場合は、使い回さずに
  採点をやり直します。
- 使い回した結果には、ログをコピーせず、元のrunのログのpathを記録します。元の
  ログが消えていれば、reportのlogは `null` になり、理由を出します。
  checkpointから読み戻したかどうかの表示は、元のrunの記録に従います。
- reportのJSON（`baseline.reusedFrom` に元の `runId` と採点の完了時刻
  `checkedAt`）とMarkdown（「Baseline check」節の `source`）、web UIの
  「工程ごとの時間」の事前検証の行に、使い回したかどうかと、使い回した
  ときの元のrunと時刻を出します。
- 運用のための最適化で、エージェントに見せるものも採点の基準も変えないので、
  `configVersion` には入りません。

### 検証とレビューを同時に始める（parallelReview）

既定では、封印した候補を検証し、通ったものだけをレビューします。
`factory.json` に `"parallelReview": true` を書くと、候補を封印した直後に
検証と二つのレビューを同時に始めます。検証がほぼ毎回通るリポジトリでは、
レビューを待つ時間のぶんrunが短くなります。

```json
{
  "parallelReview": true
}
```

- 書かなければオフで、工程の順序、stepの名前、レビューの呼び出し回数と
  費用は今までと同じです。値は `trigger` の時点でrun inputに保存します。
  `retrigger` は保存した値を引き継ぎ、`--reload-config` はファイルを読み直し、
  `demo repair` の修正runは元のrunの値を引き継ぎます。いつレビューするかの
  選択で、レビューの中身は変えないので、`configVersion` には入りません。
- オンのとき、レビュー役が読む候補のコードは、封印したcommitから取り出した
  木（head snapshot）と、候補のdiffと変更ファイル一覧だけです。検証が動いている
  worktreeは、作業ディレクトリにも、promptにも、読める場所にも入れません。
  promptのレビューはhead snapshotの中で動きます。`command` や
  `local-instructions` のレビューは今までどおり自分用のディレクトリで動き、
  base snapshotも読めます。Codex、Claudeのどちらでも同じです。
- 検証とレビューの両方が通った候補だけが、今までどおり承認に進みます。
  レビューが修正を求めたときは、今までどおり修正に回ります。
- 検証がレビューの途中で失敗すると、その回のレビューを止めます。止めた
  呼び出しは、それまでに分かった使用量と、完了のcheckpointを
  `cancelled`（理由 `superseded-by-verify`）として残します。workerが再開しても
  その呼び出しを送り直さず、`uncertain-invocation` にもしません。まだ送って
  いなかったレビューは送らず、呼び出しとしても費用としても数えません
  （計測の記録は `not-sent`）。すべてのレビューが終わってから次の工程に進みます。
- レビューが先に終わってから検証が失敗した回は、判定を記録に残したうえで
  `discarded`（理由 `verify-failed`）として使いません。
- 止めた回と使わなかった回の判定は承認に使わず、`review-cap-reached` までの
  レビュー回数にも数えません。
- 検証が失敗したとき、次の修正にはまず検証の失敗を渡し、先にそれを直すよう
  求めます。その回で最後まで終わったレビューの判定と指摘は、そのあとに
  信頼できない入力として区切って渡します。検証に落ちた候補へのレビューなので、
  修正後には当てはまらない指摘もあると添えます。止めたレビューからは
  何も渡しません。
- レビューの途中でworkerが止まり、開始のcheckpointしかない呼び出しは、
  今までどおり `uncertain-invocation` で止め、送り直しません。
- 検証が失敗する前に、レビューがそれ自体の理由で失敗したとき（返答を読めない、
  providerが拒否した）は、逐次のときと同じくrunを失敗にします。ツール呼び出しを
  拒まれただけなら、返答が読める限りレビューは失敗にしません（後述）。

reportの「Review rounds」では、数えなかった回に `cancelled` か `discarded` と
理由が付きます。検証がまだ終わっていない回と、検証がエラーで終わった回は
`pending`（理由 `verify-pending`）で、これも数えず、レビューの要点にも
使いません。「検証に落ちた候補へのレビュー」の呼び出し数と費用は、
reportの要約、`demo compare` の設定ごとの行、`demo compare --trend` の列に、
総費用とは別に出ます。この費用は総費用に含まれています。使用量や価格が
分からない呼び出しがあれば、0 ではなく不明と出します。止めたレビューは、
止めるまでにproviderが報告した使用量（モデル別）とsession IDを残します
（後述の「止めた呼び出しの使用量」）。この使用量は止めた時点までの下限なので、
それを含む合計は完全な値として出さず、そのrunの総費用も不明と出ます。web UIでは、
レビューの欄と工程の時系列の詳細に「中止」「不採用」「検証待ち」と理由が出て、
工程の時系列では検証とレビューの重なりが実際の時刻どおりに見えます。

### 終える前にエージェントに確かめさせる（selfCheck）

`factory.json` の `"selfCheck"` に短いコマンドを書くと、実装と修正のpromptに
「終える前にworktreeでこれらを実行し、出た問題を直す」という規則が1つ加わります。
未使用のexportのように、手元ですぐ見つかる問題で修正の1回を使わないためです。

```json
{
  "check": ["pnpm", "validate"],
  "selfCheck": [
    ["pnpm", "lint"],
    ["pnpm", "typecheck"]
  ]
}
```

- 1から5個のコマンドを書けます。各コマンドは `check` と同じくargvの配列で、
  空の配列と空の文字列は `trigger` の時点で拒否します。
- promptには各コマンドを1行ずつ、バッククォートで囲んで載せます。あわせて、
  採点コマンドも同じ問題を見つけることと、runの合否を決めるのは採点コマンド
  だけであることを伝えます。
- factoryはこれらのコマンドを実行しません。工程も、やり直しも、反復の数え方も
  増えません。合否は今までどおり `check` だけで決めます。
- 書かなければpromptは今までと同じです。値は `trigger` の時点でrun inputに
  保存します。`retrigger` は保存した値を引き継ぎ、`--reload-config` はファイルを
  読み直し、`demo repair` の修正runは元のrunの値を引き継ぎます。promptが変わる
  ので、書いたときは `configVersion` に入ります。

### 新しいテストをbaseとcandidateで動かす（testProbe）

レビュー役はコマンドを実行できないので、新しいテストが変更を本当に確かめて
いるかを、コードを読んで推測するしかありません。`factory.json` の
`"testProbe"` を書くと、候補を封印したあと、検証とレビューの前に、候補が追加・
変更したテストファイルをbaseと候補の両方で実行し、その結果を両方のレビュー役に
信頼できる情報として渡します。

```json
{
  "testProbe": [
    {
      "glob": "test/**/*.test.ts",
      "command": ["pnpm", "vitest", "run", "{files}"]
    }
  ]
}
```

- 1個以上の `{ glob, command }` を書けます。`glob` はリポジトリ直下からの相対
  パスに当てます。`command` はargvの配列で、`"{files}"` だけの要素を1つ以上
  含める必要があります。テストファイルごとに1回起動し、`"{files}"` の要素を
  そのファイルのパス1つ（`./test/a.test.ts` のように `./` を付けたもの）に置き換え
  ます。`-` で始まる名前のファイルがオプションと読まれることはありません。shellは
  通さないので、パスが展開や分割されることもありません。`"--file={files}"` のように
  他の文字と混ぜた要素、`"{files}"` の無いコマンド、空の配列と空の文字列、21個以上の
  項目、200文字を超える `glob` は `trigger` の時点で拒否します。
- 対象は、封印した候補の変更ファイル一覧（`changed-files.txt`）で `added` か
  `modified` のファイルのうち、どれかの `glob` に合うものだけです。`deleted`、
  `renamed`、`copied` のファイルは実行しません。複数の `glob` に合うファイルは、
  最初に合った項目のコマンドで1回だけ実行します。合うファイルが無い候補では
  コマンドを実行せず、「実行するテストが無かった」と結果に書きます。
- setupでは、エージェントのworktreeと並べて、baseのcommitの切り離したworktree
  （`runs/<id>/base-work`）を作り、同じ `setup` を実行します。候補ごとにこの
  worktreeをbaseに戻し（前の候補のテストが書いた未追跡のファイルと、ファイルを
  1つも含まない未追跡のディレクトリも、ファイルのあるディレクトリの中のものまで
  消します。
  `setup` が終わった直後に残っていた未追跡のファイルは
  `runs/<id>/test-probe/base.json` に中身の指紋（ファイルはsha256）と一緒に記録
  してあり、それは消しません。`setup` が作った `.gitignore` に当たらないfixture
  も、候補側と同じようにbaseに残ります。前のテストが記録したファイルを書き換えたり
  消したりしていたら、baseのworktreeを作り直して `setup` を実行し直し、記録も
  取り直します。作り直しに失敗したら、baseの側は理由つきで「実行できなかった」に
  なります）、対象のテストファイルだけを候補から持ってきて実行します。まとめて
  持ってこられなかったときは1つずつ持ってきて、持ってこられなかったファイルだけ
  baseの側を理由つきで「実行できなかった」にします。候補側はエージェントの
  worktreeで同じファイルを実行します。テストが追跡中のファイルを書き換えても、
  新しいファイルを書いても、レビューの前に封印した内容に戻し（`.gitignore` に
  当たる依存などは残します）、候補が封印どおりであることを確かめます。封印が
  gitlinkとしてコミットした入れ子のリポジトリ（`setup` が作ったものなど）の中で
  テストがファイルを書き換えたりcommitしたりしたときは、そのリポジトリをgitlinkの
  指すcommitに `reset --hard` で戻します（1階層だけで、その中の未追跡のファイルは
  残します）。次の封印に
  テストの出力が入ることはありません。テストの実行中にworkerが止まったときは、
  再開した検証が候補のworktreeを封印した内容に戻してから、probeをやり直します。
- コマンドはどれも `CI=true` を足した環境で実行します。VitestやJestは、snapshotが
  無いときに書いて通すのではなく、落ちます。baseに持ってくるのは対象のテスト
  ファイルだけなので、候補が一緒に追加したfixtureやhelperで、どの `glob` にも
  合わないものを使うテストは、baseではそれが無いために落ちます。結果の中でも、
  出力の末尾からそれを見分けるよう求めます。
- 各実行の時間の上限は `checkTimeoutMs` と同じで、出力は末尾だけを残します。
  stdoutの末尾のあとにstderrの末尾を並べ、片方が長くてももう片方の末尾が押し
  出されないようにします。時間切れのときも、それまでの出力を残します。
  結果は `runs/<id>/test-probe/<候補ID>.txt` に書き、step の出力として保存します。
  32 KiBに収まるように出力の末尾を短くし、それでも収まらないときは、件数には
  含めたまま後ろのファイルの詳細を省きます。
- 結果には、ファイルごとにbaseと候補の終了コード、所要時間、出力の末尾と、
  「baseで落ちて候補で通った」「両方で通った」「候補で落ちた」「実行できなかった」
  のどれかを書きます。factoryは結果を判定に使いません。baseで落ちても、新しい
  テストが読み込むモジュールがbaseに無いだけのことがあるので、結果の中で、
  出力の末尾から落ちた理由を読むよう求めます。結果が添付されたレビューでは、
  規則も「添付の結果を根拠に判断し、結果が無いテストだけコードを読んで判断する」
  に変わります。
- 実行できなかった場合（baseのworktreeを作れない、baseの `setup` が失敗した、
  コマンドが起動しない、時間切れ）も、runは止めません。理由を結果とreportに
  残して、検証とレビューに進みます。baseの準備に失敗したときも、候補側は
  実行します。
- 結果は候補ごとの `stage:<n>:verify:test-probe` stepに保存します。`parallelReview`
  でも、検証と二つのレビューを始める前に終わらせます。結果は検証のイベントで
  runの状態に入り、順次のレビューはその状態から作ったtargetで受け取ります。
  workerが止まって再開しても、保存した結果を使い、同じ候補のテストを二度実行
  しません。保存する出力の末尾は、結果のテキストに載らなかったファイルの分も
  含めて全部残ります。
- baseのworktreeは、runが終わるとき（完了、失敗、cancel、setupやpreflightでの
  失敗）に、gitの登録も含めて消します。specや承認を人が決めるのを待つ間はrunが
  終わっていないので残し、待機のあとのprobeはそのまま使います。消えていれば
  作り直します。別のプロセスからのcancelもその場で消し、それと行き違って残った
  ものはworkerの起動時に消します。gitの登録は `git worktree remove -f -f` で
  ディレクトリと一緒か先に消し（途中で止まった `git worktree add` が残したロック
  付きの登録も消します）、`base.json` は `git worktree list` にbaseが出なくなって
  から消します。片付けの途中でworkerが止まったりgitが失敗したりしても、起動時の
  片付けが `base.json` から登録の残りを見つけて消します。`demo archive` と `demo prune --apply` も
  worktreeと一緒に消します。
- reportのJSON（`testProbes`）とMarkdown（「Test probe」節）には、候補ごとに
  対象のファイル数、baseで落ちて候補で通った数（両方で落ちたファイルは数えません）、
  所要時間、実行できなかった理由が出ます。
  保存したstepから読むので、reportのためにテストを実行し直すことはありません。
- 書かなければ、baseのworktreeもprobeのstepも作らず、工程は今までと同じです。
  値は `trigger` の時点でrun inputに保存します。`retrigger` は保存した値を
  引き継ぎ、`--reload-config` はファイルを読み直し、`demo repair` の修正runは
  元のrunの値を引き継ぎます。`configVersion` には入りません。
- 次の制約は直さずに残しています（詳しくはADR-0039の「Known limits」）。
  - 同じ候補の中では、先に走ったテストが変えたものを後のテストがそのまま見ます。
    ファイルごとに戻すとgitの処理がファイル数倍になるためで、出力の末尾で見分け
    られます。
  - 削除の途中でleaseを失い、別のworkerが引き継いだとき、古いworkerの後片付けが
    新しいworkerのprobeの出力や印を消すことがあります。leaseを失い、しかもその間に
    引き継がれたときだけ起きるので、削除ごとにleaseで守る仕組みは入れていません。
  - `base.json` が指すリポジトリが無くなっても、マウントされていないボリュームと
    見分けられないので、起動時の片付けは毎回試し直します。
  - baseを戻すときは追跡外のファイルを1つずつ消し、記録したファイルの指紋も毎回
    取り直します。遅くなるのは `setup` が大量の追跡外ファイルを残すときだけで、
    `setup` のファイルを残すにはこの作業が要ります。
  - probe全体の時間の上限はありません（最大でファイル数×2×`checkTimeoutMs`）。
    上限には設定と途中で止まったprobeの扱いが要り、今のところ必要になっていません。
  - Durablyの待機と失敗を、エラーの文言 `Durably execution suspended` で見分けて
    います。判定の型や関数はライブラリ側でexportするもので、この例の範囲外です。
  - worktreeの外を指すかの判定の重複と、verify-reviewの工程がreducerと同じ登録と
    targetの作り直しをしていること（そのためのservicesの `createTarget`）は、
    動作の変わらないリファクタリングなので別に行います。
  - 古いgitに対応するため `git worktree list --porcelain` を `-z` なしで読むので、
    改行を含むworktreeのパスは扱えません。factoryがそういうパスを作ることは
    ありません。
- 判断の理由は [ADR-0039](../../docs/adr/0039-local-agent-loop-test-probe.md)
  にあります。

### レビューのblockerを頻度と深刻さで決める（review.blockerThreshold）

`findings-json` のコードレビューには、製品の動作についての指摘を、実際に起こる
頻度（likelihood）と起きたときの深刻さ（impact）でそれぞれ1から10の整数で評価させ、
2つの積が閾値未満なら `non-blocker` にするよう伝えます。起こる可能性が極めて低い
指摘で、修正と再レビューの往復を重ねないためです（ADR-0040）。

```json
{
  "check": ["pnpm", "validate"],
  "review": { "blockerThreshold": 5 }
}
```

- `blockerThreshold` は0から100の整数で、書かなければ5です。負の数、101以上、
  小数、数でない値は `trigger` の時点で拒否します。0は規則を入れません（今までの
  レビューと同じです）。
- 積が閾値以上の指摘は、今までどおりレビュアーが `blocker` か `non-blocker` かを
  決めます。テストの十分さ、範囲の逸脱、誘導（steering）、秘密情報の混入など、
  製品の動作でない指摘には積の規則を当てず、今までどおり判断させます。
  課題、仕様、確定した文脈（`--context-file`）がはっきり求めていることを変更が
  満たしていない、という指摘にも当てません。求められた要件は、起こりにくい
  ケースについてのものでも、頻度で外しません。
- 分類するのはレビュアーです。factoryは返された `severity` を採点値から書き換えず、
  今までどおり `blocker` が一件でもあれば `needsChanges` にします。指摘が製品の
  動作についてのものかは、JSONの値からは分からないからです。
- 規則はレビューの文脈のCHECKに入るので、通常のprompt、`command` の後ろに続く文脈、
  `local-instructions` の `CLAUDE.local.md` のどれにも届きます。`verdict` のレビューと
  仕様のレビューには入れません。重さで振り分けたいレビューは `output` を
  `findings-json` にします。
- 値は `trigger` の時点でrun inputに保存します。`retrigger` は保存した値を引き継ぎ、
  `--reload-config` はファイルを読み直し、`demo repair` の修正runは元のrunの値を
  引き継ぎます。この設定ができる前に保存したrunとその修正runには規則を入れません。
  レビューの基準が変わるので、閾値は0も含めて `configVersion` に入ります。
- reportは固定した閾値（JSONの `reviewBlockerThreshold`、Markdownの
  `review blocker threshold` の行）を出します。JSONの `reviewBlockerRuleLenses` は
  規則が届いたレビュアー（`output` が `findings-json` で、レビューの記録があるか、
  レビューの呼び出しを送ったもの）です。送った後に取り消したレビューも数え、
  送る前に取り消したものは数えません。送ったかどうかは、呼び出しを渡す時点の
  記録で見ます。モデルが読む前に止まったかどうかは分かりません。
  Markdownの行は届いたレビュアーと規則の対象外を書き、どのレビューにも届いていない
  run（コードレビューがすべて `verdict`、または最初のレビューを送る前に止まったrun）では
  そう書きます。
- 積が閾値未満なのに `blocker` にする指摘には、理由として `thresholdException` を
  書かせます。値は `not-product`（製品の動作でない指摘）か `explicit-requirement`
  （課題、仕様、確定した文脈がはっきり求めている要件の漏れ）です。ほかの値は欄だけ
  捨て、指摘はそのまま受け付けます。値はレビュアーの自己申告で、factoryは正しさを
  確かめません。
- reportは、2つの採点値を持ち積が閾値未満の `blocker` を、レビューの回とレンズごとに、
  例外ありと例外なしに分けて数えます（JSONの `belowThresholdBlockers`、Markdownの
  `blockers below threshold` の行）。検査の失敗で数えなかった回と、runが終わったときに
  検査が終わらず `pending` のままの回も含めます。閾値が0のとき、採点値がそろわない
  指摘、`non-blocker` は数えません。数えるのはreportが残した指摘（レビューごとに
  先頭20件）だけです。
- 同じrunの中でレビューの指摘を受けて直す回にも、起こりにくいケースや将来のケースの
  ために設計しないよう伝えます。新しいセッションの回も、会話を続ける回も同じです。
  検査だけが落ちて直す回と、最初の実装の回には伝えません。

### 設定の事前確認（preflight）

baselineの後、triageを含む最初のエージェント呼び出しの前に、全役割
（code、二つのreview、設定したtriage）のprovider、model、effortを確かめます。
同じ組み合わせは一度だけ確かめ、使う役割すべてに結果を対応付けます。

- Codexは無料の `model/list`（固定したCodex CLIのapp server）で、そのloginで
  使えるmodelと、そのmodelが受け付けるeffortを確かめます。一覧にあるmodelが
  そのeffortを受け付けなければ、promptを送らずに止めます。app serverが起動
  しない（CLIが見つからない、`app-server` に対応しない古い版、初期化の失敗）
  場合も、promptを送らずに止めます。初期化が時間切れになっただけの場合は起動が
  遅いだけかもしれないので、止めずに最小の呼び出しで確かめます。最小の呼び出しの
  初期化も時間切れになった場合は、送ったかどうか分からない呼び出しとして
  `uncertain-invocation`（`retry: NO`）で止まります。一覧は1ページ目だけを
  読みます。一覧は隠しmodelを含まないので、一覧に無い
  modelは使えないとは決めず、一覧が読めないときと同じく最小の呼び出しで確かめます。
  一覧は同じCLIファイルにつき1回だけ読みます。
- Claude Codeにはpromptを送らずに確かめる手段が無いので、組み合わせごとに
  最小の呼び出し（「OK」とだけ返させる読み取り専用の呼び出し）を1回します。
- 最小の呼び出しは通常の呼び出しと同じcheckpointと計測を通り、使用量と推定費用は
  stage・roleとも `preflight` として別に集計します（code/reviewには混ぜません）。
  providerが明示的に拒否した場合（未知のmodel、使えないmodel、login切れ、
  Codex CLIが起動しないなど）は完了として記録し、`preflight-failed`（`retry: yes`）
  で止まります。Claude Codeのlogin切れやmodelの誤りは、providerが構造化した
  種別を付けずに本文から判定することもあり、その場合も拒否として扱います。送ったかどうか分からない呼び出しは送り直さず、
  `uncertain-invocation`（`retry: NO`）になります。
- 使えない組み合わせがあると、実装の呼び出し前に `preflight-failed` で止まり、
  役割、設定、確認方法、原因をエラーに出します。reportの `preflight`（JSON）と
  「Preflight」節には、役割ごとの結果、確認方法、CLIのpathと版、最小の呼び出しの
  使用量と費用（分からなければ `unknown`）が残ります。

### Codex CLIを固定する（codexPath）

`factory.json` の `"codexPath"` で起動するCodex CLIを指定できます。相対パスは
`factory.json` のあるディレクトリから解決し、実行可能な通常ファイルでなければ
`trigger` が失敗します。解決した絶対パスをrun inputに固定し、preflight、本番の
呼び出し、版の取得はすべてそのファイルを使います。`.js` などのscriptは `node`
で起動します。省略時はPATHの `codex` を優先し、無ければ同梱の `@openai/codex`
を使います。同梱の版は新しいモデルに追いつかないことがあるためです。CLIのpathと版はreportの「Versions」と「Preflight」に
出て、`configVersion` にも入るので、違うCLIで動いたrunは別の設定として比較されます。

### trigger時点で固定されるもの

`factory.json`、task、spec、dispositions、contextは `trigger` の時点で一度だけ読みます。
フラグを適用した後の各役割のrequested設定と、入力ファイルのpathと本文をrun inputに
保存します。実際に使うmodelとeffortは、workerがそのrequested設定からproviderの
presetで解決します。workerは元のファイルを読み直さないので、trigger後にファイルを
書き換えても、そのrunの設定とpromptは変わりません。timeout、`codexPath`、
`baselineCheck`、`baselineReuse`、`parallelReview`、`selfCheck`、`testProbe`、`review.blockerThreshold`、`commit` も同じく解決済みの値をrun inputに保存します。reportには各入力ファイルの
pathと、保存した本文から計算したSHA-256が出ます。contextは本文もreportに出します。
Markdownでは本文中のどのバッククォートの並びより長いフェンスで囲むので、
本文の見出しがreportの見出しと混ざりません。設定を直した後に同じtaskで
やり直すには、`demo retrigger --run <id> --reload-config` を使います（上の
「止まったrunと次の手順を見る」を参照）。

### タスクの事前判定（shadow mode）

`factory.json` の `profiles.triage` を書くと、setupの後、実装の前に一度だけ
LLMにタスクを判定させます。書かなければ判定の呼び出しは起きず、従来と同じ
流れで動きます。

```json
{
  "profiles": {
    "triage": { "provider": "codex", "model": "gpt-5.6-sol", "effort": "low" }
  }
}
```

- 項目の補い方は他の役割と同じです。`"triage": {}` でも有効になり、
  `--provider`、`--model`、`--effort` とpresetの値を使います。fakeと実providerを
  混ぜられない規則も同じです。
- 判定は `routine`（そのまま実装とレビューで終わりそう）か `probe`（試しに実装
  してみるべき）のどちらかと、1〜2文の理由です。新しいsessionで、読み取り専用
  権限で動きます。渡すのは保存済みのtaskとspecだけで、「信頼しないデータ」の
  区画に入れます。dispositionsは渡しません。
- 今は **shadow mode** です。判定は記録するだけで、工程やprofileの選択には
  一切使いません。`routine` と `probe` のrunは同じ工程を同じprofileで進みます。
  経路の切り替えは [ADR-0018](../../docs/adr/0018-local-agent-loop-adaptive-routing.md)
  の後続の段階で、判定の精度を測ってから入れます。
- 形式に合わない応答（空、JUDGMENTが無い、二つある、`routine`/`probe` 以外、
  REASONが無いか500文字を超える）と、provider errorやtimeoutは `unknown` として
  理由と一緒に記録し、runは実装へ進みます。判定の失敗でrunが止まることはありません。
  timeoutは最長5分です。triage呼び出しの使用量が分からない場合、そのrunの合計
  token・costも不明として扱います（0とは数えません）。
  ただし、再開時に開始だけのcheckpointが見つかった場合は、他の呼び出しと同じく
  未確定として止まります。
- 判定と理由は `report --format json` の `triage`、Markdownの「Triage」節、
  `status --run` の `triage` に出ます。承認待ちの途中でも読めます。判定の
  無いrunは `null`（Markdownでは `none`）で、`unknown` とは区別します。
- `profiles.triage` の有無と中身は `configVersion` に入ります。triageの無いrunの
  `configVersion` は以前と変わりません。

- triageの完了記録には、判定と理由と一緒に、保存済みのtaskとspecから測った
  較正材料を残します。taskの文字数、specの文字数、specの受け入れ基準の項目数、
  specが挙げる変更予定ファイルの数の四つです。文字数はUnicodeのcode pointで
  数えます。項目数とファイル数は、次の一つの規則で数えます。
  - `#` 〜 `######` の見出しのうち、題が `Acceptance Criteria`、
    `Completion Criteria`、`受け入れ基準`、`完了条件`、`完了基準` のもの
    （受け入れ基準）と、`Files to Change`、`Files to Modify`、`Changed Files`、
    `変更するファイル`、`変更予定のファイル`、`変更対象のファイル` のもの
    （変更予定ファイル）を対象にします。題は大文字小文字と末尾のコロンを
    区別しません。
  - 節は次の同じか上の階層の見出しまでで、その中の小見出しも含みます。
  - 数えるのは行頭から始まる箇条書き（`-`、`*`、`+`、`1.`、`1)`。
    `[ ]` / `[x]` 付きも可）だけで、字下げした入れ子は上の項目の一部として
    数えません。fenced code blockの中は読みません。
  - 同じ記述は一度だけ数えます。受け入れ基準は空白をまとめて小文字にした
    本文で、変更予定ファイルは項目の最初の `` `code` ``（無ければ最初の語）の
    pathで比べます。
  - specが無いrunでは、spec由来の三つは「不明」（`null`）です。specに該当する
    見出しが無い場合も、その値は「不明」にします。0とは数えません。この値の
    無い古いtriage記録も「不明」として読みます。
    較正材料は、承認待ちの途中のreport（triageの完了step）と、終わった後のreport
    （run output）に同じ値で出ます。
- triageの呼び出しをproviderが明示的に拒否した場合は、`unknown` として
  進まずに `rejected-invocation` で止まります。

### 修正専用のprofile（profiles.repair）

`factory.json` の `profiles.repair` を書くと、修正（検証の失敗やレビューの
指摘を受けた2回目以降の実装）だけを別のprovider、model、effortで動かせます。

```json
{
  "profiles": {
    "code": { "provider": "codex", "model": "gpt-5.6-sol", "effort": "medium" },
    "repair": {
      "provider": "codex",
      "model": "gpt-5.6-terra",
      "effort": "high"
    }
  }
}
```

- 書かなければ、修正は従来どおり `code` の設定で動き、`--context reuse` では
  実装のsessionを継続します。`configVersion` も変わりません。
- 書かなかった項目は、フラグやpresetではなく解決済みの `code` から補います。
  `"repair": { "effort": "high" }` なら、providerとmodelは `code` のまま、effortだけ
  変わります。providerを `code` と違うものにした場合は、`code` のmodelとeffortは
  使わず、そのproviderの既定presetで補います。
- fakeと実providerを混ぜられない規則、preflightの対象になることは
  他の役割と同じです。preflightは同じ設定を一度だけ確かめるので、`code` と同じ
  設定の `repair` は追加の確認をしません。
- `repair` のprovider、model、effortが `code` と同じなら、書かなかった場合と同じ
  です。sessionを継続し、`configVersion` も変わりません。
- 違う場合は、修正のたびに新しいsessionを始めます。promptには保存済みのtask、
  spec、実装の規則と、検証・レビューから得た修正の指示を渡し、前の実装が
  作業場所に残っていることを伝えます。`configVersion` はこの設定を含むので、
  `repair` の無いrunとは別のグループとして比較されます。
- ただしClaudeでeffortだけが違う場合は、実装のsessionを継続します（次の節）。
- `--context fresh` の修正は、`repair` の有無にかかわらず毎回新しいsessionです。
- 修正の呼び出しと使用量は、reportの役割別集計で `code` ではなく `repair` の
  行に入ります。
- 修正の呼び出しをproviderが明示的に拒否すると `rejected-invocation` で止まります。
  `factory.json` の `repair` を直してから `demo retrigger --run <id>
--reload-config` でやり直します。

### effortだけ違う修正は実装のsessionを継続する（Claude）

Claude Codeは、再開したsessionのeffortを変えてもprompt cacheを保ちます
（[公式ドキュメント](https://code.claude.com/docs/en/prompt-caching#changing-effort-level)、
Claude Code 2.1.280での実測でも、新しいsessionのcache readは0、effortを変えて
再開したsessionは同じeffortでの再開と同じ43,628 tokenでした）。そこで次の条件を
すべて満たすときは、`repair` が `code` と違っていても、修正で実装のsessionを
継続します。

- `--context reuse`
- providerが両方ともClaudeで、実効effortだけが違う
- 事前確認（preflight）の最小呼び出しで、Claude Codeが報告したmodelが
  両方で同じ（下の「modelの確かめ方」）
- そのmodelがOpus 5.5（`claude-opus-5-5`）かFable 5.1（`claude-fable-5-1`）
- Claude Code CLIが2.1.260以降（`claudeCli` の版から読みます。読めなければ継続しません）。
  2.1.260は公式ドキュメントが挙げる版で、実測は2.1.280で行いました。
  なお `claude-opus-5-5` そのものを使うには2.1.280以上が必要です（「モデルの選び方とサブスクでの制約」の節）
- `CLAUDE_CODE_USE_BEDROCK`、`CLAUDE_CODE_USE_VERTEX`、
  `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` のどれも設定されていない

```json
{
  "profiles": {
    "code": {
      "provider": "claude",
      "model": "claude-opus-5-5",
      "effort": "medium"
    },
    "repair": { "effort": "high" }
  }
}
```

- modelの確かめ方: `opus` のような別名を実際のmodelに解決するのはClaude Code
  自身で、このサンプルは別名の対応表を持ちません。実効modelは指定どおり
  （`opus` なら `opus`）です。そこで事前確認の最小呼び出しで、Claude Codeが
  `init` メッセージで報告したmodel（`opus` なら2.1.280では `claude-opus-5-5`）を
  読み、`code` と `repair` で比べます。
  - `opus` と `opus`、`opus` と `claude-opus-5-5` は、両方の報告が
    `claude-opus-5-5` なら継続します。
  - 報告が無いmodel（報告を記録する前の事前確認を含む）は、分からないものとして
    新しいsessionにします。
  - `claude-` で始まる完全なmodel IDはClaude Codeがそのまま使います。どちらか
    片方でも対象外の完全なID（`opus` と `claude-sonnet-5` など）なら、また
    完全なIDどうしが違えば、setupの時点で継続しないと決めます。
- 判定は二段です。setupで、modelを除く条件（context、provider、effort、CLIの版、
  環境変数、完全なIDの確認）を一度だけ判定し、runの `setup.repairSession`
  に候補かどうか（`eligible`）と理由を記録します。候補になっても継続はまだ
  確定していません。事前確認のあとで報告されたmodelを確かめて確定し、
  `preflight:repair-session` stepに、setupの判定、確定した判定（`continues` と
  理由）、runの `configVersion` を記録します。どちらも記録済みのstep出力だけから
  決まるので、あとでworkerを別の環境変数で起動し直しても、そのrunの扱いは
  変わりません。
- 確定した判定と理由は、JSON reportの `repairSession` と、Markdown reportの
  `repair session` の行に出ます。修正呼び出しごとの扱いは `repairCalls` の
  `sessionHandling` と `sessionReason` で確かめられます。
- 継続する修正は、記録済みのsession IDを `resume` に、`repair` の実効effortを
  `effort` に渡して呼びます。promptは新しいsessionとしては書かず、前の会話の
  続きとして書きます。修正が返したsession IDを次の修正のために記録します。
- 継続してよいかは、provider、事前確認で確かめたmodel、作業場所、指示版の
  一致で確かめます（effortの一致は求めません）。このため実装と修正のsessionには、
  その呼び出しでClaude Codeが報告したmodelを記録します。事前確認と実装の間に
  Claude Codeが更新されて別名の解決先が変わった場合など、記録したmodelが確定した
  modelと違えば、止まらずに新しいsessionにし、理由を `sessionReason` に残します。
  modelを記録していない古いsession（`null` を含む）も、effortをまたいで継続せず
  新しいsessionにします。
- 事前確認で継続が確定したrunだけ `configVersion` にこの方針が入ります。setupでは
  方針を含まない版を記録し、確定したときだけ事前確認のあとの呼び出しとreportが
  方針を含む版になります。候補になっても確定しなかったrun（たとえば `sonnet`
  どうしで、Claude Codeが `claude-sonnet-5` を報告した場合）を含め、それ以外の
  runの `configVersion` は変わりません。事前確認の最小呼び出しの計測には、
  確定前の版が残ります。
- Codex、providerやmodelが違う修正、`--context fresh`、外部の指摘から始まる子run
  の最初の修正は、これまでどおり新しいsessionです。子runは親のsessionを
  引き継ぎません。
- 環境の判定は環境変数だけを見ます。設定ファイルやgatewayなど、環境変数以外の
  方法でBedrockやVertexを使っている場合は判定できず、継続してしまうことが
  あります。そのときはcacheが効かないだけで、結果は変わりません。reportの
  修正呼び出しごとのcache-read比率で確かめられます。
- 判断の理由は [ADR-0024](../../docs/adr/0024-local-agent-loop-claude-effort-session-reuse.md)
  にあります。

### レビュー役の呼び出しと出力（command、context、output）

`profiles.review.correctness` と `profiles.review.edge-cases` には、provider、model、
effortに加えて、呼び出し方と返答の読み方を役割ごとに書けます。

```json
{
  "profiles": {
    "review": {
      "correctness": {
        "provider": "claude",
        "model": "claude-opus-5-5",
        "effort": "high",
        "command": "/code-review {effort} {base}...{head}",
        "context": "local-instructions",
        "output": "findings-json"
      },
      "edge-cases": { "provider": "codex", "output": "findings-json" }
    }
  }
}
```

- `command` は、factoryのレビューpromptの代わりに送る入力です。使える
  プレースホルダーは `{effort}`（その役割のeffort）、`{base}`（runが固定した
  base commit）、`{head}`（レビューするcandidateのcommit）の三つだけです。
  展開した文字列を一度だけ送り、送り直しません。空白だけの値、ほかの `{…}`、
  閉じていない `{` や対応しない `}`、effortが決まらない役割での `{effort}` は、
  `trigger` の時点で理由を付けて拒否します。factoryは特定のコマンド名を知りません。
- `context` はレビューの文脈（確認事項、trusted context、ハッシュ付きの
  `TASK`／`SPEC`／`DISPOSITIONS`／`FINDINGS`、差分と変更ファイル一覧とスナップ
  ショットの場所、返答の形）をどこに置くかです。`prompt`（既定）は入力に含めます。
  `command` があれば、その後ろに続けます。`local-instructions` は、factoryがその
  呼び出しのために作る作業ディレクトリ（後述）の `CLAUDE.local.md` に置き、入力は
  `command` だけにします（`command` が無ければ「`CLAUDE.local.md` のレビューを
  する」という短い文です）。candidateのworktreeには何も書きません。
  `prompt` でも、`command` があれば（コマンドモード）作業ディレクトリに短い
  `CLAUDE.local.md` を置きます。入力が届くのは親のセッションだけで、作業ディレクトリ
  にはコードが無いからです。このファイルはcandidateのworktree、差分、変更ファイル一覧、
  baseとheadのtreeの場所と、あればstageの結果のコピー（信頼できる情報）と実装担当の
  NOTESのコピー（信頼しない情報）の場所を示し、サブエージェントも含めて、コードを
  そこから絶対パスで読むよう伝えます。
- `output` は返答の読み方です。`verdict`（既定）は従来の `DECISION`／`NOTES` です。
  `findings-json` は、返答の最後の ` ```json ` ブロックにある配列を読みます。
  各指摘は `{"severity": "blocker" | "non-blocker", "title": "...", "body": "...",
"file": "...", "line": 12, "likelihood": 2, "impact": 3}` で、`file`、`line`、
  `likelihood`、`impact` は省けます。書く場合は
  `file` が空でない文字列、`line` が1以上の整数、`likelihood` と `impact` が
  1から10の整数でなければなりません（前述の「レビューのblockerを頻度と深刻さで決める」）。ファイル全体への
  指摘は `line` を省きます（`0` は形が違う指摘です）。`null` は「省いた」扱いにはせず
  形が違う指摘として止めます。レビュアーに示す返答の形にも `likelihood` と `impact` を
  省ける欄として載せ、値のない欄は省いて `null` を書かないよう伝えます。返答の最終行は改行1つ（`\n` または `\r\n`）を
  除いて `REVIEW_STATUS: COMPLETE` ちょうどでなければならず、末尾の空白や
  タブがあれば完了行として認めません。`blocker` が一件でも
  あれば `needsChanges` で、`blocker` だけを `- [file:line] title — body` の形で
  一行ずつnotesにし、修正に渡します。notesの長さには上限があり、各行は
  1,000文字まで、並べるのは最初の20件まで（最大でおよそ20 × 1,000文字）で、残りは
  件数だけを書きます。`title`、`body`、`file` の改行（LF、CR、垂直タブ、改ページ、
  U+0085、Unicodeの行区切りと段落区切り）は前後の空白ごと空白一つにするので、一件が
  複数行になることはありません。
  空の配列か `non-blocker` だけなら `pass` です。完了行が無い・最終行でない・別の状態、JSONが無い・壊れている、指摘の形が
  違う、途中で切れた、はどれも `review-incomplete`
  で止まり、`pass` にはなりません。同じ呼び出しを自動で送り直すこともしません。
- レビューのツール呼び出しをガードが拒んでも、それだけでは `review-incomplete` に
  しません。ガードが拒むのは、レビュー自身の作業ディレクトリ、候補のworktree、
  差分と変更ファイル一覧のディレクトリ、baseとheadの木の外だけなので、拒まれた
  読み取りで候補の中身が隠れることはないからです。返答が読めれば、その判定を
  そのまま使います。返答が読めなければ、拒まれた呼び出しがあってもなくても
  `review-incomplete` で止まります。`command` のないレビューも、仕様のレビューも
  同じです。
  拒まれた呼び出しは、ツール名とガードが示した理由（`Glob` ならパターンと
  `path` 引数）を、件数と先頭10件、各300文字までで記録します。記録はレビューの
  stepの出力と呼び出しの試行のmeasurementに残し、reportではJSONのレビューの
  `permissionDenials` と、Markdownのレビューの行の下の1行に出します。拒まれた
  呼び出しが無いレビューには出しません。
  指摘の本文にコードフェンスがあっても、JSON配列として読める最初の閉じフェンスまでを
  読むので途中で切れません。
  読めた返答の指摘は、判定とnotesとは別に、レビューstepの出力に構造化して保存し、
  レポートに出します（後述の **Review rounds**）。`blocker` と `non-blocker` は
  それぞれ先頭20件までを元の順序で残すので、`blocker` が多くても `non-blocker` は
  消えません。各指摘の `title` と `file` は200文字、`body` は600文字までに切り、
  省いた項目は付けません。`review-incomplete` で止まった返答の指摘は保存しません。
- `findings-json` はproviderを問わず使えます。`command` と `local-instructions` は
  Claudeとfakeのレビューだけが使えます。Codexのレビューに書くと、`trigger` の
  時点で役割名と項目を示して拒否します。CLIを通さずjobを直接 `trigger` した
  場合も、入力の検査で拒否し、runは作られません。fakeで使えるのはテストのためで、fakeの
  判定は実LLMの判定として数えません。
- 三つとも書かない役割は、従来どおりのpromptとverdictで動きます。どれか一つでも
  書いた役割だけ、三つの確定値が `configVersion` に入ります。どの役割も書かなければ
  `configVersion` は変わりません。`demo repair` の子runは、`--max-iterations` を除いて親の設定をそのまま使います。

`command` か `local-instructions` を使う役割があるrunでは、candidateをレビューする
直前に、次のものを `runs/<runId>/review-snapshots/` に作ります。どれもworktreeの外に
あり、候補の差分、反復のcommit、squash branchには入りません。

- `base/`：base commitのtree。runで一度だけ書き出して使い回します。
- `<candidate>/head/`：candidate commitのtree。
- `<candidate>/<役割>/cwd/`：その役割のレビューの作業ディレクトリ。base commitの
  `CLAUDE.md` と `.claude/`（あれば）と、factoryが書く `CLAUDE.local.md`
  （`local-instructions` ならレビューの指示全体、`prompt` ならcandidateの場所）を
  置きます。リンクは、たどった先がbaseのtreeの中にあるときだけ中身をコピーします。
  treeの外（ホストのファイルやディレクトリ）を指すリンク、どこも指さないリンク、
  コピー中のディレクトリに戻るリンクはコピーしません。役割ごとに別なので、
  二つのレビューが互いの指示を読むことはなく、従来どおり並行して呼びます。

treeは、commitを一時的なindexに読み込んで `git checkout-index` で書き出します。
`git archive` と違い、`.gitattributes` の `export-ignore` や `export-subst` で
中身が変わりません（checkoutのfilterや改行の変換はworktreeと同じく効きます）。
アーカイブファイルは作りません。書き出すgitのプロセスはほかの子プロセスと同じく
登録するので、cancel、leaseの喪失、workerの停止で止まります。やり直したレビューは、
中断した書き出しが残した途中のtree、一時的なindex、そのロックファイルを消してから
足りないtreeを書き出し直し、作業ディレクトリは作り直します。

消すのはworkerです。candidateのtreeと作業ディレクトリは、そのレビューの回が
終われば（失敗や中断でも、記録済みの結果を読むだけのやり直しでも）消します。
もうレビューが来ない工程（承認、完了、停止）の前にはbaseのtreeも消すので、
workerがレビューの記録の直後に落ちても、承認待ちの間に残りません。runが失敗する、
cancelされる、終わる、setupをやり直す、のいずれでも全体を消します。失敗とcancelでは、
jobの中で消し終えてからrunの状態が記録されます。別のプロセスから `demo cancel` した
ときは、workerにはleaseの喪失としか見えず、ほかのworkerがrunを拾い直す場合に備えて
workerは消しません。代わりにcancelした側が消しますが、そのときworkerが書き出していた
treeは残ることがあります。workerは起動時に、終わったrun（完了、失敗、cancel）の
`review-snapshots/` をすべて消すので、そうした残りも次の起動で消えます。このとき
見るのはworker自身のstate rootのrunだけで、データベースを調べるのは
`review-snapshots/` が残っているrunだけです。

`command` か `local-instructions` を使うClaudeのレビューは、次の設定で動きます。
通常のClaudeの呼び出しの設定は変わりません。

- `cwd` は上の作業ディレクトリです。`settingSources` は `project` と `local` なので、
  読み込む設定は、base commitの `CLAUDE.md` と `.claude/`（settings、コマンド、skill、
  agentの定義）と、factoryの `CLAUDE.local.md` だけです。candidateの `CLAUDE.md` や
  `.claude/` は、実装役が書き換えられるので読み込みません。baseはすでにマージされた
  コードなので信頼します。`CLAUDE.md` が `@` で取り込む別のファイルは作業ディレクトリに
  無いので読まれません。Claude Codeはcwdより上のディレクトリの `CLAUDE.md` も読みますが、
  そこにcandidateのファイルはありません。
- candidateはデータとしてだけ読みます。worktree、差分・変更ファイル一覧のある
  ディレクトリ、二つのtreeは `additionalDirectories` にしません。Claude Codeは追加
  ディレクトリの `.claude/` にあるskill、コマンド、agentの定義を読み込むからです。
  これらは、許可した道具と下の検査を通して読みます。
- 使える道具は `Read`、`Grep`、`Glob`、`Agent` だけで、`permissionMode` は `dontAsk`
  です。
- 読み込んだ設定のうちプログラムを動かすものは止めます。`--settings` と同じ層
  （project、localより優先）で `disableAllHooks` と `disableSkillShellExecution` を
  指定し、settingsやpluginのhookとstatus line、コマンドやskillに埋め込んだshell
  （`!` の行）を動かしません。`strictMcpConfig` と空の `mcpServers` で、`.mcp.json`
  やsettingsのMCPサーバーも起動しません。`!` の出力に頼るコマンドは、出力の代わりに
  プレースホルダーを受け取ります。factoryの検査はSDKに渡すcallbackなので、これらの
  影響を受けません。baseのsettingsにある `env` や認証用のhelperは、baseを信頼する
  ので止めていません。
- 読めるのは作業ディレクトリ、worktree、差分・変更ファイル一覧のあるディレクトリ、
  二つのtreeだけです。`canUseTool` と `PreToolUse` hookが、サブエージェントの
  呼び出しも含めて、Bash、書き込み、ほかの場所への読み取りを拒否します。
  パスはシンボリックリンクを解決してから比べるので、candidateやtreeの中から外を
  指すリンクは通りません。`~` で始まるパスも拒否します。`Grep` と `Glob` がディレクトリを
  たどる途中のリンクは、ツールがリンクをたどらないこと（ripgrepの既定）に頼ります。
- `Agent` は、`isolation`（`worktree` や `remote`）を指定した呼び出しを拒否します。
  `mode` が `acceptEdits`、`auto`、`bypassPermissions` の呼び出しも拒否します。
  これは念のための防御で、境界そのものではありません。サブエージェントは親の権限の
  モードを引き継ぐか、agentの定義の `permissionMode` に従い、その定義はbaseの
  `.claude/` からしか読みません。チームのメンバーを起動する道具も無く、サブエージェントの
  呼び出しも上の検査を通ります。
- セッションは保存しません（`persistSession: false`）。レビューは再開せず、呼び出し
  ごとに作業ディレクトリが違うので、保存すると `~/.claude/projects/` に呼び出しの数だけ
  項目が増えるからです。
- 使用量は最終結果の `modelUsage` から、サブエージェントの分も含めて一回分として
  数えます。親の使用量に重ねて足しません。モデルが報告しない項目は不明のままです。
  費用はモデルごとにそのモデルの単価で計算して合計し、単価の分からないモデルが
  一つでもあれば不明にします。親のモデルの単価で代用しません。
- これはこのモードのレビューだけです。ほかのClaudeの呼び出し（既定のレビューを
  含む）の使用量は、従来どおり親のループの値です。

`command` も `local-instructions` も使わず `output: findings-json` だけを書いた
Claudeのレビューは、道具を `Read` だけにして呼びます。ガードが拒む道具は
最初から見せません。

### 仕様を先に作ってレビューする（spec）

`factory.json` に `spec` を書くと、`--spec-file` を渡さなかったrepository runは、
実装の前に仕様を作ってレビューします。`--spec-file` を渡したrunと `spec` の無い
runは、これまでどおりの工程で動き、`configVersion` も変わりません。ただし
`--spec-file` を渡したrunでも `spec.checkFromSpec` があれば、baselineの前に
`spec-check` を走らせ、それが選んだcheckで採点し、`checkFromSpec` を
`configVersion` に含めます（後述の `checkFromSpec` を参照）。

```json
{
  "spec": {
    "template": "docs/spec-template.md",
    "reviewTemplate": "docs/spec-review.md",
    "maxRounds": 3,
    "author": {
      "provider": "claude",
      "model": "claude-opus-5-5",
      "effort": "high"
    },
    "fix": { "effort": "medium" },
    "review": {
      "product": { "provider": "codex", "output": "findings-json" },
      "tech": {
        "provider": "claude",
        "command": "/spec-review {base} {effort}",
        "context": "local-instructions",
        "output": "findings-json"
      }
    },
    "checkFromSpec": ["node", "scripts/check-from-spec.mjs"]
  }
}
```

工程の順番は次のとおりです。

1. 準備（setup）
2. 事前確認（preflight）。実装やレビューの役割に加えて、仕様の作成、修正、
   全レビュー役を確かめます。使えない役割があれば、仕様を書き始める前に止まります。
3. 仕様の作成。`author` がリポジトリを読み、仕様を書きます。
4. 仕様レビュー。`review` に名前を付けて並べたレビュー役が、同じ仕様を並列に
   レビューします。一人ずつ別のstepとして記録するので、再開時には済んだレビューを
   読み戻します。
5. 仕様の修正。blockerがあれば `fix` が仕様を直し、4に戻ります。blockerが
   なくなった時点の仕様を確定します。non-blockerは直す条件にしません。
6. `checkFromSpec` があれば、確定した仕様から採点コマンドを決めます。
7. 事前検証（`baselineCheck` のとき）、見立て、実装と続きます。

- 仕様ファイルは `runs/<runId>/spec/spec.md` にあり、worktreeの外です。
  `author` と `fix` はリポジトリを読めますが、書けるのはこのファイルだけです。
  Claudeは `Read`、`Grep`、`Glob`、`Edit`、`Write` だけを持ち、`Edit` と `Write` は
  このファイルに限ります。Codexはこのファイルのディレクトリを作業ディレクトリにして
  workspace-writeで動かすので、worktreeには書けません。ただし同じディレクトリに
  ほかのファイルは作れるので、`author` と `fix` の呼び出しが終わるたびに
  （成功しても失敗しても）`spec.md` 以外を消し、成功したときは消したものを
  そのstepの出力（`removed` と `warning`）に残します。この掃除はrunを止めません。
  そのうえで `spec.md` 自体が通常のファイルでなければ（シンボリックリンクなど）、
  それを消してstepを失敗させます。レビュー役は読むだけです。
- `fix` を書かなければ `author` の設定で直します。`fix` で省いた項目は `author` から
  補います。`maxRounds` の既定は3で、正の整数に限ります。0、負数、小数、
  `Number.MAX_SAFE_INTEGER` を超える値は `trigger` で拒否します。
- `template`（仕様の雛形）と `reviewTemplate`（レビューの指示）は、`factory.json`
  のあるディレクトリからの相対パスで、`trigger` の時点で一度だけ読みます。中身は
  run inputに保存し、`configVersion` に含めます。あとでファイルを直しても、
  始まったrunは変わりません。
- レビュー役の `command`、`context`、`output` は、候補のレビュー役と同じ規則で
  読みます（前の節）。違いは、候補がまだ無いので `{head}` を使えないことです。
  使えるのは `{effort}` と `{base}` だけです。仕様ファイルの場所は、
  `local-instructions` なら `CLAUDE.local.md` に、`prompt` なら入力に書きます。
  壊れた `findings-json` は通過にせず、runを止めます。
- 仕様を直す `fix` には、blockerの指摘、前の回で直した指摘、人のメモを
  「信頼しないデータ」の区画で渡します。
- 確定した仕様は、実装とレビューの `SPEC` として渡します。最後の回のnon-blocker
  （人が承認したときは残ったblockerも）は助言 `SPEC_ADVICE` として、実装だけに
  「信頼しないデータ」の区画で渡します。

#### 上限の回まで直らなかったとき

`maxRounds` 回レビューしてもblockerが残ると、`spec-wait:<n>` というdurable waitで
人の判断を待ちます。`status` と `wait` は候補の承認待ちとは別の「仕様の判断待ち」と
して表示し、次のコマンドを示します。

```bash
pnpm --filter example-local-agent-loop demo approve --run <id> --wait <waitId>
pnpm --filter example-local-agent-loop demo spec-revise --run <id> --notes-file notes.md
pnpm --filter example-local-agent-loop demo reject --run <id> --wait <waitId>
```

- `approve` はいまの仕様を確定して実装に進みます。
- `spec-revise` はメモのファイルを読み、その中身をsignalに入れます。仕様の修正と
  レビューを1回ずつ足し、まだblockerが残れば、もう一度判断を待ちます。メモの
  ファイルは入力ファイルと同じく、256 KiBまでのUTF-8で、空は拒否します。
- `reject` は実装を始めずにrunを終えます。結論は `rejected` です。
- signalには、run ID、待っている仕様のSHA-256、判断が入ります。別のrunや別の
  版の仕様に向けた判断は受け付けません。再開したworkerは、記録した判断とメモを
  そのまま使います。

#### 仕様から採点コマンドを決める（checkFromSpec）

`checkFromSpec` はargvです。runが固定した仕様（spec工程で確定した仕様か、
`--spec-file`）の絶対パスを最後の引数に足し、worktreeで、`checkTimeoutMs` 以内に
一度だけ実行します。成功したときの標準出力は次の形のJSONに限ります。

```json
{
  "check": ["pnpm", "vitest", "run", "src/calc.test.ts"],
  "notes": "calcだけで足りる"
}
```

- `check` は空でない文字列の配列で、`factory.json` の `check` と `--check` の
  代わりに、事前検証、その識別（baselineReuse）、すべての検証で使います。
  `checkFromSpec` があるとき、`check` は省けます。
- `notes` は任意で、実装と候補のレビューに `CHECK_NOTES` として「信頼しないデータ」
  の区画で渡し、reportに残します。
- 失敗、時間切れ、JSONでない出力、形の違う `check` は `spec-check-failed` で止まり、
  事前検証も実装も始めません。スクリプトを直したら、`retrigger --reload-config`
  で新しいrunを始めます。同じrunの再開で、スクリプトの結果を読み替えることはしません。
- `checkFromSpec` があるのに仕様が無い（spec工程も `--spec-file` も無い）runは、
  `trigger` で拒否します。

#### reportとweb UI

- reportの `specRounds[]` は `reviewRounds[]` と同じ形で、回ごとにレビュー役ごとの
  結果を持ちます（`lens` はレビュー役の名前です）。済んだstepから読むので、
  進行中のrunでも出ます。
- `spec` には、確定した仕様、確定した回、残った指摘を人が承認して進めたか
  （`blocked`）、助言、`checkFromSpec` が決めた採点コマンドとnotesが入ります。
  確定する前は、最後に書かれた仕様を `content` と `sha256` に入れ、`round` は
  `null` のままです。仕様の判断を待つ間も、判断する仕様をここで読めます。`--spec-file` の
  runには `spec:final` が無いので、`spec-check` がまだ済んでいなくても
  （失敗していても）runの入力の仕様を `source: "input"` として入れます。
- 使用量は `spec-author`、`spec-fix`、`spec-review:<名前>` の役割で分けて数え、
  工程の時間は `spec`、`spec-review`、`spec-check` として出します。`compare` にも
  同じ工程が並びます。3つを合わせた経過時間は `specWallMs` です。各 attempt の
  区間を重ねて数えるので、並んだ仕様レビューは一度だけ入り、区間の間（仕様の判断を
  人が待った時間など）は入りません。
- web UIは、spec工程があるrunだけ「仕様」「仕様レビュー」を工程に出し、仕様の
  判断待ちを候補の承認待ちとは別の状態で見せます。

### 外部の指摘から修正する（repair）

承認して納品まで終わったrepository runに、あとからUIの確認、正式なレビュー、CIなど
factoryの外で指摘が見つかったときは、`demo repair` でそのrunの候補を直す子runを
起動します。終わったrunを再開するのではなく、候補のcommitを引き継ぐ新しいrunとして
記録するので、修正の時間、費用、回数もfactoryで測れます。

修正の回数を使い切ってもチェックが通らずに止まったrun（`verification-failed`）と、
チェックは通ったのにレビューが修正を求めたまま止まったrun（`review-cap-reached`）、
最後の候補がチェックを通ったあとにレビューが終わらず失敗したrun
（`review-incomplete`）も、同じ `demo repair` で最後の候補から続けられます。`retrigger` と違って実装を
最初からやり直さず、修正の回数を新しくして最後の候補を直します。

```bash
pnpm --filter example-local-agent-loop demo repair --run <親の runId> \
  [--findings-file findings.md] [--dispositions-file dispositions.md] \
  [--context-file decisions.md] [--max-iterations 4]
```

- 親にできるのは、repository runのうち次の4種類です。
  - `completed` で、結論が `approved`、納品が記録され、最後の候補と納品の
    commitが一致するrun。
  - `completed` で、結論が `verification-failed`、最後の候補のcommitとブランチが
    記録されたrun。納品は要りません。
  - `completed` で、結論が `review-cap-reached`、最後の候補のcommitとブランチが
    記録されたrun。納品は要りません。
  - `failed` で、runのエラーか失敗したレビューのstepのエラーが
    `review-incomplete` で始まり、最後に封をした候補のstepにcommitとブランチが
    あり、その候補のあとの検証のstepが完了して通ったrun。失敗したrunには出力が
    無いので、候補と検証の結果はrunが残したstepから読みます。

  拒否、取り消し、承認待ちのrunと、ほかの理由で失敗したrunは、候補が残っていても
  親にできません。最後の候補に封をしていない、その候補の検証が無いか落ちた、
  という失敗したrunも親にできません。
  子runが同じ条件を満たせば、さらにその子を作れます。

- 起動前に、親の候補commitが対象リポジトリにあり、記録された候補ブランチの先端が
  そのcommitのままであることを確かめます。ブランチが動いていれば何も作りません。
  子runのsetupも、worktreeとブランチを候補commitから作る直前（CLIの確認のあと、
  `setupCommand` の前）に同じ確認をします。途中で止まったsetupをやり直すときは、
  前回のworktreeとブランチを片付けてから確かめます。`demo repair` の確認のあとで
  ブランチが動いた場合や、子runを `demo retrigger` した場合も、ここで
  `candidate-moved`（`retry: yes`）として止まります。worktree、ブランチ、
  run directoryは残さず、agentは呼びません。ブランチを候補commitに戻せば
  `retrigger` で続けられます。
- `demo repair` が受け付けるのは `--run`、`--findings-file`、`--dispositions-file`、
  `--context-file`、`--max-iterations` だけです。`--publish`、`--check`、`--config` など、ほかの
  フラグは黙って無視せずエラーにします。
- 子runは、親が保存したtask、spec、issue、profile（triageも含む解決済みの値）、
  check、`selfCheck`、`testProbe`、setup、timeout、`codexPath`、commitとpublishの設定、`--max-iterations` を
  引き継ぎます。`--max-iterations`（1から5の整数）を渡したときだけ、子runの修正回数を
  その値にします。値は子runの入力に保存され、`configVersion` にも入ります。親のsetupが記録した値は `null` でもそのまま使い、setupに項目が
  無い古い親だけ保存済みの入力から補います。子の子も同じです。
  いまの `factory.json` と環境変数は読みません。`--reload-config` は受け付けません。
  設定を変えたいときは、通常の `trigger` から始めます。
- 親が `approved` なら指摘ファイルは必須です。親が `verification-failed`、
  `review-cap-reached`、`review-incomplete` なら任意で、渡せばそのファイルを
  使います。渡さなければ、親が保存した記録から指摘を作ります。
  - `verification-failed` の親では、最後の候補で失敗したチェックの出力の末尾
    （stdout と stderr）、終了コード、親が使った採点コマンドです。ログファイルは
    読まず、前の候補の結果で代用もしません。最後の候補の失敗結果が保存されて
    いなければ、指摘ファイルを求めて止まります。親のrunの中で検証に落ちた候補への
    レビューは、子runには渡しません。渡したいときは指摘ファイルに書いて渡します。
  - `review-cap-reached` の親では、runの出力に保存した各レビューの最後の判定のうち
    `needsChanges` のものを、レビューの種類ごとの見出しとメモにまとめます。
    `pass` のレビューのメモは入れません。`findings-json` で答えるレビューのメモは、
    保存済みの直すべき指摘の行です。途中の回の工程やログは読みません。
    `needsChanges` のレビューが無いか、メモが空白だけなら、指摘ファイルを
    求めて止まります。
  - `review-incomplete` の親では、最後の候補の回のレビューのstepのうち、完了して
    `needsChanges` を返したものを、同じくレビューの種類ごとの見出しとメモに
    まとめます。前の候補のレビューと、終わらなかった、取り消した、失敗した
    レビューは入れません。該当するレビューが無いか、メモが空白だけなら、
    指摘ファイルを求めて止まります。
- 処分ファイルは任意で、指定すると親の処分を置き換え、
  省略すると親の処分を引き継ぎます。どちらも `--task-file` と同じ検査（256 KiB
  まで、UTF-8、空白だけは不可）を通し、内容と読み込んだパスを子runに保存します。
  指摘は修正担当と両レビュアーに、task、specと同じ信頼しない入力として渡します。
  記録から作った指摘も同じです。
  処分はこれまでどおり両レビュアーにだけ渡します。親が `approved` なら、
  レビュアーには、承認済みの候補に対する修正だけの差分を見て、指摘に応えているか、
  承認済みの候補を壊していないかを判断するよう伝えます。親が `verification-failed`
  なら、修正担当とレビュアーに、基点の候補はチェックが通らず承認されていないことを
  伝えます。親が `review-cap-reached` なら、チェックは通ったもののレビューの上限の
  あとも指摘が残り、承認されていないことを伝えます。親が `review-incomplete` なら、
  チェックは通ったもののレビューが終わらず、候補全体をまだ誰もレビューしていない
  ことを伝えます。どれも、レビュアーには
  基点と修正を合わせた候補全体をtaskとspecに照らして判断する
  よう伝えます。レビュアーに渡す変更ファイルの一覧は修正の分だけなので、基点の
  変更は、CANDIDATE FILES の節が示す候補の木を読んで確かめるよう伝えます。
  節が木を示していなければ、作業ディレクトリを読みます。
- 子runの基点は親の最後の候補commitです。親の元のbaseや、起動時点の `HEAD` は
  使いません。反復のブランチはissueの有無にかかわらず `factory/<子の runId>`、
  squashedブランチは `factory/<子の runId>-squashed` で、差分、patch、squashed
  commitの親はすべて親の候補commitです。
- 子runでもsetup、preflight、設定していればbaselineCheckを実行します。
  `baselineReuse` も親の設定を引き継ぎます。ただし親が `verification-failed`
  の子runはbaselineCheckを実行しません。基点は親のチェックが失敗した候補なので
  必ず `baseline-check-failed` で止まり、その失敗はすでに指摘として渡しているから
  です。設定は記録して孫runへ引き継ぎ、reportの「Baseline check」節は `none`
  になります。親が `review-cap-reached` か `review-incomplete` の子runは、基点が
  チェックを通った候補なので、baselineCheckを通常どおり実行します。triageと
  初回実装は行わず（triage profileは記録するだけで、呼び出しも事前確認も、CLIの
  確認もしません）、最初のcode工程を `repair` の1回目として新しいsessionで始め
  ます。`profiles.repair` があればそれを使います。そのあとは通常どおり検証、
  両レビュー、承認、納品に進みます。
- 子runの `--max-iterations` は、引き継いだ値でも指定した値でも、子run自身の
  修正回数だけを数え、親が使った回数は差し引きません。最初の修正も修正回数と
  使用量に入ります。
- `--context-file` を渡すと、子runのcontextは親のものと置き換わります。渡さなければ
  親が保存したcontextと読込元を引き継ぎます。上限はtriggerと同じ32 KiBです。
- 同じ親、同じ指摘の内容、同じ処分の内容、同じ修正回数、同じcontextの内容で起動
  すると、パスが違っても同じ子runを返し、runもブランチも増やしません。記録から
  作った指摘は親の記録だけで決まるので、繰り返しても同じ子runです。指摘か処分か
  contextの内容、または修正回数が変われば別の子runです。親と同じ修正回数を指定
  したときは、省略したときと同じ子runです。contextの無い子runは、contextが加わる
  前と同じ子runです。
- `--publish` のDraft PRは通常のrunと同じく既定ブランチ向けです。親がまだ
  mergeされていなければ、PRには親の変更も含まれます。
- 子runは起動するどの経路（`demo repair`、`demo retrigger`、`demo seed`）でも
  run label `repairOf=<親の runId>` を付けます。1件の `report`、`status --run`、
  CLIの `compare`、web UIの詳細は、このlabelで子を1回問い合わせます。SQLiteは
  この問い合わせでjobのrunを順に見てlabelを引くので、費用は履歴の長さに比例
  します。web UIの一覧と比較は、読み込んだ全runのlabel（無ければ入力の
  `repairOf`）から親ごとの子を一度にまとめ、runごとには問い合わせません。
- `report` と `status --run` には親のIDと子のID一覧が、reportには指摘ファイルの
  パスと保存内容のSHA-256も出ます。記録から作った指摘は、パスの代わりに作った元の
  親runを示します（JSONでは `parentRun`）。web UIでは一覧と詳細で、親と子をtaskの名前で
  リンクします。`compare` は通常のrunと子runを別のグループに分け、親の時間、費用、
  工程を子の値に足しません。子run同士は `configVersion` ごとにまとめます。
- 判断の理由は [ADR-0022](../../docs/adr/0022-local-agent-loop-external-repair-runs.md)
  と、`verification-failed`、`review-cap-reached`、`review-incomplete` の親を加えた
  [ADR-0030](../../docs/adr/0030-local-agent-loop-verification-failed-repair.md)
  にあります。
- `verification-failed` か `review-cap-reached` で止まったrepository runの次の一手
  には、`retrigger` と並べて `demo repair --run <id>` を出します。
  `review-incomplete` で失敗したrepository runでは、最後の候補が記録されていて
  その検証が通っているときだけ、次の一手に `demo repair --run <id>` を出します。

### durably checkoutを固定して呼ぶ

コードを対象リポジトリへコピーせず、durablyのcheckoutを特定のcommitに固定して
そのまま呼ぶこともできます。

```bash
git -C ~/src/durably fetch
git -C ~/src/durably checkout <commit>
pnpm -C ~/src/durably install --frozen-lockfile
pnpm -C ~/src/durably --filter example-local-agent-loop demo worker     # Terminal 1
pnpm -C ~/src/durably --filter example-local-agent-loop demo trigger \
  --repo "$PWD" --task-file "$PWD/task.md"                                # Terminal 2
```

Terminal 1のworkerは省略できますが、そのときは `trigger` が自動で起動する
workerが、コマンドを実行したcheckoutのCLIで動きます（「workerの自動起動と
アイドル終了」の節）。固定したcheckoutのworkerで処理させるには、先にそこで
workerを起動しておきます。

対象リポジトリに置くのは `factory.json` と作業内容のファイルだけです。固定する
commitは利用側で記録し、上げるときは意図してcheckoutし直します。コピーする方式との
比較は [docs/porting.md](docs/porting.md) にあります。

### DBと作業物の置き場所

DBと全runのデータは `~/.local/state/local-agent-loop/` に置きます。

```text
~/.local/state/local-agent-loop/
  local-agent-loop.db              run、step、attempt、wait
  runs/<runId>/
    work/                          worktree（同梱題材ではコピー）。repo runでは
                                   納品後やアーカイブ時に片付ける
    worktree-removed               納品後に片付けを始めた印（再実行の判定用）
    operation-checkpoints/         LLM呼び出しと検証のcheckpoint
    agent-logs/<attempt>.log       エージェントの出力（LLM呼び出しの試行ごと）
    verification-scratch/          検証用の一時領域
    verification-logs/<candidate>/<attempt>/
      stdout.log                   検証コマンドの標準出力（全文）
      stderr.log                   検証コマンドの標準エラー（全文）
    candidates/<candidate>/        repo runの候補ごと
      changes.diff                 base commitから候補commitまでの全差分
      changed-files.txt            変更ファイルの一覧（1行1ファイル）
    delivery/<candidate>.patch     成果物
```

- **検証ログ**: 採点コマンドの出力は、検証の物理的な試行（step attempt）ごとに
  `verification-logs/` へ切り詰めずに保存します。reportの抜粋や修正promptに渡す
  出力は従来どおり末尾だけですが、ログファイルには途中の失敗箇所も残ります。
  タイムアウトで打ち切った試行は終了コードを `null` とし、打ち切りまでの出力を
  残します。完了checkpointから復旧した試行は採点をやり直さず、元の試行のログと
  終了コードを指します。開始checkpointだけが残った試行は採点し直し、新しい試行の
  ログを別のディレクトリに書きます。止まった試行のログも消しません。
  キャンセルやリースの喪失で中断した試行も、終了コードを `null` として途中までの
  ログを記録し、`interrupted: true` を付けます。この試行は判定を出していないので、
  検証の結果には数えません。子プロセスを起動する前に中断した試行はログを記録しません。
  ログファイルへの書き込みに失敗しても検証の結果は変えず、エラーを
  `writeError` に残します。そのログファイルは中身が欠けているかもしれません。
- **エージェントの出力**: LLMを呼ぶ試行は、送る前に `agent-logs/<attempt>.log` を作り、
  そのパスを試行の `agentLog.path` に記録してから呼び出します。assistant の本文を
  届いた順に、ツールの呼び出しを名前と短い引数（コマンド、検索語、パスを優先）で
  `> exec pnpm test` のように1行ずつ、コマンドの終了コードを `< exec exit 1` の
  ように1行ずつ追記します。prompt、
  思考や推論のブロック、使用量は書きません。完了checkpointから復旧した試行と、
  送る前に取りやめた試行はファイルを作りません。追記に失敗しても呼び出しの結果は
  変えず、エラーを `agentLog.writeError` に残します。作業ツリーの片付けや
  `demo prune` では消しません。保存期限やローテーションはありません。
- **候補の差分**: repo runでは候補を封印するたびに、記録済みのbase commitと候補
  commitの差分を `candidates/<candidate>/` に書き出します。worktreeの外なので、
  agentが書き換えることはできません。検証で止まってレビューに進まなかった候補にも
  書きます。両方のレビュアーのpromptにはこの二つのファイルの絶対パスが入り、
  全文を読むよう指示します。Claudeのレビュアーは、作業場所の外ではこの二つの
  ファイルだけを読め、書き込みはできません。

worker、trigger、status、waits、approve、report、compareはすべて引数なしで同じDBを
見ます。ディレクトリが無ければDBを開く前に作ります。durablyのcheckoutの中にも、対象
リポジトリの中にも、DBや `runs/` は作りません。checkoutをどのcommitに切り替えても、
過去のrunはそのまま読めます。置き場所を変える引数や環境変数はありません。二つの
プロセスが別のDBを見ると、runが黙って見えなくなるからです。

### 以前の版からの移行 (Upgrading)

以前の版はDBを `examples/local-agent-loop/local-agent-loop.db`（または `DURABLY_DB`
の指す場所）に、作業物を `examples/local-agent-loop/runs/` に置いていました。
この版はそれらを読まず、移行もしません。checkoutに古いDBが残っていると、
workerとCLIは起動時にその場所と新しい場所をstderrに一度警告します。承認待ちや
実行中のrunが残っているなら、上げる前に以前の版で終わらせるか破棄してください。
その後、古いDBと `runs/` は消して構いません。worktreeを消したときは、対象
リポジトリで `git worktree prune` を実行します。

### 使用量の責任範囲

factoryが責任を持つのは、factoryのDBと `report --format json` までです。利用側で
使用量の台帳をつけている場合は、run終了後に利用側がreportを読んで取り込みます。
factoryから台帳へ書き込むことはしません。

```bash
pnpm --filter example-local-agent-loop demo report --run <runId> --format json \
  | jq '{runId, configVersion, inputs, delivery, roleUsage, summary}'
```

`roleUsage` は `code`、`correctness`、`edge-cases` の三行で、それぞれrequested
provider/model/effort、invocation数、token内訳、合計token、cost、`complete`、
`costComplete` を持ちます。fake providerのようにusageを返さない呼び出しは0にせず、
tokenとcostを `null`、`complete` を `false` にします。tokenがそろっていても価格表に
無いmodelならcostは `null`、`costComplete` は `false` です。

## `reuse` と `fresh` の比較

同じ題材、プロバイダー、モデル、推論量、最大反復数で、2 つの実行を作ります。

```bash
pnpm --filter example-local-agent-loop demo trigger \
  --provider codex --context reuse --model gpt-5.6-sol --effort medium

pnpm --filter example-local-agent-loop demo trigger \
  --provider codex --context fresh --model gpt-5.6-sol --effort medium
```

両方を承認まで進め、`compare` で、修正回数、キャッシュの読み込みと書き込み、
実作業時間、レビューを並べて動かした区間、人の待ち時間、実行全体の時間の中央値を
比べます。セッションを続けても、キャッシュが使われるとは限りません。効果は、
プロバイダーが報告したキャッシュの使用量で判断します。

モデルと推論量は、コマンドラインとプリセットの表だけで決まります。環境変数は
一切使いません。実行の構成を、それを起動したコマンドを読めば分かるように
しておくためです。とくに `CLAUDE_EFFORT` は Claude Code がシェルへ export する
ので、これに従うと、「どのエージェントのセッションからコマンドを打ったか」で
推論量が変わります。同じつもりの実行が、別の `configVersion` に分かれてしまいます。

## 呼び出しの識別と復旧

次の ID を混同しません。

```text
sessionId      provider-native conversation/thread
operationKey   一つの論理的な仕事
invocationId   実際に送った一回の依頼
attempt.id     Durably step callbackの実行試行
```

LLM の呼び出しと固定テストは、実行する前に、`operationKey` と `invocationId` の
開始のチェックポイントを保存します。結果を受け取ったら、完了のチェックポイントを
途中で切れない形で（atomic に）保存してから、Durably の `step` を完了します。
復旧するときに完了のチェックポイントがあれば、同じ結果を読み、依頼もテストも
送り直しません。

開始の記録だけが残ったときの扱いは、その仕事を送り直してよいかどうかで分かれます。

- **LLM の呼び出し**: 自動では送り直さず、`uncertain external invocation` で
  止まります。CLI がすでに仕事を終えて課金されたかもしれず、それをこちらからは
  判定できないためです。
- **固定テスト**: 古い開始の記録を消して、採点し直します。固定した候補を読み、
  使い捨ての作業ディレクトリ（scratch）へ書くだけなので、もう一度動かしても
  費用はかからず、同じ判定になります。そのため、ワーカーを `kill -9` する再開の
  デモが、ずっと詰まったままになることはありません。

作業物とチェックポイントは `~/.local/state/local-agent-loop/runs/<runId>/` に
残ります。独自の常駐プロセス（daemon）や、送信を管理する DB はありません。

この取り決めは、「結果を受け取ったあと、Durably のチェックポイントの前」に起きる
重複を防ぎます。一方、CLI が作業を終えた直後で、完了のチェックポイントの前に
プロセスを強制終了した場合は、未確定として止まります。初版では、プロバイダー側の
会話の履歴を推測して、自動で採用することはしません。

## 計測

LLM の呼び出しはすべて `src/engine/runner.ts` を通り、試行のメタデータへ次の値を
保存します。

- 要求した（requested）、実際に使った（effective）、プロバイダーが報告した
  （provider-reported）モデルと推論量（指定がない値と報告がない値は `null`）
- `sessionId`、`operationKey`、`invocationId`、回収した結果かどうか
- 修正の呼び出しでは、呼び出す前に決めたセッションの扱い（`sessionHandling`：
  `continued`、`continued-effort-change`、`fresh`）とその理由（`sessionReason`）
- 通常の入力、キャッシュの読み込み、キャッシュの書き込み、出力、合計のトークン
- 使用量の単位（このサンプルでは、プロバイダーへの 1 回の呼び出し）と、取得元
- 経過時間、結果、エラー、中断の理由、API 換算の参考価格と、料金の項目（meter）
  ごとの内訳
- `configVersion`（3 つの役割それぞれのプロバイダー、モデル、推論量、会話の文脈の
  扱い、指示の版、反復の上限、対象、時間の上限のハッシュ。事前判定のプロファイル、
  `code` と違う修正のプロファイル、`selfCheck` のコマンドがあれば、それも含む。
  推論量だけ違う修正でセッションを続けると事前確認で確定した実行では、その方針も
  含む。事前確認の最小の呼び出しには、確定する前の版が入る）

プロバイダーが返す使用量は、1 回の呼び出しの中の**すべてのモデルの応答の合計**で
なければいけません。エージェントの CLI は、1 回の呼び出しの中で何十回もモデルを
呼ぶので、最後の応答だけでは桁が変わります。

- **Claude**: Agent SDK の `result` メッセージの累計を、そのまま使います。
  Claude Code の記録（transcript）にある各応答の合計と一致することを確かめて
  あります。
- **Codex**: `ai-sdk-provider-codex-cli@2.3.0` は、応答ごとの `thread/tokenUsage/updated`
  を、ターンの中で合計します（2.2.1 は上書きしていたため、最後の応答の分しか
  返しませんでした。
  [ben-vargas/ai-sdk-provider-codex-cli#49](https://github.com/ben-vargas/ai-sdk-provider-codex-cli/issues/49)
  で報告し、`patches/` のパッチで直していました。2.3.0 で上流に入ったので、パッチは
  外しています）。増えた分は、ターンを始める前のスレッドの累計からの差で求めるので、
  `--context reuse` でも前回の呼び出しの分は含みません。キャッシュの書き込みも、
  上流で `0` 固定をやめ、
  app-server が返す値を読むようにしています。ただし ChatGPT のログイン（サブスク）
  では、実際に書き込んだかどうかに関係なく、サーバーが常に 0 を返します
  （[openai/codex#32479](https://github.com/openai/codex/issues/32479)）。この環境の
  33 万の応答のうち、確実に書き込みが起きた 2,334 件も、すべて 0 でした。そのため、
  ChatGPT のログインでの 0 は不明として扱い、正の値だけを使います。API キーでは
  値が実際の数なので、0 もそのまま使います。ログインの方式は `codex login status`
  で判定します。キャッシュの書き込みが分からない呼び出しがあると、レポートには
  「書き込みの割増を含まない下限」と注記します。
  この修正の前は、実際には 25 回応答していた実装の工程が 1 回分として記録され、
  実行全体の費用が約 16 分の 1 に見えていました。

集計では、`invocationId` ごとに 1 回だけ数えます。同じ完了のチェックポイントを
別の試行が読み直しても、トークンを二重に数えません。ローカルのテストや、次の
工程を決める判断（policy）などは、使用量の対象外です。LLM を呼んだのに使用量がない
場合は、欠測として件数を残し、完全な合計にはしません。

レポートは、SQLite にある実行、試行、待ちの記録から作り直す、副作用のない処理です。

```bash
pnpm --filter example-local-agent-loop demo report --run <runId> --format json
pnpm --filter example-local-agent-loop demo report --run <runId> --format md \
  --out reports/<runId>.md
```

レポートは、次の三層に分けて出します。

- **Summary**: 実行 1 本を 1 行にまとめた値。成功したか（success）、所要時間
  （lead time。登録から終わるまで）、作業時間（work。工程の実作業の合計）、人の
  待ち時間（human wait）と、その所要時間に対する比、LLM の呼び出し数、合計の
  トークン（total tokens）、費用（cost）、成功 1 回あたりの費用（cost per success。
  成功した実行だけ）、修正回数（repairs）、レビューの回数（review rounds）
- **Inputs / Candidate / Delivery**: タスク、仕様、指摘の扱い（dispositions）、
  文脈の各ファイルの SHA-256（文脈は読み込み元と本文も）、最後に封印した候補の
  ブランチとコミット、成果物の場所、ブランチ名、コミット SHA、1 コミットにまとめた
  （squash した）ブランチの名前とコミット SHA
- **Candidates**: 封印したすべての候補（JSON の `candidates`）。候補ごとに、
  何回目の実装か、ブランチ、コミット、変更したファイルの数、追加した行数、削除した
  行数、差分のファイルと変更の一覧のパス（`changes`）を持ちます。名前の変更は
  1 ファイルと数えます。バイナリファイルは変更したファイルの数にだけ数え、行数には
  git が報告するテキストの行だけを足します。変更のない候補は、すべて 0 です。
  同梱の題材の候補は規模を記録しないので、`changes` は `null` です。`candidate` は、
  これまでどおり最後の候補です
- **Review rounds**: レビューのすべての回（JSON の `reviewRounds`）。回ごとに、
  レビューした候補と、2 人のレビュアーの判定とメモを、回の順に持ちます。保存した
  レビューの `step` の出力から組み立てるので、走っている途中、承認待ち、修正の後に
  止まった実行でも、終わった回が出ます。途中で止まった回には、終わったレビュアーの
  分だけが入ります。`reviews` は、これまでどおり最後の回です。`findings-json` の
  レビューは、`reviewRounds[].reviews[]` と `reviews[]` の両方に `findings` を
  持ちます。`findings.blocker` と `findings.nonBlocker` は、保存した指摘
  （`severity`、`title`、`body`、あれば `file`、`line`、`likelihood`、`impact`、
  `thresholdException`）の配列で、それぞれ先頭の 20 件までです。`findings.counts`
  は、省いた分も含めた `severity` ごとの総件数です。件数は、配列の長さではなく、
  こちらで読みます。
  指摘は、完了したチェックポイントの返答をレビューの `step` が読んだときに保存した
  ものです。レポートを作るときに、レビュアーを呼び直したり、チェックポイントを
  読み直したりはしません。`verdict` のレビューと、指摘を保存するようになる前の
  実行のレビューは、`findings: null` です。実行の出力（`output.reviews`）には、
  指摘を入れません。Markdown と画面には、総件数と、保存した指摘の題名、省いた件数
  だけを出し、本文、ファイル、行番号は出しません。
  Markdown では、各レビューの指摘の一覧で、採点値か `thresholdException` のある
  指摘の題名の後ろに、`(likelihood 2, impact 3)` や
  `(likelihood 2, impact 3, exception not-product)` の形で付けます。レビューの
  要点（`reviewHighlights` の各群の `kept`）の題名には、採点値だけを同じ形で
  付けます。画面では、レビューの要点と、各レビューの指摘の一覧の題名の横に、
  頻度と深刻さを添えます。
  メモの表示は変わらないので、`blocker` の場所と本文は、これまでどおりメモに出ます
- **Verification logs**: 検証の試行ごとの終了コードと、`stdout.log` / `stderr.log`
  のパス。JSON では `attempts[].measurement.verificationLog` で、`exitCode`、
  `stdoutPath`、`stderrPath` に加えて、中断した試行には `interrupted: true`、
  書き込みに失敗したログには `writeError` が入ります。Markdown では、中断した試行の
  行に `interrupted, not part of the verdict` を付け、書き込みのエラーを
  `log write error:` の行に出します。検証の失敗で止まった実行では、最後の検証の
  すべての試行の終了コードとログのパスを、`failure.details` にも載せます
  （`check attempt: `、`check exit code: `、`check stdout log: `、
  `check stderr log: `、`check log write error: `）
- **Repair session**: `repair` が `code` と違う実行で、推論量が変わっても実装の
  セッションを続けるかどうか（JSON の `repairSession`、Markdown の
  `repair session` の行）。準備のときの判定（`eligible` と理由）と、事前確認の
  あとに確定した判定（`continues`、モデル、理由）を持ちます。レポートの
  `configVersion` は、この確定のあとの版です
- **Repair calls**: 修正の呼び出しごとの行（JSON の `repairCalls`）。セッションの
  扱い（`continued` は同じプロファイルで続けた、`continued-effort-change` は推論量
  だけ違うプロファイルで続けた、`fresh` は新しいセッション）とその理由
  （`sessionReason`）、入力、キャッシュの読み込み、その呼び出しの
  キャッシュの読み込みの比率（`cacheReadTokens / inputTokens`）を持ちます。使用量が
  ないときや、入力が 0 のとき、比率は `null` です。回収した呼び出しも 1 行で、
  `(recovered)` を付けます。続けた修正の比率が高く、新しいセッションの修正の比率が
  0 に近ければ、キャッシュが効いています
- **Triage**: 事前判定（`routine` / `probe` / `unknown`）とその理由、4 つの
  較正の材料（分からなければ `unknown`）。判定のない実行は `none`
- **Stage usage**: 工程ごとの visits / reworked（同じ工程にもう一度入った回数、
  つまり手戻り）、呼び出しの数、in / cache-read / cache-write / out / total、
  費用（cost）。どれかの呼び出しの使用量が数えられていなければ PARTIAL、価格が
  分からなければ unknown
- **Role usage**: `code`、`correctness`、`edge-cases`（修正を呼んだか、修正の
  プロファイルがあれば `repair`、事前判定のプロファイルがあれば `triage` も）ごとの、
  要求したプロバイダー / モデル / 推論量、呼び出しの数、トークン、費用、使用量と
  費用のそれぞれがそろっているかどうか。2 つのレビューを別の行に分けるので、役割
  ごとに違うモデルを使った実行でも、内訳が混ざりません
- **Timing / Attempts / Waits**: これまでどおりの、工程ごとの work / wall の時間、
  呼び出しごとの生のデータ、承認待ちの inputWait / executionSlotWait
- **Versions**: `ai` とプロバイダーのパッケージの版に加えて、プロバイダーが実際に
  起動した CLI の版とパス。Codex は `codexCli` / `codexCliPath`、Claude は
  `claudeCli` / `claudeCliPath` です。Codex は、`codexPath` がなければ PATH 上の
  `codex` を起動し、それもないときだけ、プロバイダーが解決できる `@openai/codex` を
  `node <パッケージ>/bin/codex.js` として起動します。Claude Agent SDK は同梱の
  ネイティブバイナリを起動し、PATH 上の `claude` は使いません。factory は同じ
  解決を行い、その実行ファイルをプロバイダーに明示して渡すので、記録した版と
  起動した CLI は同じファイルです。見つからない値は `null` にし、別のインストール
  から推測しません

価格は、サブスクの請求額ではなく、各呼び出しのときに保存した
`api-equivalent-estimate` の参考値です。AI SDK v7 の使用量の取り決めに合わせて、
`inputTokens` 全体のうち、キャッシュの読み込みと書き込みはそれぞれの料金の項目
（meter）の単価で、残りは入力の単価で計算します。キャッシュの書き込みは、どちらも
入力の 1.25 倍です。キャッシュの読み込みはモデルごとに違い、多くは 0.1 倍、
Claude Opus 5.5 は 0.05 倍、Claude Fable 5.1 は 0.025 倍です。価格表は
`src/engine/pricing.ts` にあり、確かめた日と出典を `PRICE_BASIS` に記録して
います。キャッシュの内訳（cache legs）が報告されなかった呼び出しは、入力全体を
定価で扱い、`costCacheAware: false` として区別します。レポートは保存した値を
合計し、今の価格表で計算し直したとは表示しません。知らないモデルや、欠けた
使用量を、0 円としては扱いません。

### 止めた呼び出しの使用量

最後まで終わらなかった呼び出しも、止めるまでに使った分を残します
（[ADR-0034](../../docs/adr/0034-local-agent-loop-stopped-call-usage.md)）。
Claude と Codex は、呼び出しの途中でも、その時点までの累計を報告します。

- **Claude**: API の応答ごとの使用量を、message ID ごとに 1 回だけ足し、
  モデル別にも分けます。assistant メッセージの使用量は応答を始めたときの値で、
  出力はほとんど入っていません。そのため、途中の使用量を記録する呼び出しでは、
  Agent SDK のストリームのイベント（`includePartialMessages`）も受け取り、
  `message_start` で応答を、`message_delta` でその応答のその時点までの
  出力を読みます。各項目（leg）は応答の中で増えるだけなので、見えた最大の値を
  使います。Claude Code が自分で作る
  `<synthetic>` のメッセージと、トークンのないメッセージは数えません。最終の
  使用量と同じ範囲で数えるので、サブエージェントは `command` モードのレビューでだけ
  数えます。セッション ID は、結果を待たずに、各メッセージから読みます。
- **Codex**: app-server の `thread/tokenUsage/updated` を、プロバイダーの最終の
  集計と同じく、スレッドの累計の増えた分で足します。最初の通知は直前の応答の分
  だけを足すので、`--context reuse` で再開したスレッドの前回の分は入りません。
  この通知を読むために、加工していない通知（raw 通知）を有効にします。ただし、
  raw 通知は活動として数えず、エージェントのログにも書きません。無通信の時間を
  数え直すのは、トークンのある使用量の通知だけです（ほかの途中の使用量と同じ）。
  それ以外の raw 通知と、トークンのない使用量の通知では、数え直しません。
  スレッド ID は、ターンを始める前に `onSessionCreated` で受け取ります。

検証の失敗でレビューを止めたとき（`superseded-by-verify`）と、factory の時間の
上限で止めたとき（`timeout`）は、止めた時点までの使用量、モデル別の内訳、
セッション ID、報告の回数と最後の報告の時刻を、完了のチェックポイントにも保存
します。ワーカーが再開してチェックポイントを読み直した試行にも、送り直さずに同じ
値が入ります。実行の取り消しや、リースを失ったことで止まった呼び出しは、結果が
分からないので、これまでどおり `uncertain` のままにし、完了のチェックポイントは
作りません。それまでに受け取った値は、試行の計測にだけ残します。

止めた呼び出しの結果は、これまでどおり使いません。採点、承認、レビューの回数には
入らず、残るのは使用量だけです。最終の使用量を受け取った呼び出しでは、途中の
累計を最終の値で置き換えます。最終の値にモデル別の内訳がなければ、途中の内訳も
消します。最終の結果に使用量やセッション ID がないまま終わった呼び出しは、途中で
受け取った値を計測に残し、完了のチェックポイントにも保存します。そのため、
読み直した試行にも同じ値が入ります。

計測の `usageUntilStop` は、使用量が途中までであることを示します（止めた理由、
報告の回数、最後の報告の時刻と、呼び出しを始めてからの時間）。報告が一度もなかった
呼び出しは、`usage` が `null` で、報告の回数が 0 です。0 トークンとは扱いません。
レポートの JSON は `stoppedCalls` に、Markdown は「Usage of stopped calls」に、
呼び出しごとの止めた理由、報告の回数、最後の報告の時点、使用量とモデル別の内訳、
セッション ID を出します。止めた呼び出しを含む合計は、トークンがそろっていても
`complete` と `costComplete` を false にし、下限として扱います。途中の報告
（`provider-partial`）のままの使用量も同じです。最終の使用量がないまま終わった
呼び出しや、呼び出しの途中でワーカーが異常終了して `started` のまま残った試行が、これに
当たります。同じ呼び出しの試行が複数あるときは、完了した試行、止めた呼び出しとして
確定した試行（`cancelled`、`timed-out`）、それ以外の順に 1 つを選んで集計します。
Markdown の集計の行も、工程や役割の合計と同じ試行から数えます。試行の表では、途中の
報告のままの使用量とその費用に `(partial)` と付けます。Summary の total tokens も、
数えた合計のどれかが不完全なら `tokensComplete: false` にし、Markdown では
`(PARTIAL)` と付けます。`demo compare` は、不完全なトークンの合計と、不完全な
工程のトークン・キャッシュの読み込みの合計を、不明として扱います。

### モデルの選び方とサブスクでの制約

ログイン済みの CLI（サブスク）で使う前提なので、価格表に載っていても呼べない
モデルがあります。2026-09-23 に実際に呼んで確かめた結果です。

| モデル                                                        | サブスクで使えるか                                                       |
| ------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `gpt-6-astra`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna` | 使える                                                                   |
| `gpt-6-sol`, `gpt-6-luna`                                     | 使えない。ChatGPT アカウントの Codex では 400 が返る。API キーでは使える |
| `claude-opus-5-5`, `claude-sonnet-5`                          | 使える                                                                   |

`claude-opus-5-5` には Claude Code 2.1.280 以上が必要です。
`ai-sdk-provider-claude-code` は Agent SDK を版を固定して同梱しており、最新の 4.3.2
でも 2.1.278 までしか入りません。そのため、ルートの `pnpm-workspace.yaml` の
override で、`@anthropic-ai/claude-agent-sdk` を 0.3.280 に上げています。

`codex debug models` の一覧には、サブスクで呼べないモデルも出ます。一覧ではなく、
実際に呼べるかどうかで判断してください。

### 複数の実行の比較

1 本の実行は、キャッシュが使われるかどうかや修正回数でぶれるので、同じ条件で何回か
動かして、`compare` で見ます。`configVersion` が同じ実行を 1 つのグループにまとめ、
中央値 / 最小 / 最大と、欠測の数を出します。

```bash
pnpm --filter example-local-agent-loop demo compare \
  --runs <runA>,<runB>,<runC>,<runD> --format md
```

グループごとに、success の率、結論ごとの実行の数（`conclusions`。結論を記録する
前に失敗や取り消しで終わった実行は、`failed` / `cancelled` として数える）、
lead time、work、human wait、total tokens、cost、cost per success、repairs、
工程ごとの work / tokens / cache-read / cost / reworked を並べます。事前判定の
ある実行を含むグループには、判定（`routine`、`probe`、`unknown`）ごとの表が
付きます。列は、実行の数、approved、verification-failed、review-cap-reached、
repairs と cost の統計、そして、`routine` と判定されたのに修正が要った、または
上限（review cap か、検証の失敗で終わった反復の上限）に達した実行の数と、
止まった理由（`rejected-invocation`、`uncertain-invocation` など）ごとの実行の
数です。`routine` の列が判定の見逃しで、判定だけを記録するモード（shadow mode）で
測りたい値です。続く表は、同じ判定ごとに、4 つの較正の材料（タスクと仕様の文字数、
受け入れ基準の項目数、変更する予定のファイルの数）の統計を並べます。費用や較正の
材料が分からない実行は、統計から外して unknown の件数に数えます。事前判定の
呼び出しのトークンと費用は、`triage` の工程と `triage` の役割に 1 回ずつ数えます。

外部の指摘から作った修正の実行（`demo repair`）は、通常の実行とは別のグループに
まとめます。子の実行の数字はその実行自身のもので、親の時間、費用、工程は足しません。

週ごとの移り変わりは `--trend` で見ます。`--runs` は取らず、実行ではなくタスクを
数えます。タスクは、一覧と同じく、最初の実行と、その下の修正の実行（`demo repair`）
をまとめたものです。最後に作った実行が終わり、その完了時刻が直近の `--days` 日
（既定は 30）に入るタスクだけを読みます。最後の実行が動いているタスク、完了時刻の
ないタスク、期間の外で終わったタスクは数えません。

```bash
pnpm --filter example-local-agent-loop demo compare --trend
pnpm --filter example-local-agent-loop demo compare --trend --days 14 --include-fake --format json
```

- 最初の実行の実装に使ったモデルと推論量（`code` のプロファイルの
  `effectiveModel` と `effectiveEffort`）の組でまとめ、最後の実行が終わった週
  （月曜始まり、この PC の時刻）で分けます。CLI の版はまとまりに含めません。
- 週ごとと期間全体について、タスクの数、初回承認の数と率、最終承認の数と率、
  タスクの所要時間と費用の中央値 / 最小 / 最大と欠測の数、修正の実行の数の中央値を
  出します。
- 初回承認は、修正の実行なしに、最初の実行で承認されたタスクです。最終承認は、
  最後の実行が承認されて納品されたタスクです。レビューの上限で止まった実行を、
  修正の実行で直して承認されたタスクは、最終承認に数え、初回承認には数えません。
- タスクの所要時間と費用は、期間の外で終わった実行も含めた、すべての実行の合計
  です。修正の実行の数は、最初の実行の下にある実行の本数で、実行の中で修正した
  回数とは別のものです。
- 最初の実行が fake プロバイダーのタスクは除き、除いたタスクの数を `fakeExcluded`
  に出します。含めるときは `--include-fake` を付けます。
- `--days` は、1 から `Number.MAX_SAFE_INTEGER` までの整数だけを受け付けます。
  0、負の数、`NaN`、`Infinity`、小数、それより大きい数は、DB を開く前に拒否します。
- 費用や時間が分からない実行を 1 つでも含むタスクは、その中央値から外して欠測の
  数に数え、0 として混ぜません。タスクのない週は件数を 0 とし、率や中央値は出し
  ません。

`reuse` と `fresh` を比べるときは、`code` の工程のキャッシュの読み込みの比率と、
repairs の中央値を見ます。unknown は統計から外して件数だけを残し、0 として
平均に混ぜません。

## 権限と制約

- Codex の実装と修正は workspace-write、レビューは read-only のサンドボックスで
  動きます。
- 事前判定は、Codex では read-only のサンドボックス、Claude では Read だけで
  動きます。
- Claude のレビューは Read だけです。実装と修正では、`canUseTool` と
  `PreToolUse` フックの両方で、作業ディレクトリの外のパスを拒否します。これは
  入力の検査で、OS のサンドボックスではありません。`command` か
  `local-instructions` を使う Claude のレビューは `Read`、`Grep`、`Glob`、
  `Agent` だけで、読める場所は、自分の作業ディレクトリ、作業ツリー、レビュー資料の
  ディレクトリです（「レビュー役の呼び出しと出力」を参照）。このレビューが
  読み込む設定は、ベースのコミットの `CLAUDE.md` と `.claude/` だけで、候補の
  ものは読みません。フック、コマンドの中のシェル、MCP サーバーは動かしません。
- 仕様の作成と修正では、リポジトリを読み、実行が持つ仕様ファイル
  （`runs/<runId>/spec/spec.md`）だけを書けます。仕様のレビューは読むだけです
  （「仕様を先に作ってレビューする」の節）。
- 同じセッションへは、並べて送りません。並べて送るのは、新しいセッションを使う
  レビューと、仕様のレビューだけです。
- モデル、推論量、指示の版、ツール、cwd を途中で替える引き継ぎ（handoff）は、
  まだありません。`trigger` のときに解決した 3 つの役割のプロファイルを、実行の
  あいだ固定します。
- 実装と修正でセッションを続けるのは、`code` の役割のプロバイダー、プロファイル
  ID、cwd、指示の版が一致するときだけです。レビューのプロファイルは関係しません。
  `code` と違う `repair` のプロファイルでの修正は、実装のセッションを続けません。
  例外は Claude で推論量だけが違う場合で、プロファイル ID の代わりに、事前確認で
  Claude Code が報告したモデルが一致することを確かめて続けます（「effortだけ違う
  修正は実装のsessionを継続する」の節）。
- fake プロバイダーは、決まった筋書きどおりに答えるローカルの練習用（deterministic）
  で、実際の LLM での検証には数えません。

## fake モード

```bash
pnpm --filter example-local-agent-loop demo trigger \
  --provider fake --context reuse --max-iterations 3
```

ワーカーは `trigger` が自動で起動し、実行が終わってしばらく仕事がなければ、自分で
終了します（「workerの自動起動とアイドル終了」の節）。

`FAKE_FAIL_FIRST=0` で、最初の実装を成功させられます。
`FAKE_REVIEW_SEQUENCE="needsChanges,pass"` で、レビューと修正の繰り返しを再現
できます。`FAKE_TRIAGE` は、事前判定の応答を、呼び出しごとに順に選びます
（`routine`、`probe`、`empty`、`invalid`、`contradictory`、`unsupported`、
`error`。既定は `routine`）。fake の事前判定は、同梱の題材では `trigger` の
フラグから指定できないので、ジョブの入力の `profiles.triage` で渡します。

fake の事前確認（preflight）は、要求したモデルの名前で決まります。`unlisted-*` は
無料の確認で拒否され、`probe-*` は無料の確認では決まらずに最小の呼び出しが通り、
`refused-*` は最小の呼び出しがはっきり拒否されます。`rejects-*` は無料の確認で
通り、その後の実装、修正、レビュー、事前判定の呼び出しが、すべてはっきり拒否
されます。それ以外は、無料の確認で通ります。

`FAKE_LATENCY_MS=20000-90000` を付けると、各呼び出しが、その範囲のランダムな
時間だけ待ちます。取り消しと時間の上限では、待ちを打ち切ります。
`FAKE_USAGE=realistic` を付けると、役割に応じたそれらしいトークンの数を返し、
要求したモデルの価格で費用を計算します。付けなければ、これまでどおり、トークンと
費用は不明です。

ジョブの入力の `fakeScenario` は、実行ごとに fake の振る舞いを変える、デモと
テスト専用の欄です。上の環境変数と同じ項目を、実行ごとに上書きします。
`reviewSequence` と `reviewNotes` は、レビューの回ごとに correctness、edge-cases
の順で 2 つずつ並べます。回と観点で引くので、呼び出しの順番や、再起動のあとの
やり直しで、判定が入れ替わりません。`reviewOutputs` は、同じ並びで、レビューの
返答そのものを指定します（`findings-json` の壊れた返答や、途中で切れた返答も
書けます）。`reviewDenials` は、同じ並びで、その呼び出しが道具の使用を拒否された
ことにします（空文字列なら拒否なし）。テストが記録を始めているあいだ
（`recordFakeReviewCalls`）だけ、`command`、`context`、`output` を設定した
レビューの呼び出しについて、受け取った入力、作業ディレクトリとその中のファイル、
読めるディレクトリのファイルと中身、呼び出しを始めたときと返答したときの作業
ディレクトリの `CLAUDE.local.md` の有無と中身を記録します。記録していない
ワーカーは、何もためません。`output` は `{ chunks, intervalMs }` で、各呼び出しが、
返答の前に `intervalMs` ごとに `chunks` を 1 つずつ、エージェントの出力として
書きます。指定がなくても、fake の呼び出しは返答の本文を出力の最後に書きます。
`FAKE_REVIEW_SLOW_MS` は、これらの呼び出しでも edge-cases のレビューを遅らせます。
すべての役割が fake の実行でしか受け付けず、そうでなければ `trigger` のときに
断ります。`configVersion` にも入りません。`demo seed` がこれを使います。

テスト専用の `claudeEffortResume: true` を付けると、fake は「推論量を変えて
セッションを再開しても、キャッシュが残る Claude Code」の代わりをします。呼び出し
ごとに、渡された推論量をそのまま使います（`low` に固定しません）。Claude の
プロバイダーと同じく、実際に使うモデルは指定どおり（指定がなければ `fake-model`）
で、別名の解決は「CLI」の側が行います。各呼び出しは、実際に動いたモデルを報告し、
`fake` は `fake-model` として報告され、`unobserved-*` は何も報告しません。
Claude Code と同じく無料の確認がないので、事前確認では最小の呼び出しを行って、
そのモデルを読みます。実装と修正の呼び出しでは、セッションを再開したときには
キャッシュの読み込みの多い使用量を、新しいセッションのときにはキャッシュの
読み込みが 0 の使用量を返します。準備の工程もこの欄を読み、推論量だけ違う修正は、
事前確認でモデルを確かめたうえでセッションを続けます。準備の工程での判定は
`configVersion` に入ります。実際のプロバイダーには影響しません。

## ファイルの構成

コードは三層です。`engine/` はどのリポジトリでも同じもの、`factory/` は工程の
つなぎ方、`targets/` は「何を相手に働くか」です。別のリポジトリへ移すときは、
`engine/` と `factory/` をそのまま持っていき、`targets/` を書きます。

```text
src/
  engine/           リポジトリに依存しない機構
    runner.ts       LLM呼び出し1回の冪等化と計測
    verification.ts checkpoint付き検証step（採点内容は呼び出し側が渡す）
    candidate.ts    ディレクトリコピーによるCandidate封印
    git.ts          worktree、commit封印、差分、patch、push、worktreeとbranchの削除
    tree.ts         ディレクトリのhashと差分
    child.ts        process group単位で終了する子process
    providers/      AI SDK v7のCodex / Claude / fake adapter
    models.ts       modelごとのpresetとprovider既定
    usage.ts        token集計（欠測はnullのまま）
    pricing.ts      meter別のAPI換算参考価格
    report.ts       工程別集計とmarkdown/json
    build-report.ts 永続記録からのレポート組み立て
    compare.ts      config version別の複数run比較
    status.ts       runの状態区分、理由、次のコマンド（statusとweb UIで共有）
    types.ts        CandidateRef / SessionRef / ResolvedProfile
  factory/          工程のつなぎ方（何を作るかは知らない）
    target.ts       Targetインターフェース：targetsとの境界
    job.ts          役割別profileの固定、decision保存とStage dispatch
    stages.ts       code / verify / review / approve / finish / stop
    policy.ts       次に実行する工程の決定
    prompts.ts      promptの骨格（TASKとRULESはtargetが埋める）
    types.ts, events.ts, reducer.ts   状態機械
  targets/          何に対して働くか
    subject.ts      同梱の題材。固定テストで採点、成果物はディレクトリ
    repo.ts         実リポジトリ。worktreeで作業、commitで封印、patch/PRを出す
    index.ts        setup時のprepareと、replay時のcreateTarget
  ui/               web UI（server.tsとReactの画面）。操作はactions.tsを呼ぶ
  cli.ts            コマンドの入口
  trigger-input.ts  factory.jsonと入力ファイルの読み込み、trigger時の固定
  actions.ts        承認、却下、仕様の修正、再実行、アーカイブ（CLIとweb UIで共有）、pruneの対象選び
  approval.ts       candidateに結びつけた承認と却下のsignal
  demo-seed.ts      demo seedが作るデモ用のリポジトリとrun
  durably.ts        固定state directoryのDB
subject/            変更しないバグ入り題材
```

境界の形は、`engine/verification.ts` と `factory/target.ts` によく出ています。
前者は、開始と完了のチェックポイント、計測、`signal` の転送までを持ち、「何を
もって検証とするか」は `grade` コールバックとして受け取ります。後者は、作業場所、
封印の仕方、採点、レビューに渡す文脈、成果物の渡し方という、対象ごとに必ず違う
5 つだけを切り出しています。

移植の手順は [docs/porting.md](docs/porting.md) にあります。
