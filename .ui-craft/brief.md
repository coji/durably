# Project Brief

## 1. Product purpose

ローカルで動くソフトウェアファクトリー（examples/local-agent-loop）の task について、いまの状態、次に人がすべきこと、工程ごとの時間と費用を見せる。画面は次の三つの問いに答える。

1. **判断待ち・壊れているものはあるか。** 人の判断を待つ task と、止まった task が最初に目に入る。
2. **この task で何が起きたか。** 1つの task を開くと、結論、次の一手、工程の流れ、時間と費用が順に読める。
3. **factory は良くなっているか。** 設定のまとまりごとに、所要時間、費用、成功率を比べられる。

## 2. Primary user

factory の様子を見に来る owner。factory を回している開発者本人で、別のターミナルで worker を動かしながら、1日に数回、ラップトップのブラウザ（localhost）で様子を見る。利用者は1人で、画面を見る時間は短い。

## 3. Principles（上ほど優先）

1. **説明より次の一手。** 状態を細かく説明する前に、人の判断が要る run と、そこで打つべきコマンドを先に見せる。
2. **分からないものは、分からないと見せる。** 使用量や費用が不明なときは、0 や空欄で埋めずに「不明」と書く。
3. **UI は記録を映すだけ。** UI 独自の状態や計算は持たない。数字は CLI の `report` / `compare` と必ず一致させる。
4. **操作は CLI と同じ道を通す。** UI から操作するときは、CLI と同じ関数を呼び、実行の前に確認を挟み、同じ操作の CLI コマンドを添える。UI だけの近道は作らない。
5. **色は状態を表すためだけに使う。** 装飾の色は入れず、色が付くのは「人待ち」「失敗」「実行中」だけにする。
6. **迷ったら減らす。** 網羅するより、シンプルで便利なほうを選ぶ。

## 4. Success metric

ページを開いて10秒以内に、「いま動いている run がどの工程にいるか」と「人の手が要る run があるか」が分かる。終わった run の工程ごとの時間と費用を、CLI の report と同じ数字で比べられる。

## 5. Out of scope

- localhost の外への公開、ログイン、複数人での利用
- factory.json や入力ファイルの編集
- エージェントの出力のリアルタイム表示（ログのストリーミング）
- 独自のグラフ表現。時間は横棒だけで見せる（工程ごとの横棒と、工程の時系列のタイムライン）。工程の流れはステッパーで見せる

## 6. Learned constraints

<!-- 日付つきで追記する。例: - **YYYY-MM-DD** — ルール。*Why:* 理由。 -->

- **2026-09-24** — ID を主役にしない。run の見出しは task の名前（task の1行目、issue のタイトル、同梱題材の名前）にし、ID は末尾数文字を薄い等幅で補助的に出す。完全な ID はコピーと詳細画面だけ。コマンドは「〜をコピー」ボタンにして全文は開いて見る形にし、wait ID のような内部 ID は画面に出さない。時刻は相対表記を主にし、正確な時刻はホバーで出す。_Why:_ 一覧が ID で埋まると、どの run が何の作業かを目で追えず、10秒で状況を掴むという成功指標を満たせない。
- **2026-09-24** — 画面の文言で、補足をかっこで足さない。要らない補足は消し、意味のある補足はバッジ、別の行、小さなラベルなど構造で示し、細かい説明はツールチップか注記の1文に移す。_Why:_ かっこの補足が続くと1行に情報が二重に詰まり、目で追う速さが落ちる。
- **2026-09-24** — 画面の言葉は日本語にそろえる。英語のまま残すのは、そのまま打つかコピーするもの（コマンド、model 名、ブランチ、commit、ファイル名）だけ。run は「実行」、工程名は準備・見立て・実装・検証・レビュー・承認・完了、triage の判定は定型・試行が必要と訳す。_Why:_ 英語の識別子と日本語が1行に混ざると読みにくく、画面が内部の用語をそのまま見せている印象になる。
- **2026-09-30** — 画面の単位は task にする。一覧も詳細も、run の ID ではなく task の名前でまとめる。_Why:_ owner が知りたいのは「どの作業がどうなったか」で、1つの task が修正の run を含む複数の run にまたがっても、見る単位は1つのままにしたい。
- **2026-09-30** — 詳細は結論から書く。task を開いたら、最初に結果と次の一手を出し、工程、時間、費用、記録はその下に置く。_Why:_ 数分で様子を見る owner は、上から読んで途中でやめる。結論が下にあると読まれない。
- **2026-09-30** — 画面の数値と言葉は、書式関数と用語集だけを通す。費用、トークン、時間、相対時刻、短縮 ID は `src/engine/format.ts` の関数で、固定の文言は `src/ui/glossary.ts` から出す。部品と画面に文言、色、文字や余白の数値を直書きしない。_Why:_ 同じ量が画面ごとに `$6.443984` や `0 ms` のように違って見えると比べられず、訳語の揺れは画面を内部の用語のまま見せる。
